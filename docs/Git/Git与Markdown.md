# Git 与 Markdown 学习文档

> 本文档整理 Git / GitHub 的操作方法与 Markdown 语法，按知识主线组织编写，持续补充。

## 第 1 章 Git 与 GitHub 起步

### 1.1 版本管理与 GitHub 是什么

先理解"版本控制"要解决的问题：假设每次修改都另存为"最终版""最终版2""真正最终版"，时间一长就很难回答——哪一版修复了问题？昨天删除的内容在哪里？两个人的改动怎样合在一起？**版本控制**负责记录文件随时间发生的变化；Git 让你把有意义的一组改动保存为一次提交，之后可以查看历史、比较差异、找回以前保存的内容，也可以同时尝试不同方向的修改。要注意：编辑器里保存文件不会自动产生 Git 提交，做了本地提交也不会自动上传到 GitHub——记录的是你主动提交的内容。

几个名称先分清：

| 名称 | 作用 | 例子 |
|---|---|---|
| Git | 安装在电脑上的分布式版本控制工具 | 在本地记录一次修改、查看昨天的版本 |
| GitHub | 托管 Git 仓库并支持项目协作的网站 | 保存远程仓库、浏览代码、跟踪问题 |
| Git Bash | Git for Windows 提供的 Bash 终端环境 | 输入 `git status`、`cd` 等命令 |
| Markdown | 用纯文本符号描述文档结构的轻量标记语言 | 编写项目的 `README.md` |

Git 可以离线完成初始化、提交、查看历史和本地合并；连接 GitHub 时才涉及网络和权限，GitHub 也不是 Git 唯一可用的远程托管服务。Git Bash 提供部分常见命令，但不等于完整的 Linux 系统，也不保证已安装 C/C++ 编译器等依赖。

GitHub 是一个开源代码托管网站，大量企业级工程和开源工程都托管在上面，可以把它当成程序员的"工具网站"：平时上去查一查、逛一逛，找自己感兴趣的项目。

对软件研发工程师来说，会使用 GitHub 是必要技能：很多公司要求会用；有的公司项目就托管在 GitHub 上，办公时它就是日常工作网站（公司会分配对公账号，让你去管理项目）。

需要掌握的不只是"查"，还包括最基本的操作：把自己的项目代码上传到云端、下载别人的开源项目，以及在此之前需要完成的配置。网站内容以英文为主，平时用得最多的是查询。

### 1.2 仓库与分支

**仓库（Repository）** 是项目的存储单位。一个账户下可以有多个仓库，但一个仓库存储一个独立的项目——它是项目/工程的单位。比如腾讯有很多产品（QQ、微信、各款游戏），每个产品都放在各自的仓库里，一个项目一个仓库。

**仓库与分支的关系**：仓库包含分支，一个仓库可以拥有**多个分支**。

先建立几个核心概念的准确理解：

| 概念 | 准确理解 |
|---|---|
| 提交（commit） | 对当时暂存内容形成的一次版本记录，包含快照、作者、说明及父提交等信息 |
| 提交编号 | 标识提交的哈希值，日志里常显示缩写；每个人的编号通常不同 |
| 分支（branch） | 指向某个提交、并随新提交向前移动的引用，用于组织不同的开发路线 |
| HEAD | 表示当前检出的版本；正常的本地操作中，它通常指向当前分支 |
| 默认分支 | 仓库默认展示及协作使用的分支，由仓库设置决定 |

**分支不是把不同文件分别装入抽屉。** 同一个项目的两个分支可以共享大量历史，只在部分修改上不同；切换分支时，Git 会更新工作区中的文件——分支的完整操作（创建、切换、合并）见第 3 章。

关于主分支的名字：常见教程与旧项目使用 `master`，GitHub 新建仓库当前常用 `main`。两者都只是分支名称，没有"其中一个更高级"的区别；操作已有项目时要使用它实际的分支名（在仓库页面或 `git branch` 中都能看到）。

### 1.3 查找开源项目

**关键字查询。** 在搜索栏输入关键字，项目名称或内容里包含该关键字的都会被列出来。注意查询结果是**分语言**的：项目下方会标出所用语言（C++、Python、MATLAB 等）。如果不懂该语言、或本机没有对应环境（如 MATLAB、Python 环境），项目下载了也用不了——下载开源项目前先确认语言是否合适。

**示例/教程类关键词。** `sample`、`demo`、`tutorial` 是可以组合使用的普通关键词，不是平台的特殊"资料标签"；它们常出现在仓库名称、描述和 README 中，含义大致如下：

| 关键词 | 常见含义 |
|---|---|
| `sample` | 示例代码，展示某个库、框架或 API 的基本用法，通常体量较小、只覆盖核心功能 |
| `demo` | 演示项目，重在展示运行效果，通常是可以跑起来的完整小项目 |
| `tutorial` | 教程，按步骤讲解并配有说明文档，适合跟着操作学习 |

还可以用限定符把搜索范围收窄（在搜索栏输入，并在结果页选择 **Repositories**）：

```text
socket sample language:C++  # 在 sample 结果中限定语言为 C++
python tutorial             # 只用普通关键词搜索
git topic:tutorial          # 用 topic: 限定仓库主题（作者主动打的标签）
```

代码块中 `#` 及其后的内容是注释，实际搜索时不需要输入。第一行用 `language:` 限定编程语言；第三行的 `topic:` 用于限定仓库主题（作者主动打的标签），匹配方式与普通关键词不同。无论用哪种方式搜索，结果仍需检查 README、依赖要求和更新时间，不能仅凭名称判断是否适合自己。

例如搜 socket 相关样例，能找到各种 TCP 客户端、服务端的示例代码——以后学某项技术不会用时，可以找现成样例参考着写。想学 Python 时用 tutorial 查询，结果基本全是 Python 相关资料。

**Explore 与推荐。** Explore 页可以按类别、按分类浏览内容（例如了解与浏览器相关的 CSS）；推荐流类似短视频平台的推荐，展示社区里最近比较火的内容（多为小工具类项目，以英文项目为主）。可以在页面上设置自己的主语言与感兴趣的编程语言，影响推荐结果。

**搜索的典型用途。** 抢票（12306、演唱会门票）、秒杀脚本、路径规划（高德/外卖类）、AR 功能、毕业设计等，都能搜到现成的开源项目：先拿过来学习，再加入自己的内容。

**使用提醒。**

- GitHub 上内容"三教九流"什么都有：游戏外挂、抢红包、脚本工具等。分享者做的是技术分享、给的是源码，使用者自己研究可以，但**千万不要售卖、传播、盈利**——一旦涉及金钱往来，就可能被起诉。抢票、秒杀类软件本身也属灰产，可能侵犯其他公司的计算机信息系统安全，学技术可以，不要拿来牟利。
- **源码 ≠ 安装包**：GitHub 上发布的是源代码，不是打包好的程序，下载后要自己编译才能用（没有编译环境用不了）；游戏类工具有时还只适配旧版本，需要自己更新。这也是它门槛高、不如普通软件"火"的原因。
- 学编程兴趣很重要：可以到 GitHub 上找好玩的项目，边玩边学。

### 1.4 仓库里都有什么

进入一个仓库页面，主要有这几块内容：

- **Code**：存放工程源码、文档、配置文件等；页面上可以切换查看的分支，先确认当前分支对不对。开源就是把源码开放，下载到本地后用自己环境编译。
- **README.md**：项目自述文档，使用 Markdown 撰写（后缀 `.md`）。开源项目一般都有 README，说明项目是什么、支持哪些语言、如何下载安装、有哪些功能、如何解决特定问题；给别人交付东西也一定要有自述文档。README 的特殊之处是**默认显示在仓库页面上**，是别人了解项目的第一入口。
- **LICENSE**：许可证文件，说明使用、修改、分发该开源项目的权限与限制。
- **Issues**：仓库自带的问答区（小论坛）。使用时遇到 bug 可以到这里提问或查找——很多人已经遇到并解决过；作者通常会维护它，你也可以提交问题。
- **提交历史**：可以看到最近的改动、项目维护情况，以及一次提交具体修改了哪些行。
- **Releases（如有）**：作者发布的版本说明和附件，可能提供可直接运行的程序。

**不要把"下载源代码"和"安装软件"混为一谈。** 源码项目可能还需要编译、解释器或依赖，是否能直接运行要看 README；也不是所有项目都只提供源码，有些会在 Releases 里发布安装包。

> Markdown 在程序员行业非常流行：公司文档、技术分享帖（如 CSDN）都常用它来写，配合修饰符可以做出列表、代码、图片、表格等效果（第 4 章详解）。

### 1.5 开源许可证与合规使用

开源内容**不一定完全免费**，而是受许可证（LICENSE）约束。典型场景：项目里用了开源的路径规划代码，将来产品上线要盈利，就可能需要授权——给作者发邮件说明用途；若要盈利，需要获取授权（一次性买断或分期付费）。没有被授权还继续使用，被发现就可能被起诉。业界已有因开源版权问题引发的诉讼案例（使用了开源内容而未获授权，最终开发者胜诉），进入公司后这类问题会被严格追究，必须重视。

公开展示代码也不等于授予任意用途的许可；项目**缺少许可证时**，不应直接把它当作"可以任意复制、修改和分发"的开源项目。三个最常见、比较"宽松"的知名许可证，入门先记住各自要点：

| 许可证 | 入门要点 |
|---|---|
| MIT | 限制最小：允许商业使用等用途，但需要保留相应版权和许可声明 |
| Apache-2.0 | 含明确的专利授权；分发时需要保留声明、标注修改，并按条件处理 NOTICE |
| GPL-3.0 | 约束相对较强：允许商业使用，但分发受其约束的软件或衍生作品时，涉及提供对应源码及相同许可等要求 |

使用原则：

- 使用权限最大的许可证，限制最小；反之有些许可证限制很严（例如不允许打包售卖）。
- 遇到**非知名机构**的许可证，要详细阅读条款（有的要求发邮件联系作者获得授权），避免法务问题——即使是知名机构的许可证，也建议细读。
- 这张表用于识别基本差异，**不代替许可证全文**；是否收费、是否公开可见、允许怎样使用，应分别判断。

### 1.6 仓库可见性与分享管理

先注册并登录自己的 GitHub 账号。仓库网页地址通常具有 `https://github.com/所有者/仓库名` 的结构，所有者可以是个人，也可以是组织；仓库地址与本地文件夹名不必相同。

| 可见性 | 含义 |
|---|---|
| Public（公开） | 其他人通常可以浏览和克隆；不代表其他人可以直接推送 |
| Private（私有） | 只有获得相应访问权限的用户可以访问 |

**读取权限与写入权限是两件事。** 能看到公开项目、下载它并在本地修改，并不代表能把修改推回原作者的仓库。

分享作业时，通常复制浏览器地址栏中的仓库网页链接即可（手机上也能直接打开）；分享私有仓库链接不会自动赋予接收者读取权限。

**管理提醒：** 仓库设置和账号设置属于不同范围——删除仓库通常在该仓库的 **Settings → General → Danger Zone** 中；注销账号在个人账号设置中。删除前要看清对象与确认提示。删除 GitHub 仓库不会自动删除电脑里的克隆；删除本地文件夹也不会自动删除 GitHub 仓库。

## 第 2 章 本地仓库与设备认证

### 2.1 创建本地仓库：git init

先安装 Git for Windows 并打开 **Git Bash**（安装地址见附录；也可在目标文件夹中右键选择 **Open Git Bash here**，Windows 11 中该菜单有时位于"显示更多选项"内）。检查安装：

```bash
git --version        # 预期输出以 git version 开头，后面是版本号
```

`git init -b main` 指定初始分支名需要 Git 2.28 或以上版本，旧版本可先升级。

在 Git Bash 中先学会定位文件夹和输入命令：

| 命令或符号 | 含义 |
|---|---|
| `pwd` | 显示当前所在目录 |
| `ls` / `ls -a` | 列出文件 / 同时列出隐藏项目 |
| `cd 目录` / `cd ..` | 进入指定目录 / 返回上一级目录 |
| `~` | 当前用户的主目录 |
| `mkdir 目录名` | 新建目录 |
| Tab | 尝试补全命令或文件路径 |
| ↑ / ↓ | 浏览以前输入的命令 |
| Ctrl+C | 中断当前终端操作，不能保证撤销已经完成的动作 |

Windows 路径 `C:\Users\你的用户名\Desktop`，在 Git Bash 中可以写成 `/c/Users/你的用户名/Desktop`；路径包含空格时，用英文引号包起来。输入命令时使用英文半角空格、引号和减号；代码块可直接复制，不要额外输入 `$`。

在桌面新建一个文件夹（名字随意），本地仓库就放在这个文件夹里：

```bash
cd 文件夹          # 先进入该文件夹（用 cd .. 可回到上级目录）
git init -b main   # 创建本地仓库，并把初始分支名指定为 main
```

- 执行成功后，目录下会出现以点开头的隐藏文件夹 `.git`，它就是本地仓库本体（保存本地版本历史与配置）；不要手动修改或删除它。
- 判断自己是否在仓库位置：命令行提示符中会显示**当前分支名**（如 `main` 或 `master`，随仓库实际设置，不是固定值）；`cd ..` 之后没有该标志，就不在仓库位置。后续所有操作都必须在仓库位置进行。
- 为什么建议建在单独文件夹里：`.git` 默认是隐藏文件夹，很多电脑不显示隐藏文件；放在文件夹里位置好记，且以后直接删除该文件夹就等于删除仓库。
- `git init` 不会联网：不创建 GitHub 仓库，也不会生成 SSH 密钥。初始化不等于已经有了第一个版本——第一次成功提交后，`main` 才有一个可以指向的提交。

### 2.2 身份配置：git config

向云端上传数据前，要配置"你是谁"——这是**提交署名**，用于记录每次提交的作者，**不是登录凭据**（登录认证在 2.3 完成）。查看配置：

```bash
git config --list                 # 查看全部配置项
```

结果中有两项关键内容：`user.email`（提交邮箱）和 `user.name`（署名）。没有就添加，不对就修改：

```bash
git config --global user.name "你的署名"          # 添加/修改署名
git config --global user.email "you@example.com"  # 添加/修改邮箱
git config --global --unset user.email            # 删除全局邮箱配置项（不是"退出登录"）
git config --global --get user.name               # 检查单项配置
git config --global --get user.email
git config --show-origin --get user.email         # 查看该项来自哪个配置文件
```

要点：

- 配置是**键值对**格式：等号左边是键（key），右边是值（value）。
- 命令的特性：配置里没有这一项就新增，已有就修改其内容（既是添加也是修改）。
- **署名可以自定**，不必与 GitHub 用户名相同；若希望提交关联到 GitHub 账号，请使用该账号已添加的邮箱。如需隐藏个人邮箱，可以使用 GitHub 邮箱设置页提供的 noreply 地址。
- `--global` 表示设置当前电脑用户使用的默认值；在某个仓库里设置不带 `--global` 的同名项，可以覆盖该仓库使用的默认值。
- 添加完再用 `git config --list` 检查确认：关键字不能错、邮箱不能错、内容也不能错。
- `--unset` 只是删除该配置项；改错了邮箱时，重新运行设置命令通常就够了。

### 2.3 SSH 密钥与设备认证

**为什么需要认证、认证的是什么。** 把自己的数据上传到 GitHub，需要先让服务器确认"连接的用户持有相应密钥"。提交身份回答"这次提交署名是谁"；SSH 认证回答"连接 GitHub 的用户能证明自己持有哪个密钥"——**配置姓名和邮箱不能代替认证**。

SSH 密钥是一对配合使用的密钥：

| 文件 | 用途 |
|---|---|
| `~/.ssh/id_ed25519` | 私钥：保存在自己电脑上，用来证明持有相应密钥 |
| `~/.ssh/id_ed25519.pub` | 公钥：可以添加到 GitHub 的 SSH keys 中交给服务器 |

密钥默认保存在用户目录下的 `.ssh` 文件夹中（Windows 下如 `C:\Users\你的用户名\.ssh\`）。SSH 使用一对**非对称加密**密钥进行身份认证，并建立加密连接；密钥**不是**从网卡 MAC 地址或 IP 地址提取的"设备身份证"，公钥能证明的关系与用户对私钥的控制有关。

**先检查是否已有密钥：**

```bash
ls -al ~/.ssh        # 列出 .ssh 目录内容
```

如果提示目录不存在，首次使用时很正常；如果已经有准备使用的密钥，可以复用并跳到 2.4。**不要为了跟着教程而覆盖已有私钥。**

**仅在需要新密钥时执行**（替换为自己的邮箱，邮箱只是便于识别的注释）：

```bash
ssh-keygen -t ed25519 -C "you@example.com"
```

- `-t ed25519`：指定密钥类型。旧系统不支持 Ed25519 时，官方示例是 `ssh-keygen -t rsa -b 4096 -C "you@example.com"`；两种方式择一即可，采用 RSA 时默认文件名相应为 `id_rsa`。
- 询问保存路径时：没有同名密钥才接受默认路径；**发现覆盖提示应停止并检查**。若另取文件名，后续读取和添加密钥时也要使用那个文件名。
- 询问 passphrase（私钥口令）时，为私钥设置保护口令并重复输入。终端不显示输入字符是正常现象；它与 GitHub 登录密码不是一回事。

### 2.4 添加公钥并验证连接

在 Git Bash 中启动 ssh-agent，并让它管理私钥口令：

```bash
eval "$(ssh-agent -s)"        # 启动 agent（通常输出其进程编号）
ssh-add ~/.ssh/id_ed25519     # 添加私钥（可能要求输入刚才设置的口令）
```

关闭终端后，下次会话如有需要可重新加载。Windows 也有系统自带的 OpenSSH 服务，不能假定它与 Git Bash 的 agent 互通；本教程的命令不需要修改 Windows 服务。

查看要添加到 GitHub 的**公钥**：

```bash
cat ~/.ssh/id_ed25519.pub     # 复制完整公钥这一行（含开头的密钥类型及末尾注释）
```

然后在 GitHub 中操作：

1. 点击头像，进入 **Settings**；
2. 打开 **SSH and GPG keys → New SSH key**；
3. Title 填可识别的名称，例如"个人电脑"；Key type 选择 **Authentication Key**；
4. 在 Key 中粘贴公钥内容并添加，按网页要求完成身份确认。

添加的是 `.pub` 文件内容——不是私钥内容，也不是文件路径。

**验证连接：**

```bash
ssh -T git@github.com     # 注意：这里的 git 是固定的 SSH 用户名，不能换成你的 GitHub 用户名
```

首次连接可能询问是否信任服务器：将提示中的主机密钥指纹与 GitHub 官方指纹对照，一致后再输入 `yes`。成功时会显示类似：

```text
Hi YOUR-USERNAME! You've successfully authenticated, but GitHub does not provide shell access.
```

- 这表示认证成功；后半句表示 GitHub 不提供交互式 shell，并不是认证失败；此测试成功时退出码仍可能为 `1`，应结合上述响应判断。再确认问候中的账号确实是目标账号。
- 认证成功也不代表你对任意仓库都有写权限。
- 报错排查：`Permission denied (publickey)` 检查公钥、私钥与 agent；如果连接超时，先检查网络。

配置完成后，后续上传操作即可通过密钥完成认证，不再依赖账号密码。

> 练习：创建自己的仓库 → 完成用户名/邮箱配置并检查 → 生成密钥并添加公钥 → 用 `ssh -T` 验证认证成功。

### 2.5 远程仓库别名：git remote

本地仓库要上传到云端，先得知道"传到哪里"。

**先找到仓库地址。** 打开自己的仓库页面（此时是空的），仓库地址有两种形式：**HTTPS 地址**和 **SSH 地址**。两者都可用于读、写操作，只是认证方式不同（HTTPS 需要凭据管理器或合适权限的令牌，SSH 使用已配置的密钥）；本教程统一使用 **SSH 地址**。复制时不要用页面上的复制按钮（可能有 bug、会带出多余字符），直接手动选中复制。

**为地址起别名：**

```bash
git remote add origin "仓库SSH地址"    # 给地址起别名（示例中约定叫 origin）
git remote -v                          # 查看已配置的别名与地址（fetch/push 两行）
git remote set-url origin "新地址"     # 地址写错时：修改已有别名的地址
git remote remove origin               # 删除该别名配置（不会删除 GitHub 仓库）
```

要点与易错点：

- `origin` 是当前本地仓库给远程地址起的**名称，只是惯例**，自己随便起，相当于变量名；整条命令相当于一个键值对：别名是键，地址是值。
- 地址要放进**双引号**里；每个关键字之间都要有**空格**。
- **这条命令千万别做错**，写错会直接影响后续所有上传；写错了用 `set-url` 改正或把别名删掉重新创建。
- 为什么要配别名：账户里可能有多个仓库（七八个），数据往哪传？给每个仓库配一个别名、记住对应地址，上传时指定目标别名即可。
- 地址形如 `git@github.com:用户名/仓库名.git`，不是 GitHub 的个人主页地址。
- `git remote add` 只是保存地址，不会立即上传，也不能证明地址和权限一定有效。

### 2.6 四个区域与数据流向

Git 的工作流程围绕四个区域展开，可以用"写作归档"来理解：

| 区域 | 类比 | 作用 |
|---|---|---|
| 工作区（Working Directory） | 你的书桌 | 实际修改文件的地方（写代码、改改删删） |
| 暂存区/缓冲区（Staging Area） | 待邮寄的篮子 | 确认要提交的改动先放这里，用 `git add` 放进来 |
| 本地仓库（Local Repository） | 个人保险箱 | `git commit` 把篮子的内容打包贴标签锁进箱子，成为项目历史的一部分 |
| 远程仓库（Remote） | 云端收件箱 | `git push` 把本地仓库内容发给远程服务器（GitHub 等） |

"缓冲区""缓存区"在这些操作语境中统一称为**暂存区**：它不是普通的临时缓存，而是决定下一次提交包含什么内容的区域。

```text
编辑文件          git add          git commit          git push
   ↓                 ↓                  ↓                  ↓
工作区 ───────────→ 暂存区 ───────────→ 本地仓库 ───────────→ 远程仓库
  ↑                                      ↑
  └──── merge 后更新文件 ────────────────┘

远程仓库 ── git fetch ──→ 本地远程跟踪引用（例如 origin/main）
本地远程跟踪引用 ── git merge ──→ 当前本地分支及工作区
```

配套概念：

- **本地与云端没有"谁永远更新"**：两侧可以任一方领先，也可能各自新增提交形成分叉；同步就是让两侧重新对齐，下载或上传哪个方向都可能发生。
- **分支的对应规则**：推送时以你指定的"本地分支 → 远程分支"为准（如 `git push origin main`）。远程会在需要时新建同名分支存放上传内容；但不是"同名就自动合并/替换"——普通推送通常要求**快进**，分叉时 Git 会拒绝，需要先获取并整合（详见 3.3、3.4）。

## 第 3 章 常用命令与工作流

### 3.1 暂存区操作

缓冲区（暂存区）的基础操作是四条命令：

```bash
git add file        # 资源文件/文件夹添加到缓冲区（文件或文件夹命令相同）
git rm file         # 删除文件，并把删除动作暂存（从缓冲区与磁盘一起移除）
git restore file    # 用暂存区内容还原工作区文件
git status          # 查看状态
```

行为细节与状态解读：

- `git status` 同时报告工作区与暂存区的状态：文件显示**红色**通常表示改动尚未进入缓冲区；`git add` 后变**绿色**表示已进入缓冲区。颜色只是直观提示，**不是"能否恢复"的判断依据**。
- `git rm` 会同时删除工作区文件与暂存区记录，**不经过 Windows 回收站**，直接从磁盘删除；但"删除"只影响本次的工作区和暂存区——**已提交的历史里仍保留该文件**，之后可以从历史恢复（见 3.8）。
- `git restore` 用于从暂存区还原工作区文件：例如不小心把本地文件删了、缓冲区里还有记录，可以用它还原回来。能否恢复取决于**恢复来源**：从未暂存、从未提交过的文件，Git 没有可供恢复的内容。
- 撤销、找回与忽略文件的完整场景（取消暂存、丢弃修改、从历史恢复、`.gitignore` 等）见 3.8。

### 3.2 提交：commit

```bash
git commit -m "提交说明"      # 把缓冲区数据提交到本地仓库，可回滚
```

- `-m` 后面附提交说明（中文、英文都行），要写清楚这次提交做了什么，如"修复了一个 bug""新增朋友圈功能"。
- 提交保存在**本地仓库**中（占用本地磁盘），此时还没有上传到 GitHub。
- **一次提交表达一件完整、容易解释的事**：修复一个小问题或完善一段文档都可以单独提交，不必等到"重大功能上线"；也不需要把每次按保存键都变成一个提交。提交说明会逐条形成开发日志：今天修了 bug 提交一次、明天加了功能再提交一次，开发过程被记录得清清楚楚。

**"添加时的内容"才进入提交。** 暂存记录的是 `git add` 那一刻的文件内容：如果 add 之后又修改了文件，直接 commit **不会**包含新改动，需要再次 `git add`。提交前后常用的检查命令：

```bash
git status --short     # 简要状态：?? 未跟踪；A 已暂存；M 已修改（两列分别对应暂存区与工作区）
git diff               # 工作区与暂存区的差异（还没暂存的内容）
git diff --staged      # 暂存区与上次提交的差异（即将提交的内容）
git commit -m "提交说明"
git log --oneline      # 一行一条查看历史
git show --stat HEAD   # 查看最近一次提交的文件与行数摘要
```

`git diff` 默认不展示未跟踪文件的内容，查看新文件还需结合 `git status` 和编辑器。完整差异通常用 `+` 标记新增、`-` 标记删除；不要只依赖颜色，终端主题可能不同。

### 3.3 推送：push

先创建目标仓库（若尚未创建）：在 GitHub 新建仓库页面，所有者选择自己的账号，填写仓库名；个人练习可以选 Private，需要公开展示选 Public；**本次不要勾选初始化 README、.gitignore 或 LICENSE**，让远程仓库保持空白（本地已有自己的提交，空白仓库可避免两边历史对不上）。创建后在快速设置区域选择 **SSH**，复制仓库地址（配合 2.5 的 `git remote add` 使用）。若远程仓库已经带有 README 或其他提交，不要按本节"空白仓库 + 本地已有提交"的流程硬推，应先克隆仓库、再把文件加进去提交（见 3.4）。

```bash
git remote add origin "仓库SSH地址"    # 首次：先配别名（见 2.5）
git branch --show-current              # 确认当前在哪个分支
git push -u origin main                # 把本地主分支数据推送到 origin 指向的云端仓库
git branch -vv                         # 查看分支与上游关系
```

- 解释：`origin` 里存的是云端仓库地址，`main` 是要推送的本地分支名（**按仓库实际分支名，有的旧仓库仍叫 master**）；整句就是把本地主分支数据推到 origin 指向的云端仓库，需要网络。
- `-u` 在首次推送时为本地分支设置**上游关系**（upstream，即默认关联的远程分支）；设置成功后 `git branch -vv` 会显示 `main` 对应 `[origin/main]`，之后可以直接使用 `git push`。
- **上传三步走**：`git add`（进缓冲区）→ `git commit -m`（进本地仓库）→ `git push`（推送到云端）。
- **前提与排查**：三条命令能否成功完全依赖两项配置——**SSH 认证**与**仓库别名**，任何一项有问题都会上传失败；push 报错时先检查这两处。
- `push` 不会把工作区里未暂存、未提交的改动自动上传：它传输的是已提交的内容并请求更新远程引用——不是把整个目录当网盘同步。
- 命令行支持历史命令（上下箭头调出），重复上传时不必重新敲。

**为什么 push 不等于自动合并。** 对于普通分支，推送通常要求远程原有提交已经包含在你要推送的历史中，即可以**快进**。若其他人先推送了你没有的提交，Git 会拒绝覆盖那段历史：

```text
可以快进：        A──B          远程在 A，本地在 B，远程可前进到 B

已经分叉：          B           本地
                  /
                 A
                  \
                   C           远程；需要先整合 B 与 C
```

此时不要认为"分支同名就会自动合并"，更不要用强制推送覆盖；正确做法是先获取并整合远程修改（见 3.4）。

> 操作流程示例：用 vi 创建 `first.c` → `git status`（红色）→ `git add`（变绿）→ `git commit -m "首次提交"` → `git push` → 刷新云端仓库确认：文件与提交历史出现在远程对应分支上（默认分支名由仓库设置决定，如 main 或 master），页面上可看到分支列表与提交记录。

### 3.4 下载与同步

**先区分"推拉仓库"与"下载文件"。**

- `push`（推）和 `pull`（拉）以**仓库**为单位，是开发者/协作者的行为：想给某个项目提交改动，需要先获得相应权限（或被接受贡献的渠道），才能把仓库拉下来参与开发。
- **下载开源项目**：可以只取文件，也可以克隆整个仓库，方式见下表。

| 操作 | 得到什么 | 适合什么情况 |
|---|---|---|
| Code → Download ZIP | 所选版本的文件快照，通常不包含 `.git` 历史 | 只想查看某一版本的文件 |
| `git clone "地址"` | 完整的本地仓库：含可获取的历史，检出分支，并自动配置好 `origin` 与上游关系 | 第一次把已有仓库拿到本地并继续维护 |
| `git fetch` | 获取远程对象，更新相应的远程跟踪引用 | 已有本地仓库，先了解远程变化 |
| `git pull --ff-only` | 获取远程变化，并在能够快进时更新当前分支 | 已有本地仓库，安全地跟上远程进度 |

- **clone 不止是"下载文件"**：它建立 Git 仓库（含历史），因此**无需**再次 `git init` 或 `git remote add origin`。网页 Download ZIP 解压后不会自动拥有原仓库的版本历史；网页下载还可能遇到 404 或速度慢（网页服务器与资源服务器不是同一台，梯子对下载资源帮助有限），可以换网络或改用命令 clone 重试——clone 速度与网络状况有关，有时不挂代理反而更快。建议先找一个小项目练习。
- clone 地址用 **HTTPS 地址**（Code 弹窗里可复制）或 **SSH 地址**都行：公开仓库的 HTTPS 读取通常无需认证；SSH 则使用已配置的密钥。

**HTTPS 与 SSH 都能用于 Git 传输**（重要澄清）：

| 地址形式 | 示例 | 认证说明 |
|---|---|---|
| HTTPS | `https://github.com/用户名/仓库名.git` | 公开仓库读取通常无需认证；私有读取或写入需要相应认证（凭据管理器或合适权限的令牌，令牌不要写进仓库文件） |
| SSH | `git@github.com:用户名/仓库名.git` | 使用已配置的 SSH 密钥进行账号认证；访问私有仓库或写入仍受权限限制 |

HTTPS 不是"只能下载"，SSH 也不是"只能上传"——两者都可用于读写操作，差别主要在认证方式。本文继续使用已经配置好的 SSH。

**远程领先时：先 fetch，后快进更新。**

```bash
git status                          # 确认工作区干净（有未提交修改时先按 3.8 处理）
git fetch origin                    # 获取远程最新状态
git status                          # 显示本地落后于 origin/main 时可继续
git log --oneline main..origin/main # 查看远程有、本地没有的提交
git diff main origin/main           # 查看两版文件差异
git pull --ff-only origin main      # 快进更新当前分支（不创建合并提交）
git status
```

- `origin/main` 是本地记录的"上次获知的远程 main 状态"，并不是随时联网更新的实时视图——fetch 之后它才更新。
- fetch 只更新远程跟踪信息，**不会改你的工作区文件**；pull 才会更新当前分支和工作区。
- `--ff-only` 只在不需要创建合并提交时前进分支；双方各有新提交时它会拒绝整合，不会替你决定合并方式。

**双方都有提交：处理推送被拒（non-fast-forward）。** 直接 `git push` 被拒绝（提示 `rejected`、`fetch first` 或 `non-fast-forward`）时，这不是认证突然失效，而是远程有本地尚未包含的提交：

```bash
git status                                     # 确认工作区干净
git fetch origin                               # 获取远程历史
git log --oneline --graph --all --decorate     # 观察分叉情形
git merge -m "合并远程修改" origin/main        # 把远程跟踪分支的历史整合进当前分支
git push origin main                           # 整合后重新推送
```

两侧修改的是不同文件时通常可以自动合并；如出现内容冲突，按 3.6 的方法解决后再推送。**不要用强制推送绕过这类拒绝**——先保留并整合双方的历史。

**其他常用命令：**

```bash
git pull        # 拉取远程更新并自动合并（相当于 fetch + merge；建议用 --ff-only 更安全）
git fetch       # 只下载远程更新，不自动合并
git merge       # 手动把远程内容合并进本地代码
git stash       # 贮藏：改动写了一半不想提交，先"藏进抽屉"，忙完用 stash pop 取回
```

**把删除操作同步到云端。** 本地删了、云端不会自动删。完整流程：

1. 先删掉本地文件；
2. `git rm` 把缓冲区里的数据删掉；
3. `git commit` 提交这次"删除操作"；
4. `git push` 推到云端——云端的文件也随之删除。

**日常同步习惯。** 每天开始修改前，先查看状态、确认在工作分支且工作区干净，再拉取：

```bash
git status
git branch --show-current
git pull --ff-only origin main
```

随后编辑文件、查看差异、暂存、提交，最后推送。注意：`git status` 显示干净，只说明本地当前没有待提交变化；没有新执行 fetch/pull 时，不能仅凭它认定服务器没有新提交。遇到"本地修改会被覆盖"的提示时，先整理并提交需要保留的修改（或备份到仓库外），再拉取，不要为了拉取成功而丢弃内容。

### 3.5 分支操作

分支的价值在于多人协作与并行开发；日常上传默认只涉及主分支（按实际分支名），需要独立开发新功能时再开分支。

```bash
git branch <分支名>          # 创建分支
git branch                   # 查看分支（当前分支前带 * 号）
git switch <分支名>          # 切换分支（Git 2.23+ 推荐；旧写法 git checkout <分支名>）
git switch -c <分支名>       # 创建并切换分支（旧写法 git checkout -b <分支名>）
git branch -d <分支名>       # 删除已合并的分支（未合并时会提示，先检查历史确认，不建议直接 -D 强制删除）
git merge <分支名>           # 合并分支：把目标分支的历史整合进当前分支（先切回主分支再执行）
git rebase <分支名>          # 变基：把当前分支的提交"重新播放"到目标分支最新提交之上，抹平分叉
```

**分支很轻量**：创建分支通常不会把整个项目复制成另一个目录，只是在历史中多一个可移动的引用；在同一工作区切换分支时，你看到的文件会随版本变化。分支名是名称不是文件名，如果分支已经存在，使用 `git switch 分支名` 切换，不要重复创建。

**典型流程：新建分支 → 修改并提交 → 合回主分支。**

```bash
git switch main              # 确认回到主分支、工作区干净（有自己的未提交改动先整理）
git switch -c feature-notes  # 创建并切换到功能分支
（在分支上编辑文件并提交）
git switch main              # 切回主分支，观察文件
git merge -m "合并功能分支" feature-notes   # 合并
git branch -d feature-notes  # 删除已合并的本地分支名
git push origin main
```

合并的两种情况：

- **快进（Fast-forward）**：主分支没有独立前进时，分支指针直接前移，**不会额外产生合并提交**（`-m` 的说明也就没有用到）。
- **合并提交**：两边都有新提交时，Git 会创建一个新的**合并提交**（有两个父提交）；`-m` 为它提供说明，避免进入编辑器。

删除分支名不会把已经合入主分支的文件删掉，也不会删除远程同名分支；本文没有推送过功能分支时，只需要处理本地名称。若 `-d` 提示尚未合并，先检查历史，不要直接改为强制删除。

### 3.6 合并冲突处理

同一基础版本的内容被两侧改成不同结果时，Git 无法替你选择，会报告 `CONFLICT` 并停下来等待解决。冲突文件中的标记形如：

```text
<<<<<<< HEAD
color=green
=======
color=red
>>>>>>> feature-color
```

- `HEAD` 一侧是当前分支的内容，另一侧来自正在合入的分支；标记行只是"待解决范围"的示意，**不是应该保留的配置**。使用不同冲突显示配置时，文件也可能包含共同祖先信息。
- 解决流程（三步）：

```bash
git status                    # 查看冲突文件列表（unmerged paths）
（在编辑器中打开每个冲突文件，检查每个冲突块，删除标记行，写入最终内容）
git add <解决后的文件>        # 标记该文件已解决
git commit -m "解决冲突"      # 完成这次合并
git log --oneline --graph --all --decorate   # 查看合并结果
```

- 解决结果不一定"二选一"：也可以写出兼顾双方需求的新内容。
- 冲突文件较多时，可用 `git diff --name-only --diff-filter=U` 列出尚未解决的路径，逐一处理；全部确认后再提交。
- 标记消失并不保证业务含义正确——还需根据项目实际检查程序或文档是否正确。
- **中止合并**（条件路线）：如果暂时不想解决，且尚未提交合并结果，可以退回合并前的状态：

```bash
git merge --abort      # 中止本次合并；功能分支上的提交仍在
```

中止不是删除分支，也不是撤销已经完成的合并提交；如果合并前工作区就带着未提交改动，Git 不一定能完整重建原状态——养成合并前先检查干净的习惯。

### 3.7 版本历史与回溯

```bash
git log        # 查看提交历史记录
git log --oneline          # 一行一条，快速浏览
git log -1                 # 只显示最近一次提交
git show --stat HEAD       # 最近一次提交的文件与行数摘要
```

- **差异对比**：提交记录中**红色**表示删除的代码、**绿色**表示新增的代码、**白色**表示未改动部分；每条提交有对应的提交地址（哈希值），在提交列表里永远能找到想要的版本。
- **版本回溯**：修改 `first.c`（删旧代码、加新代码）→ 再走一遍 add、commit（说明写"修改提交"）、push → 提交列表变成两条，点开每条即可看到删了什么、加了什么。删掉的代码永远找得到，再也不用担心"改坏了回不去"。
- **实时备份**：提交相当于对代码做备份，且可以保留无数个版本——但要注意：**提交保存在本地仓库、占用本地磁盘**；"云端也有备份"是 `push` 之后的事。可以随时回滚到某个版本。
- **不用再堆"屎山"**：传统开发中不敢删旧代码、只能注释保留，迭代久了代码结构混乱（业内称"屎山代码"）；有了提交功能，旧版本随时可取，代码里不需要保留历史包袱——保持详细提交的好习惯即可。

### 3.8 撤销、删除与忽略文件

先分清自己想撤销哪一步。恢复类命令会**覆盖内容**，没有通用"撤销按钮"：执行前先看 `git diff`，只对确认可以丢弃的改动操作；本文这些恢复示例都建立在**已有至少一次提交**的仓库中。

| 目的 | 命令形式 | 对工作区文件的影响 |
|---|---|---|
| 取消暂存，保留自己写的内容 | `git restore --staged -- 文件` | 文件内容保留；暂存区恢复为 HEAD 中对应状态 |
| 放弃尚未暂存的修改 | `git restore -- 文件` | 用暂存区内容覆盖工作区对应文件 |
| 从上一次提交恢复工作区文件 | `git restore --source=HEAD -- 文件` | 用 HEAD 内容覆盖工作区；不改暂存区 |
| 删除文件，并把删除暂存 | `git rm -- 文件` | 工作区文件被删除，删除动作进入暂存区 |
| 停止跟踪，保留本地文件 | `git rm --cached -- 文件` | 文件保留在本地，暂存"从版本中移除"的操作 |

`--` 用来结束选项，让后面的值按文件路径处理。**能否恢复取决于恢复来源**：已经提交的历史、暂存的内容、从未记录的文件，能恢复的依据并不相同——从未暂存、从未提交的文件，Git 通常没有可供恢复的内容。

**取消暂存，但保留编辑内容：**

```bash
git add learning.txt
git restore --staged -- learning.txt   # 取消暂存：该行仍在文件里，只是回到"未暂存"状态
git diff                               # 能看到保留的修改
```

现在如果想丢弃未暂存的修改（确认不再需要时）：

```bash
git restore -- learning.txt   # 用暂存区内容覆盖工作区，临时修改消失
```

如果你想保留这行，应该重新暂存并提交，而不是执行这一步。

**误删已跟踪文件（暂存区还有记录时）：**

```bash
rm learning.txt                # 普通删除：文件从磁盘移除，但删除动作未暂存
git status --short             # 看到文件被删除的标记
git restore -- learning.txt    # 从暂存区还原
```

普通 `rm` 通常不经过 Windows 回收站，不要拿自己的重要文件来试。

**正式删除后，从提交中找回：**

```bash
git rm -- obsolete.txt            # 删除并暂存删除
git commit -m "删除练习文件"      # 提交删除（HEAD 中仍有它）
git restore --source=HEAD~1 -- obsolete.txt   # 从上一个提交找回文件
git add obsolete.txt              # 找回后先以未跟踪状态回到工作区，重新暂存提交
git commit -m "从历史恢复练习文件"
```

`HEAD~1` 表示当前提交的第一个父提交（恰好是删除前的那次提交）。真实项目中应先用 `git log --oneline -- 文件名` 找到正确版本，再使用相应提交编号作为 `--source`。**删除文件不会自动抹去历史提交中已有的内容。**

**用 .gitignore 排除不应跟踪的文件。** 在仓库根目录新建 `.gitignore` 文件，每行一条规则：

```text
# Local-only files
.env
local-settings.txt
build/
*.log
```

| 规则 | 含义 |
|---|---|
| `.env` | 忽略名为 .env 的本地配置文件 |
| `local-settings.txt` | 忽略本地个人设置 |
| `build/` | 忽略匹配的构建输出目录 |
| `*.log` | 忽略日志文件 |

```bash
git status --short                 # 被忽略的文件不再出现
git check-ignore -v build/output.txt practice.log   # 查看命中了哪个文件的哪条规则
git add .gitignore                 # 忽略规则文件本身要提交
git commit -m "添加忽略规则"
```

- `.gitignore` 一般应作为项目规则提交。它主要影响**未跟踪文件**：不会自动停止跟踪已经提交的文件，也不会删除旧提交中的数据。
- **已跟踪文件如何"退出后续版本"（停止跟踪）：** 用 `git rm --cached` 把它从版本中移除、文件保留在本地，再提交；配合忽略规则后，状态里也不再提示它：

```bash
git rm --cached -- local-settings.txt   # 停止跟踪（文件保留在本地）
git commit -m "停止跟踪个人设置"
git ls-files -- local-settings.txt      # 不再列出该文件
```

- 如果误提交的是真实密钥或密码：单纯添加忽略规则或 `rm --cached` 并不能补救已泄露的凭据——应先让凭据失效，再按项目流程处理历史。
- Git 通常不跟踪空目录：需要目录出现在版本中时，应在其中放入有实际用途的文件。

## 第 4 章 Markdown 语法

Markdown 是一种**文本修饰语言**：通过特殊符号（修饰符）让正文呈现各种样式，文件后缀统一为 `.md`。可以用任意纯文本编辑器编写，不依赖特定收费编辑器；GitHub 在基础语法之上还支持表格、任务列表等扩展。

### 4.1 标题

```markdown
# 一级标题        （井号数量决定级别，一级字体最大）
## 二级标题
### 三级标题      （最多支持到六级）
```

- 修饰符与标题内容之间**必须有空格**。
- 标题层级表达文档结构，不应只为追求字体大小而跳级；一篇文档通常使用一个一级标题，主要章节用二级标题。
- 不想让符号生效时，用反斜杠 `\` 转义。

### 4.2 正文与换行

- 正文直接编写；**空一行表示新段落**。
- 在 GitHub 的 `.md` 文档中，仅在源码里按一次 Enter，通常不会强制产生可见换行。同一段内换行有三种方式：
  1. 行尾加两个空格；
  2. 行尾加反斜杠 `\`；
  3. 使用换行标签 `<br>`（部分编译器不写标签不会换行）。

```markdown
第一行末尾有反斜杠。\
这是紧接着的第二行。

第一行<br>
第二行
```

> 注意：GitHub 的评论输入框和 `.md` 文件对普通换行的处理可能不同，应在实际发布位置预览。

### 4.3 文本修饰

```markdown
*斜体*           一对星号
**粗体**         两对星号
***粗斜体***     三对星号
~~删除线~~       两对波浪号
`行内代码`       前后各一个反引号（凸显/灰底高亮效果）
---              分隔线（一组减号，渲染为一条分隔两段内容的线）
```

- 强调标记应**紧贴内容**，写成 `**重点**`，不要写成 `** 重点 **`。
- 行内代码适合文件名、参数和短命令。若正文要显示含反引号的文字，可用更长的反引号包裹，例如 `` `git status` ``。
- 分隔线可以独占一行写成 `---` 或 `***`，前后留空行。

### 4.4 列表

```markdown
* 无序列表项           星号 + 空格 + 文本
1. 有序列表项          数字点 + 空格 + 文本
- [x] 已完成的任务     任务列表：短横线 + [x] / [ ]
- [ ] 待办任务
```

- **多级列表**：在上一级项目下缩进后（或把光标放在上一级文字上再输入）继续书写，渲染效果一级为实心圆点、二级为空心圆、三级为方块。
- 有序列表适合做目录（一级 `1.`、二级 `1.1`、`1.2`……）；**有序与无序可以混用**（如一级有序、二级无序）。
- **注意**：无论是星号还是数字点，**后面必须加空格**，没有空格就没有效果。
- 任务列表（`- [x]` / `- [ ]`）是 GitHub 支持的扩展语法，常用于记录进度。

### 4.5 引用

```markdown
> 一级引用         大于号 + 空格 + 文本
>> 二级引用        大于号数量越多，引用级别越高
```

用途：引用一段话并标注出处（如出自某本书第几章、某篇帖子）。

### 4.6 超链接与图片

**超链接：**

```markdown
[链接标题](地址)
[链接标题](地址 "悬停标题")
```

示例：`[点击访问百度](https://www.baidu.com)`，编译后是可点击的蓝色链接；在地址后加空格和双引号可设置**悬停标题**（鼠标放上去显示的提示文字）。方括号、圆括号都使用**英文半角**。

**图片：**

```markdown
![图片标题](图片地址 "悬停标题")
```

与超链接相比只在最前面多一个英文叹号 `!`；方括号里是图片的替代文本，后面的可选引号内容是悬停提示。

**图片地址分两种：**

- **网络图片**：URL 地址（http/https 前缀）——任何人都能访问；
- **本地图片**：磁盘地址（C 盘、D 盘……）——这类**本机绝对路径**（如 `C:\Users\某人\Desktop\图片.png`）在网页上会显示不出来（一个叉）：别人打开网页时不可能到你本地磁盘去加载图片。

> **关键结论**：文档要传到 GitHub 给别人看时，图片要放在对方能访问的位置。除了网络图片（可由"图床"托管：图片托管网站上传后会生成 URL），**更常用的做法是把图片放进仓库里，用相对路径引用**。

**仓库内的相对路径图片（不必上传图床）。** 例如 README 在仓库根目录，图片放在同一仓库的 `images/practice.png`，就可以写：

```markdown
![练习截图](images/practice.png "练习结果")
```

相对路径以当前 Markdown 文件位置为基准，文件名大小写应一致；图片文件本身也需要提交并推送，别人浏览或克隆时才加载得到。公开可访问的网络图片 URL 也可以使用，但能否显示取决于该地址是否持续可用、是否要求登录等。

### 4.7 表格

```markdown
| 表头 | 表头 | 表头 |
| :--- | :---: | ---: |
| 居左 | 居中 | 居右 |
```

- 结构：第一行写表头（决定列数），第二行写分隔与对齐方式，第三行起写数据。
- 分隔单元格**至少写三个 `-`**：`:---` 居左、`:---:` 居中、`---:` 居右；列之间用 `|` 分隔，表格前后留空行。
- 单元格里要显示竖线时通常写 `\|`，避免它被当成新的一列。
- 常见问题：表格可能因空行/格式问题不生效，调整后即正常显示；表格适合比较命令与短信息，不适合塞入很长的多段正文。

### 4.8 代码片段

````markdown
```c
// 头部三个反引号 + 语言名（c、cpp、python、java、bash……）
int main(void) { return 0; }
```
````

- 结构：头部三个反引号紧跟语言名 → 中间写代码 → 尾部三个反引号结束，两者需要**配对**。
- 语言名用于让渲染器做**语法高亮识别**（不会执行代码，也不会决定固定的背景色）；具体外观与配色由渲染平台和主题决定，不同平台可能不同。
- 也可插入终端命令块；技术分享文章中的代码块、命令块都用它。若代码内容自身含有三反引号，可以用四反引号作为外层围栏。

### 4.9 转义与常见渲染问题

- **转义**：符号不想被解析时加反斜杠 `\`（如 `\#` 显示为普通井号、`\*` 显示为普通星号）。
- **空格**：修饰符与内容之间必须有空格，否则不生效；强调标记则要**紧贴内容**。
- **空行与编辑器差异**：表格、代码块等对空行敏感，不同编辑器/平台渲染效果可能不同。
- **上传验证**：把写好的示例文档保存为 `readme.md`，走一遍 add → commit → push；刷新云端仓库可见文档内容、表格、代码片段正常显示；网络图片能加载，本机磁盘路径的图片加载不出来（再次印证 4.6 的结论）。

### 4.10 综合示例：一份完整 README

README 的特殊之处是**默认显示在仓库页面上**，是别人了解你项目的第一入口：把"是什么、怎么装、怎么用"讲清楚。下面是一份综合了常用语法的示例：

````markdown
# 项目名称

一句话说明项目用途。

## 功能特性

- 功能一：……
- 功能二：……

## 环境要求

- Windows / Linux
- 所需语言与工具版本

## 安装与运行

```bash
git clone https://github.com/用户名/仓库名.git
cd 仓库名
# 安装依赖、运行项目的命令
```

## 使用方法

简要说明典型操作步骤。

## 文件说明

| 文件 | 用途 |
| --- | --- |
| main.c | 主程序 |
| docs/ | 说明文档 |

## 进度记录

- [x] 已完成：核心功能
- [ ] 待完成：说明文档

> 每次提交前先检查差异，提交后再确认仓库状态。
````

按此结构写 README，配好相对路径的图片与链接，别人基本无需额外提问。

## 第 5 章 实践与扩展

### 5.1 用 GitHub 提交与共享代码

- 阶段性代码成果建议存到自己的仓库里，把**仓库链接**分享出去——对方用浏览器（手机也行）直接查看。
- 分享方法：复制浏览器地址栏中的仓库网页链接发出即可（也可点绿色 Code 按钮复制 HTTPS 地址）。
- 不建议发压缩包：手机上解压、查看都不方便。

### 5.2 开源项目使用规范

- 下载的是**源码**：需本地编译环境自行编译使用，注意语言与运行环境是否匹配。
- 遵守**许可证**条款（识别要点见 1.5）：商用、盈利场景需先确认授权。
- 灰产内容（外挂、抢票、秒杀等）可以研究学习，**不可售卖、传播、盈利**。
- 引用他人代码/项目写进自己的作品时，留意来源与授权，避免法务风险。

### 5.3 扩展：GitLab 与企业协作

GitLab 是另一款主流代码托管平台，与 GitHub 定位类似，但更常用于企业内网部署与团队协作。团队开发中常见做法：

- **用户与群组**：管理员创建用户、建立群组（项目按组管理），成员按角色分配权限。
- **Fork 与 Merge Request（MR）**：开发者把项目 Fork 到自己的空间开发，完成后提交 MR 请求合并；由维护者进行 **Code Review**（代码审查）后合入主仓库。
- **企业分支模型（GitFlow）**：用不同分支各司其职——

| 分支 | 作用 |
|---|---|
| master | 主分支，存放稳定可发布的版本 |
| develop | 开发分支，日常集成开发成果 |
| feature | 功能分支，每个新功能从 develop 开出、完成后合回 develop |
| release | 预发布分支，测试与发布准备 |
| hotfix | 紧急修复分支，线上 bug 从 master 开出、修复后合回 master 与 develop |

- **冲突处理**：多人修改同一文件不同区域一般可自动合并；修改同一区域会产生冲突（conflict），需要手动决定保留哪一版后提交。
- **CI/CD**：GitLab 内置持续集成/持续交付能力，代码提交后自动构建、测试、部署（由流水线配置驱动）。

### 5.4 常见问题排查

**看报错先定位失败阶段**，再针对性处理；不要一看到失败就从头重新初始化仓库或重新生成密钥。常见失败阶段：终端与目录、配置与提交、连接与认证、仓库权限、历史整合。

| 提示或现象 | 常见原因 | 检查与处理 |
|---|---|---|
| 找不到 `git` / `command not found` | 未安装、终端未重新打开或环境路径不正确 | 打开 Git Bash，运行 `git --version`；必要时检查安装 |
| `not a git repository` | 不在仓库中，或该目录没有 Git 管理信息 | 用 `pwd` 确认位置，切入正确目录；不要在不确定的目录随意 init |
| `Author identity unknown` | 没有有效的提交署名配置 | 检查 `user.name`、`user.email` 及其配置来源 |
| `nothing to commit` | 没有已暂存的新变化，也可能选错目录或文件被忽略 | 结合 `status`、`diff`、`diff --staged`、`check-ignore` 判断 |
| `remote origin already exists` | 已经配置过 origin，clone 后也会如此 | 用 `remote -v` 查看，地址错误时 `remote set-url origin 地址` |
| `src refspec main does not match any` | 尚无首次提交，或没有名为 main 的分支 | 查看 `git log --oneline` 和 `git branch --show-current`，按实际分支处理 |
| 没有 upstream / tracking information | 当前分支未设置上游 | 初次推送实际分支时使用 `git push -u origin 分支名` |
| `Permission denied (publickey)` | SSH 没用上对应私钥，或账号没添加对应公钥 | 检查公钥添加情况、`ssh-add -l` 及 `ssh -T git@github.com` |
| `Repository not found` | 地址错误、仓库不存在或当前账号无权限 | 检查所有者与仓库名、登录账号及私有仓库授权，不能仅判断为仓库不存在 |
| `403` 或写入权限被拒绝 | 凭据、账号或仓库规则不允许写入 | 核对推送地址、使用的账号与权限；组织仓库还可能有规则限制 |
| `Connection timed out`、无法解析主机 | 网络、DNS、代理或端口连通性问题 | 区分域名解析与端口连接问题；SSH 超时不靠重新填邮箱解决 |
| `rejected` / `non-fast-forward` | 远程已有本地未包含的历史 | 按 3.4 节 fetch、检查、merge 后再推送 |
| `Not possible to fast-forward` | 双方历史分叉，不能仅移动当前分支指针 | 检查历史后采用明确的整合方式（如 merge） |
| `local changes ... would be overwritten` | 未提交修改可能被拉取、合并或切换覆盖 | 先整理并提交需要保留的改动，或另外备份后再处理 |
| `refusing to merge unrelated histories` | 两边通常分别独立初始化，没有共同历史 | 初学练习优先克隆已有远程，再复制自己的文件并提交；保留原目录，不用强制推送掩盖问题 |
| `CONFLICT` / `unmerged paths` | 合并尚待人工解决 | 查看冲突文件，编辑结果，add 后 commit（见 3.6）；或在未完成时 abort |
| LF / CRLF 换行警告 | Windows 与其他环境的行尾表示不同 | 警告本身不一定表示提交失败；结合结果检查，项目已有行尾规则时遵守规则 |

**分页器与编辑器怎样退出：**

| 当前界面 | 操作 |
|---|---|
| `git log` / `git diff` 的分页器 | 按 `q` 返回命令行 |
| Vim 编辑器，准备保存并退出 | 先按 Esc，再输入 `:wq` 并回车；也可按大写 `ZZ` |
| Vim 编辑器，想让当前编辑任务以失败退出 | 先按 Esc，再输入 `:cq` 并回车；随后用 `git status` 检查 Git 状态 |
| Nano 编辑器 | Ctrl+O 保存，按提示确认文件名，再 Ctrl+X 退出 |

Vim 的 `:q!` 是放弃本次编辑，不应一概理解为"取消 Git 操作"；提交使用 `-m` 时通常不需要进入提交说明编辑器。

**按阶段检查自己的结果：**

| 刚完成的操作 | 检查命令或位置 | 应关注什么 |
|---|---|---|
| 编辑文件 | `git status`、`git diff` | 改的是不是预期文件，有无意外删除 |
| 暂存 | `git diff --staged` | 下一次提交将包含哪些内容 |
| 提交 | `git log -1`、`git status` | 提交说明是否正确，有无遗漏修改 |
| 推送 | GitHub 网页和提交历史 | 目标仓库、分支、文件内容是否正确 |
| 获取远程 | `git log --oneline main..origin/main` | 远程有哪些自己尚未整合的提交 |
| 解决冲突 | `git status`、文件内容和项目检查 | 有无未解决路径，最终内容是否符合预期 |

**几条实用提醒：**

- **push 失败**：先检查两项配置——SSH 认证（公钥是否已添加、`ssh -T` 是否通过）与仓库别名（`git remote add` / `set-url` 是否正确）；复制地址时不要用页面复制按钮，手动选中复制。
- **认证失败**：先用 `ssh -T git@github.com` 验证；检查公钥是否粘贴完整、agent 是否加载了对应私钥（`ssh-add -l`），确认无效后再考虑重新生成。
- **误删文件**：暂存区还有记录时用 `git restore` 还原；已提交过删除的可从历史找回（见 3.8）；从未暂存、从未提交的文件无法恢复。
- **云端文件删不掉**：删除需要手动同步（删本地 → `git rm` → commit → push）。
- **clone/下载缓慢或 404**：与网络环境有关，可换网络或改用命令 clone 重试。
- **Git Bash 不能替代 Linux 环境**：Git 终端能在 Windows 下使用部分 Linux 命令，但命令、工具、开发库不全（例如没有 GCC，无法编译），后续开发仍要用真正的 Linux 系统。

### 5.5 综合练习与自测

**综合练习：在任意练习仓库中完整走一遍流程。**

1. 拉取最新：确认工作区干净后执行 `git pull --ff-only origin main`；
2. 新建并切换到功能分支（如 `git switch -c feature-review`）；
3. 新增一个文件（如 `review.md`），写上本章最容易混淆的三个知识点；
4. 查看未暂存差异 → 暂存 → 查看暂存差异 → 提交（说明写"添加复习笔记"）；
5. 切回主分支，合并功能分支，删除已合并的本地分支；
6. 推送并在 GitHub 上验证文件与提交历史；
7. 选做：制造一次内容冲突并按 3.6 解决；再演示一次"取消暂存但保留内容"。

**自测题：**

| 问题 | 参考答案 |
|---|---|
| `git add` 后又改了一行，直接 commit 会包含那行吗？ | 不会；需要再次暂存该修改 |
| 不联网可以提交吗？ | 可以。本地提交与联网推送是不同步骤 |
| `fetch` 成功后为什么文件没有变化？ | 它只更新远程跟踪信息，尚未整合进当前分支和工作区 |
| 设置了 `user.email`，为什么仍无法推送？ | 提交邮箱不是认证凭据，还需检查认证（SSH）、仓库权限和历史状态 |
| 文件加入 `.gitignore` 后，历史中的秘密消失了吗？ | 没有；忽略规则不会清理既有历史 |
