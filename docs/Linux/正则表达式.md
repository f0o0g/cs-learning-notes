# Linux 正则表达式：语法、grep 与 C 正则库

> 本文档整理正则表达式的基础知识、grep 命令用法与 C 语言正则库编程，按知识主线组织编写，持续补充。

## 第 1 章 正则表达式基础

### 1.1 什么是正则表达式

正则（Regex）是经典的数据处理技术：通过**贪心算法**对数据进行快速的过滤匹配（模式匹配），查询符合**数据规则**的数据，最常用的场景是**模糊查询**。

- 对比数据库：数据库里查数据常用 like 之类的语法；要在文本当中筛选某个数据片段，就要用正则这类技术。
- 对比框架和语言：很多语言和技术都内置或支持正则，用法大同小异。

用"查姓名"解释模糊与精确的区别：精确查询只能找到"张三"；模糊查询先给出一个"张"字，凡是以"张"开头的数据都能列出来。区别的核心在于**数据规则**——使用正则时要先把规则列出来，规则就像"数据的法律"，符合规则的数据都会被列出来。

顺着这个思路，正则不仅能查，还能做**数据格式校验**：注册账号时校验邮箱是否合法、密码是否满足"8~15 位、含数字、含大小写"、手机号是否 11 位数字等；也能做**批量查找与替换**。也就是说，正则的能力覆盖"查询数据、格式校验、批量处理"三类任务。

### 1.2 与其他查找方式的区别

传统的字符串处理函数（如 `strstr`、`strcmp` 这类）提供的是简单的字符处理能力，查找单元以**字符**为单位：查找"张三"时逐个字符一一比较——先看是不是"张"，是就先标记，再看后面是不是"三"，不是就继续比较。这种方式有两个短板：

- **效率低**：逐字符偏移比较，数据多时开销明显；
- **不支持模糊查询**：只能查找特定数据、指定字段，无法按规则匹配一类数据。

正则的查询方式是"按数据规则持续向后匹配"，因此效率高，且支持模糊查询。

### 1.3 匹配过程：数据源与模式空间

正则的匹配过程有三个关键要素：

1. **正则语句**：确定数据规则，由一系列表达式构成，本质是一个字符串——要查什么，先把规则写出来。
2. **数据源**：要查找的数据来源，可以是数据库、文件（文本数据）等任何类型。
3. **模式空间（模式缓冲区）**：使用正则时，数据会先拷贝到缓冲区缓存；匹配不是直接拿表达式对着文件做的。

基本流程：从数据源把数据拷贝进模式空间——**默认按行拷贝**（如 1000 行数据，一次拷贝一行）→ 用正则语句对这一行做模式匹配 → 结果两种：

```
        数据源                 模式空间
    ┌──────────┐          ┌──────────┐
    │ 逐行读入  │ ───────→ │   line   │
    └──────────┘          └────┬─────┘
                               ↓
                     匹配：正则语句（表达式）描述数据规则
                               ↓
                 ┌─────────────┴─────────────┐
                 ↓                           ↓
               合适                        不合适
                 ↓                           ↓
             输出数据                  忽略，取下一行
```

- **符合要求**（合法）就输出，一般会高亮标记，表示找到一条；
- **不符合**就忽略这一行，取下一行继续匹配。

可以类比警匪片里"指认嫌疑人"：正则语句就是嫌疑人的体貌特征，模式空间里的每行数据都是待指认对象，拿特征去指认——成功就留下，失败就忽略。

### 1.4 贪心算法：不可回溯与局部最优

正则查找效率高的原因是它使用**贪心算法**，而贪心算法有两个典型问题：

**问题一：不可回溯性。** 匹配过程中出现异常，无法回溯处理异常，只能持续向后——即使某个结果明显找错了，也不能回头修正。就像司机闯卡没有交费，只能说"下回注意"，不能回头补。这意味着正则查过的数据准确度存疑：速度虽然快，但贪多嚼不烂，出错无法修正。

**问题二：局部最优解不一定是全局最优解。** 贪心算法的思想是"通过每一步局部最优得到全局最优"，但局部都最优，合起来不一定全局最优：

- **找零钱**：找给客户 35 元、希望张数最少——第一次取不超过 35 的最大面值 20 元，剩 15；再取 10 元，剩 5；最后取 5 元。20 + 10 + 5 = 35，每一步都选"当前余额内的最大面值"。在当前面值体系下这个结果是合理的。
- **背包问题**：背包假设能装下一定重量，可选物品按"能装就装"的局部最优去放：先放最大的、再放下一个，结果很快就放不下了。比如先放 6kg、再放 3kg，共 9kg 就装不进其他了；但如果目的是"把背包装满"（全局最优），应该是 6 + 2 + 2 = 10kg。单看每一步，放 6 是最优、放 3 也是最优，最终结果却不最优。

结论：过分强调匹配速度，可能导致匹配结果异常——这也是后面"贪婪 vs 非贪婪"要解决的问题（详见 2.10）。

### 1.5 使用正则的两种方式

在 Linux 中使用正则技术有两种方式：

1. **命令方式**：最常用的是 `grep` 命令——命令 + 正则语句 + 数据源（文件名）；
2. **函数方式**：C 语言正则库 `#include <regex.h>`，在代码中使用（详见第 4 章）。

两条重要结论：

- **正则技术非常依赖数据规则**：规则越明确、越清晰，正则表达式的编写越简单；
- 如果数据**无序存储**、没有任何边界和规则，就**无法使用**正则表达式。

由此引申到数据存储：存储数据是为了二次使用。把数据按指定格式组织（如标签化存储 `<name>张三</name><age>20</age>`）后续查找非常方便；数据库（持久化系统）也是按分行、分列、分表等格式存储数据，并提供特殊语句快速访问。**先格式化，再查找**——把文本数据格式化（序列化）后再存，日后才好检索。

> 反面例子：数据写成"张三:哈尔滨理工大学:20:北京市海淀区xxxx"连分隔符都不统一、或直接堆成一段文字，事后想查某个字段根本没有下手的地方。

## 第 2 章 grep 与正则元符号

### 2.1 grep 基本用法与结果解读

```bash
grep '正则语句' 文件名        # 基本构成：命令 + 正则语句 + 数据源
grep -n '正则语句' 文件名     # -n：结果显示行号
```

**结果解读**：执行命令后，**所有显示到屏幕上的都是结果数据**；其中**红色**标注的是"绝对匹配到"的部分，白色行同样符合规则（只是没有高亮），不符合规则的行才不会显示。

**对比示例（`A` 与 `A*`、`AA*`）**：

- `grep 'A'`：逐行过滤，该行必须至少包含一个 A。
- `grep 'A*'`：A 出现零次或多次——**空行也会被匹配出来**（A 出现零次也满足规则）。容易误以为它"匹配以 A 开头的行"，那是通配符的语义，不要与正则混淆。
- `grep 'AA*'`：星号只参照它前面**一个**字符，所以 `AA*` 拆开是"第一个 A 出现一次 + 第二个 A 出现零次或多次"，等价于"A 出现一次或多次"（与 `A+` 效果相同）。

**相等 ≠ 等价**：`'A'` 与 `'AA*'` 的结果相同，但匹配方式不同——只用普通字符查找没有使用贪心算法，是逐字符比较：一行 6 个 A 要匹配 6 次、得到 6 个结果；用 `A*` 是贪心匹配：匹配 1 次、得到 1 个结果。区别在匹配方式与结果获取过程上。所以实际查询很少只写普通字符（如直接写"张三""李四"），效率与旧字符串函数差不多，一般都要结合匹配符号。

> 通配符与正则：很多符号写法一样（如 `*`），但属于两种不同的技术，含义不同，不要搞混。

### 2.2 元符号全景

正则表达式由一系列表达式加特殊符号（**元符号**）构成，是一个长字符串。每个字符都是表达式，**表达式默认颗粒度是一个字符**：`abcd` 算表达式，`1234` 也算表达式。

两条基本规则：

- 元符号作参照时**只看它前面（或后面）的一个字符/表达式**，不会跨表达式参照；
- 必须了解每个正则特殊符号的含义，才能用正则在数据中查找。

| 元符号 | 含义 | 是否需转义（grep） |
|---|---|---|
| `\` | 转义符：转换表达式含义 | — |
| `*` | 前一表达式出现 0 次或多次（贪婪） | 不需要 |
| `+` | 前一表达式出现 1 次或多次（贪婪） | 需要 `\+` |
| `.` | 任意一个字符 | 不需要 |
| `[ ]` | 集合：匹配集合内任一字符（一位） | 不需要 |
| `[^ ]` | 集合取非：匹配非集合内容 | 不需要 |
| `^` | 行首（参照后一个表达式） | 不需要 |
| `$` | 行尾（参照前一个表达式） | 不需要 |
| `{ }` | 指定前一表达式连续出现频率 | 需要 `\{` `\}` |
| `( )` | 分组：创建新表达式、提升颗粒度 | 需要 `\(` `\)` |
| `?` | 切换为非贪婪模式 | 需要 `\?` |

### 2.3 转义符 \

转义符的作用是**转换表达式含义**：可以赋予符号另一种含义，也可以剥夺符号的特殊含义。

- `n` 本来是普通字符，`\n` 变成换行；
- `+` 是运算符（1 次或多次），`\+` 之后变成字符"+"本身；
- `$` 加转义变成字符"$"，可以匹配以字符 `$` 结尾的内容。

它不单纯是"赋予"或"剥夺"，名字就说明了作用——不管当前是什么含义，加上转义就转换成另外一种含义。

### 2.4 重复与任意字符：* + .

- `*`：以**前一个**表达式为参照，表示该表达式出现 **0 次或多次**，例如 `A*`；默认是贪婪模式。
- `+`：以**前一个**表达式为参照，表示该表达式出现 **1 次或多次**，例如 `A\+`（命令行需转义写法）；同样是贪婪模式。星号和加号就是经典的贪心匹配组合，区别在出现次数的**下限**（0 次 vs 1 次）。
- `.`：表示**任意一个字符**，只匹配有效数据，无法匹配空行、缩进等；点不需要转义。

组合示例：

```bash
grep '^h.*o$' 文件      # 匹配 h 开头、o 结尾的行（.* 表示任意字符出现 0 次或多次，中间可以没有内容）
grep '^$' 文件          # 匹配空行：开头、结尾之间没有内容
```

### 2.5 集合与取非：[a-z] [^abc]

集合 `[]` 是"表达式集合"：集合中由若干表达式构成，每次匹配时从集合中选一个表达式匹配。常用集合：

```text
[a-z]        小写字母
[A-Z]        大写字母
[0-9]        数字
[a-zA-Z0-9]  全部字母与数字
```

要点：

- **集合整体只表示"一位"**；集合内部是"**或**"的关系（`[3-9]` 就是 3 或 4 或……或 9）。
- 网站注册用户名一般限定为字母数字，就是因为用户名不允许出现特殊符号——正则里用 `[a-zA-Z0-9]` 这类集合描述，集合外的字符匹配不到，即判为非法。
- **取非**：集合内写 `^` 即 `[^abc]`，表示匹配所有**非**集合内容的数据。典型用法 `[^<>]+?`——非尖括号的任意字符 + 加号 + 非贪婪问号，可以把标签里的内容从标签头一直取到标签尾。

### 2.6 行首与行尾：^ $

- `^`：以**后一个**表达式为参照，指定该表达式为**行首**，例如 `^a`；
- `$`：以**前一个**表达式为参照，指定该表达式为**行尾**，例如 `n$`、`o$`。

典型用例：

```bash
grep '^h.*o$' 文件      # h 开头、o 结尾的行
grep '^$' 文件          # 空行
```

对比记忆：通配符中 `A*` 习惯表示"以 A 开头"；而正则中方位要用 `^` 和 `$` 明确标出。

### 2.7 出现次数：{}

大括号以**前一个**表达式为参照，用于指定该表达式连续出现的频率：

```text
A\{2\}       A 连续出现 2 次
A\{n,\}      最少 n 次、不限制最大次数（类似只给下限的星号/加号）
A\{n,m\}     最少 n 次、最多 m 次（如 A\{2,5\}：2 次到 5 次都可以）
```

- 匹配顺序是**从大到小**：先尝试连续 5 个，再看 4 个、3 个、2 个——如果先从少的看，就等不到多的了（先按 2 个匹配走，5 个的情况就不成立）。
- 大括号左右两边都要转义：`\{`、`\}`。

### 2.8 分组：()

圆括号用于**创建表达式**：把多个字符定义成一个整体，提升匹配的颗粒度。

起因：默认颗粒度是一个字符——直接写 `lis*` 去查单词，星号只参照前一个字母，匹配到的是"该字母出现多次"，还会混进长单词的片段。用括号把整个词包起来再配合元符号即可按"词"匹配：

```bash
grep '\(list\)\+' 文件      # "list" 整体出现一次或多次
```

还可以配合 `^`、`$` 保证匹配到的是独立单词（前后是空格/行首行尾，而不是其他单词的一部分）。圆括号左右都要转义：`\(`、`\)`。

> 分组还直接服务于 C 语言正则库中的"子表达式提取"（详见 4.4）——每加一对括号，表达式数量 +1。

### 2.9 贪婪与非贪婪：?

问号主要用来**切换匹配模式**：把贪婪模式切成**非贪婪模式**。用法是在贪婪符号后加问号：

```bash
grep 'a\+?' 文件     # a 出现一次或多次，以非贪婪模式匹配
grep 'a*?' 文件      # 星号同样可以切非贪婪
```

问号需要转义（`\?`）。星号、加号默认都是贪婪模式；正则有贪婪和非贪婪两种模式，`?` 就是两者之间的开关。

### 2.10 贪婪 / 非贪婪对比实验

用一组标签数据做实验，数据中有若干组 `<div>` 头、`</div>` 尾和容器数据，还夹着不属于任何标签的"垃圾数据"：

```html
<div>容器数据1</div>垃圾数据1<div>容器数据2</div>垃圾数据2<div>容器数据3</div>
```

**贪婪写法：**

```bash
grep '<div>.\+</div>' 文件
```

一行会**尽可能多地匹配**：从第一个 `<div>` 头一直匹配到最后一个 `</div>` 尾，中间所有内容（含垃圾数据）都被当成一个标签的内容取出。从数据格式角度它"没错"，但不符合需求——我们只要三个 div 的内容，垃圾数据还得二次处理抠掉，而二次处理的开销有时比查询本身还大。

**非贪婪写法：**

```bash
grep '<div>.\+?</div>' 文件
```

匹配到**一个结果就立即暂停返回**，然后自行从当前位置继续匹配第二个、第三个——这一行匹配 3 次，正好得到三个 div 的内容，垃圾数据被排除在外。

**结论**：非贪婪的本质是**用效率、速度换准确度**——贪婪一次匹配尽量多；非贪婪匹配一个就返回、再匹配下一个，匹配次数变多、速度慢一些，但准确性更好，且不需要人为操控偏移量，程序自己就会进行下一次匹配。写表达式大多数时候都是在"速度"与"质量"之间做选择，`.\+?`（"点加问号"）是使用非常多的写法。

### 2.11 命令组合与管道

**管道**：两个命令之间加竖线 `|`，前一个命令的输出传给后一个命令使用。

```bash
命令1 | 命令2 | 命令3     # 多个进程之间通过管道传递数据
wc -l                     # 统计输出的行数
```

应用示例（详见 3.4 节综合练习）：

```bash
grep 22 文件名 | grep '192.168.[0-9]\{1,3\}.1' | wc -l    # 逐级筛选并统计数量
```

很多工程人员不写代码也能用命令完成大量工作：查看端口占用、查看网络详情和状态等（如 22 端口被占用时，查是谁占用）。

## 第 3 章 规则练习

### 3.1 手机号规则

**手机号的四条规则：**

1. 11 位数字构成，数字开头、数字结尾；
2. 第一位永远是 `1`；
3. 第二位是号段，取 `3~9` 中的任一数字；
4. 后 9 位是 `0~9` 之间的任意数字。

**练习数据（判断哪些合法）：**

```text
18204508500
185890980917
11238771312
12539078133
13478O39213
15189097725
```

逐条判断：`185890980917` 是 12 位，不合法；`11238771312`、`12539078133` 第二位不在 3~9，不合法；`13478O39213` 含有字母 O，不合法。**合法的只有 `18204508500` 与 `15189097725` 两条。**

**表达式与逐段解读：**

```bash
grep '^1[3-9][0-9]\{9\}$' test
```

- `^`：开头；`1`：第一位必须是 1；
- `[3-9]`：第二位取 3~9 任一数（集合只表示一位，内部是或的关系）；
- `[0-9]\{9\}`：主体是"一个数字"，连续出现 9 次；
- `$`：结尾——与 `[0-9]` 结合，表示"以 0~9 的任意数字结尾"。

> **格式合法 ≠ 号码在用**：正则只能判断格式是否合法；要证明号码真在使用，需要短信验证（发验证码并回传核对）。肉眼判断不了号码真假，"眼睛是骗人的"，不靠肉眼查数据——这正是要用规则来匹配的原因。

### 3.2 邮箱规则

**要求（三条）：**① 用户名长度 8~15；② 用户名中不允许出现特殊符号；③ 只匹配 `.com` 后缀。

**练习数据：**

```text
liu88777@126.com
7813981032810587209182945@qq.com
busy897@7786@gmail.com
782@126.com
878231321@qq.com
buim78213@163.cn
890138729@qq.net
```

逐条判断：用户名 25 位的过长、`busy897` 仅 7 位且结构异常、`782` 仅 3 位——均不合法；`.cn`、`.net` 后缀不符合"只匹配 .com"。**合法的只有 `liu88777@126.com` 与 `878231321@qq.com` 两条。**

**思路与表达式：**

- 用集合描述用户名字符范围：`[a-zA-Z0-9]`（不允许特殊符号）；
- 用大括号限定长度：`\{8,15\}`；
- 再接 `@`、域名、并以 `.com` 结尾（点需转义成字面点）。

```bash
grep '^[a-zA-Z0-9]\{8,15\}@[a-zA-Z0-9]\+\.com$' test
```

> 说明：邮箱的用户名规则、域名（126、163、QQ、国外邮箱公司）和后缀种类都不由我们制定，所以本题只限制以上三条；这题比手机号稍难，要动手练。

### 3.3 标签匹配：规则表达式与关键数据表达式

用带标签的数据说明两类表达式的分工：

```text
<name>李四</name>
```

- 匹配 **name 标签头尾**的表达式负责"规则"定位（找到容器），属于**直接查找**——称为**规则表达式**；
- 标签内具体内容（人名）用"李.*"或"李.+?"这类形式，**李 + 任意字符**，属于**模糊查询**——称为**关键数据表达式**。

因为人名都保存在标签里，要取"标签里的名字"，需要先用规则表达式定位标签，再用关键表达式取出内容。

**取非技巧**：要取标签里所有名字、又不想限定百家姓，可以写 `[^<>]+?`——非尖括号的任意字符（人名里不会出现尖括号），配合加号与非贪婪，把内容从标签头一直匹配到标签尾。**查找一般就是查一个标签里的关键数据。**

### 3.4 综合练习：IP 筛选（面试题）

**题目**：文件中有 IP 及端口信息，找出**端口号为 22**、**号段为 192.168.1** 的 IP 并统计数量，只能用命令实现。

**思路（三条命令通过管道组合）：**

1. 先筛端口：`grep 22 文件名`；
2. 管道接入第二个 grep 过滤号段：`grep '192.168.[0-9]\{1,3\}.1'`；
3. 管道接入统计命令：`wc -l`。

```bash
grep 22 文件名 | grep '192.168.[0-9]\{1,3\}.1' | wc -l
```

**细节**：过滤号段要用**模糊匹配**的思路——如果按完全精确的字符串去写，会漏数据（实测中曾出现"结果少了一个"，改成模糊写法后才正确）；号段后续的数字也应写全，简化写法可以，但要知道差异。

## 第 4 章 C 语言正则库

### 4.1 头文件与函数总览

```c
#include <regex.h>   // 正则表达式头文件
```

C / C++ 都支持正则，代码中需要先包含头文件。正则函数数量不多，一共四个：

| 函数 | 作用 | 调用顺序 |
|---|---|---|
| `regcomp` | 正则转换：表达式字符串 → 正则类型 | ① |
| `regexec` | 匹配查询 | ② |
| `regerror` | 错误处理：语法检查 | 出错时用 |
| `regfree` | 释放正则 | 用完后 |

关键前提：在代码中**不能直接使用表达式字符串进行匹配**，必须先把表达式字符串转换成**正则类型**，后续用正则类型做模式匹配。

### 4.2 regcomp：表达式字符串转正则类型

```c
regex_t reg;                        // 声明正则类型
regcomp(&reg, regstr, 0);           // 把表达式字符串转换成正则类型，存入 reg
```

| 参数 | 说明 |
|---|---|
| `regex_t *reg` | 传入正则类型地址（转换结果存放处） |
| `char *regstr` | 正则表达式字符串的地址 |
| `int cflag` | 选项，默认传 `0` 即可 |

转换成功返回 0；函数内部会为正则类型申请空间，便于后续匹配查询。

### 4.3 regexec：匹配查询与循环匹配

```c
regexec(&reg, mmap_ptr, regnum, match, 0);
```

| 参数 | 说明 |
|---|---|
| `const regex_t *reg` | 正则类型 |
| `const char *string` | 数据源（如 mmap 得到的映射指针） |
| `size_t nmatch` | 表达式数量（N+1，见 4.4） |
| `regmatch_t pmatch[]` | 传出匹配位置数组 |
| `int eflags` | 选项，默认传 `0` |

- **调用一次只匹配一条结果**；要匹配多条须**自行 while 循环**反复调用；
- 匹配成功返回 0，匹配不到返回 `REG_NOMATCH`（非 0，作为循环结束条件）。

**指针偏移（重要）**：循环中每处理完一条，必须把指针偏移到本次匹配内容的末尾，否则**永远只匹配第一条**（死循环）：

```c
mm += match[0].rm_eo;    // 偏移到父表达式（整个匹配）的末尾
```

`match[0]` 是父表达式（整个匹配）的起止位置；偏移多一位也没问题（那个位置不会再有匹配开头），严谨做法就是跳过当前整个匹配段。

### 4.4 匹配位置数组：regmatch_t

正则匹配的返回方式不是"查到结果直接给你"，而是**标记出结果在文本中的位置**，你按位置和长度自己去取。

```c
int reg_num = 3;                 // 表达式数量
regmatch_t match[reg_num];       // 位置数组：数组长度取决于表达式数量
```

- 每个数组元素是结构体，含两个位置成员：`rm_so`（起始位置/偏移）与 `rm_eo`（末尾位置/偏移）——有了末尾和起始才能算出长度，所以每段内容需要两个位置。
- **表达式总数 = 括号对数 N + 1（父表达式）**。原则：**想要提取什么，就给什么加括号**；不想提取就不用加括号。

以 A 标签 `<a href="https://xxx.com">标题</a>` 为例（两对括号，表达式总数 3）：

| 下标 | 对应内容 |
|---|---|
| `match[0]` | 父表达式：整个 A 标签（规则表达式） |
| `match[1].rm_so / rm_eo` | 第一对括号：href 里的链接地址 起止 |
| `match[2].rm_so / rm_eo` | 第二对括号：标题 起止 |

**按位置截取数据**用 `snprintf`（目标数组、长度、格式串、内容首地址）：

```c
snprintf(title, match[2].rm_eo - match[2].rm_so + 1, "%s", mmap_ptr + match[2].rm_so);
snprintf(url,   match[1].rm_eo - match[1].rm_so + 1, "%s", mmap_ptr + match[1].rm_so);
```

- 长度写 `rm_eo - rm_so + 1`（+1 是给字符串结尾 `'\0'` 留位）；
- 内容首地址 = **数据源首地址 + 偏移量**（即 `mmap_ptr + rm_so`）；
- 每次匹配前建议用 `bzero` 清空目标数组，避免残留旧数据。

### 4.5 regerror：错误检查

如果因表达式写错导致匹配不到或异常，可以用 `regerror` 检查：

```c
regerror(&reg, err_buffer);    // 对 reg 中的正则做语法检查，结果写入 err_buffer
```

- 它会检查逻辑错误或语法错误，把错误信息（英文）输出到字符缓冲区，告诉你哪里错了；
- 排查匹配失败时的首选手段（配合"printf 打印映射内容确认数据加载成功""先用简单数据测试"一起使用）。

### 4.6 regfree：释放正则

```c
regfree(&reg);    // 释放正则类型
```

`regcomp` 为正则类型申请了空间，使用完毕必须用 `regfree` 释放，**避免内存泄漏**（与 malloc/free 的配对思想一致）。

### 4.7 C 语言中的两层转义

写代码时表达式不能直接照抄命令行的写法，因为要经过**两层解析**：

1. **C 解析器（字符串解析层）**：双引号在 C 字符串里要写成 `\"`；
2. **正则解析器（模式解析层）**：正则元字符要加反斜杠——`\+`、`\?`、`\(`、`\)`、`\{`、`\}`、`\|` 等。

**技巧**：先把表达式按纯正则形式写出来，再对照逐个加转义（统计好双引号几处、括号几处、加号几处、问号几处……），这样不会漏。

示例（两层转义后的 C 字符串）：

```c
const char *regStr = "<a[^>]\\+\\?href=\"\\([^\"]\\+\\?\\)\"[^>]\\+\\?>\\([^<]\\+\\?\\)</a>";
```

> 画图标注时注意：括号要把"非引号任意字符 + 加号 + 问号"**整体括住**，写的时候不要漏括号。

## 第 5 章 数据源加载与实战

### 5.1 两种加载方式：open/read 与 mmap

命令行匹配可以直接指定文件；程序里则要自己把数据加载进进程，有两种方式：

1. **open + read**：打开文件，把数据读到缓冲区；
2. **mmap 文件映射**：把整个文件数据直接映射到进程内存，两行代码搞定，不需要一点点读。

只有**磁盘文件**需要映射——其他数据源（进程内存、外部输入、命令行参数）在程序里直接访问即可。

### 5.2 头文件清单与 mmap 用法

所需头文件：

```c
#include <regex.h>
#include <sys/mman.h>
#include <sys/types.h>
#include <sys/stat.h>
#include <sys/fcntl.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <unistd.h>
```

映射流程：

```c
int fd = open("url.html", O_RDWR);              // 打开文件
int size = lseek(fd, 0, SEEK_END);              // 移动读写位置到末尾，返回文件大小
char *mmap_ptr = NULL;
mmap_ptr = mmap(NULL, size,                     // 映射大小
                PROT_READ | PROT_WRITE,         // 权限：可读可写
                MAP_PRIVATE, fd, 0);            // 映射方式、文件描述符、偏移量 0
close(fd);                                      // 映射建立后即可关闭 fd
```

要点：

- `mmap` 参数依次为：地址（传 `NULL` 由系统决定）、映射大小、访问权限（`PROT_READ`/`PROT_WRITE` 等）、映射方式（`MAP_PRIVATE` 等）、文件描述符、偏移量；
- **为什么先映射再关 fd**：映射要用文件描述符作参数建立；建立之后 fd 就没用了，close 放在 mmap 之后即可，此后通过映射指针照样访问文件数据；
- 映射成功后可直接通过指针访问整个文件内容；可先用 `printf` 打印映射内容验证是否成功；
- 用完后 `munmap` 释放映射；
- 相关辅助函数：`errno`（错误码）、`bzero`（清零内存块）、`snprintf`（格式化写入）在实战中配合使用。

### 5.3 实战：提取网页 a 标签的链接与标题

**需求**：使用正则函数 + mmap，把文件里 A 标签的**链接**与**标题**匹配提取出来并打印输出。

- 数据文件：先用两行 A 标签的 `URL.txt` 跑通，再换真实网页源码 `url.html`；
- 只输出链接与标题（A 标签本身不输出）；
- 声明两个数组分别存放链接与标题（长度 20~1024 均可，不要太短——链接可能很长）；
- 表达式中给要提取的两部分各加一对括号（共两对），即表达式总数 3。

**数据源（url.html 为真实抓取的新闻网页源码，含大量 A 标签，节选）：**

```html
<ul>
  <li id="10698191" class="t_weight"><em></em><a href="/iframe/2026/09-17/10698191.shtml"></a><a class="ptv" href="//www.chinanews.com.cn/sh/shipin/cns-d/2026/09-17/news1069196.shtml"> 中国成功发射天仪51、52星</a></li>
  <li id="10698334"><em></em><a href="/gn/2026/09-17/10698334.shtml">辽宁省政协原党组副书记、副主席戴玉林被查</a></li>
  <li id="10698248"><em></em><a href="/gn/2026/09-17/10698248.shtml">外交部：中国将向联合国人权理事会再次主提无障碍决议</a></li>
  ...
</ul>
```

**程序（urlRegex.c，整理版）：**

```c
#include <regex.h>
#include <sys/mman.h>
#include <sys/types.h>
#include <sys/stat.h>
#include <sys/fcntl.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <unistd.h>

int main(void)
{
    int fd = open("url.html", O_RDWR);              // 打开数据源
    int size = lseek(fd, 0, SEEK_END);              // 返回文件大小
    char *mmap_ptr = NULL;

    mmap_ptr = mmap(NULL, size, PROT_READ | PROT_WRITE, MAP_PRIVATE, fd, 0);
    close(fd);                                      // 映射建立后可关闭 fd

    regex_t reg;                                    // 声明正则类型
    const char *regStr = "<a[^>]\\+\\?href=\"\\([^\"]\\+\\?\\)\"[^>]\\+\\?>"
                         "\\([^<]\\+\\?\\)</a>";    // 匹配 A 标签的表达式（两层转义）
    regcomp(&reg, regStr, 0);                       // 转换成正则类型

    int reg_num = 3;                                // 表达式数量 = 括号数 2 + 1
    regmatch_t match[reg_num];

    char title[1024];
    char url[1024];
    while (regexec(&reg, mmap_ptr, reg_num, match, 0) == 0)   // 一次匹配一条，循环匹配
    {
        bzero(title, sizeof(title));                // 每次匹配前清空
        bzero(url, sizeof(url));
        snprintf(title, match[2].rm_eo - match[2].rm_so + 1, "%s", mmap_ptr + match[2].rm_so);
        snprintf(url,   match[1].rm_eo - match[1].rm_so + 1, "%s", mmap_ptr + match[1].rm_so);
        printf("%s:%s\n", title, url);

        mmap_ptr += match[0].rm_eo;                 // 指针偏移到本次匹配末尾，继续下一条
    }

    regfree(&reg);                                  // 释放正则类型

    return 0;
}
```

程序要点回顾：

- 先**准备表达式**（两对括号，共 3 个表达式）→ **准备正则**（regcomp 转换）→ **准备数据源**（open → lseek → mmap → close）→ **循环匹配提取**（regexec + snprintf + 指针偏移）→ **释放**（regfree）；
- 每匹配一次提取一条链接与标题；指针偏移是循环能进行下去的关键；
- 该模板学会后，以后只需要考虑"表达式怎么写"；要提取的内容越多，括号越多、位置数组越长。

### 5.4 表达式的通用性改进

**问题**：用最初写的简单表达式匹配真实网页源码，会发现有的 A 标签匹配不到——有的 A 标签在 href 之外还有别的属性字段（href 前面可能还有字段、后面还可能跟着字段），也有没有标题的 A 标签、头部带多个字段的复杂标签。最初表达式没有考虑这些差异，**兼容性差**。

**原则**：分析数据格式时要**找出最复杂的那种格式**，保证表达式能匹配到这一整类数据——比如页面上有 10 种 A 标签，表达式只能匹配 3 种就是失败。

**改进写法**：href 前后的其他字段用"非 `>` 的任意字符 + 加号 + 问号"（`[^>]\+?`）去吃；href 本身是明确要提取的字段，写得精确（`[^"]\+?` 到引号结束）：

```text
<a[^>]\+?href="\([^"]\+?\)"[^>]\+?>\([^<]\+?\)</a>
```

改进后的表达式的**可用性（通用性）**比最初强很多——可用性强的表达式可以匹配一种数据类型的不同格式变体。

### 5.5 常见错误与调试技巧

- **只匹配到第一条**：忘记在循环里做指针偏移（`mmap_ptr += match[0].rm_eo;`）——最常见的 bug；
- **转义漏写**：C 字符串里 `\+`、`\?`、`\(`、`\)` 漏一处就会匹配失败；对照法（先写纯正则、再加转义）能避免；
- **括号数量算错**：表达式数量 = 括号数 + 1，数组长度要与之匹配；
- **调试手段**：`regerror` 检查表达式；`printf` 打印映射内容确认数据加载成功；先用简单数据（URL.txt 两行）跑通再上真实数据（url.html）；
- **规范**：使用流程归纳为——① 确定数据源；② 分析待处理数据格式、编写**可用性强**的表达式；③ 用正则函数匹配和提取。

## 第 6 章 延伸阅读

### 6.1 爬虫场景中的正则

爬虫技术的核心环节之一就是**分析网页里的 A 标签、提取链接**：

```text
抓取网页 → 分析 A 标签（href 里是链接、标签中间是标题） → 提取链接
        → 按链接发起请求下载内容 → 后续做内容分析（如中文分词选关键词）
```

本节 5.3 的程序就是这个流程中的"提取"环节。

### 6.2 正则的适用边界

- **依赖数据规则**：规则越明确清晰，表达式越简单；无序存储、无边界无规则的数据无法用正则处理；
- **数据源多样**：磁盘文件、进程内存、外部输入、命令行参数都可作为数据源（如 `./check 18233214550` 用命令行参数做手机号合法性检查）；
- **不必重复造轮子**：数据库等系统自带正则支持（如 MySQL 内置正则能力），直接写正则语句即可，无需调用系统正则函数；
- 正则与数据库 like、全文检索各有所长：文本片段筛选、格式校验、批量替换是正则的主场。
