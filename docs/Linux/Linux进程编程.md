# Linux 进程编程：进程基础、进程间通信与信号

> 本文档整理 Linux 进程「基础 → 原语 → 综合实战」的完整内容，按知识主线组织编写，持续补充。

## 第 1 章 进程基础

进程这一章分为两个单元：**进程基础**与**进程原语**。本章讲第一单元：进程是什么、进程的地址空间与内存、进程的状态、以及 CPU 与进程之间的关系。

### 1.1 程序与进程

**进程**是多任务操作系统中**执行任务的单元**，有三重定位：

- 进程是系统**默认的调度单位**；
- 进程可以**访问硬件资源**（CPU、内存、磁盘等），完成特定任务；
- 进程是系统中**最小的资源分配单位**。

电脑里装的 QQ、微信启动之后都会变成进程，去访问内存、CPU、显卡等各种设备。不同软件的进程需求不同：网盘类软件主要吃网络（访问网卡）；视频类软件对 CPU 占用较多、其次访问显卡（视频渲染）。硬件由谁去使用、访问并完成任务？答案就是进程。

**程序与进程的关系**（Linux 下程序文件是 ELF 格式，Windows 下是 exe，本质类似）：

| | 程序 | 进程 |
|---|---|---|
| 本质 | 静态资源 | 动态执行结果 |
| 占用 | 只占用磁盘空间（安装≈解压） | 占用内存、CPU 等资源 |
| 关系 | 进程的静态表现 | 程序的动态执行实体 |

- **程序是静态的**：安装到电脑后不启动，就只占磁盘空间、安安静静不动。
- **进程是动态的**：用户启动程序，系统创建出进程，进程根据执行任务的需要占用资源。进程要做的事情都来源于程序怎么写的。
- 二者是**前置与后置**的关系，依赖很强。

**程序文件在进程启动后能否删除？** 取决于进程对程序文件有没有后续依赖：

- 进程执行后还要读/写配置文件、加载缓存、生成文件——离不开程序目录，**不能删**；
- 程序运行后完全独立、不再访问自身文件（例如自己编译的单文件程序）——程序文件**可以删除**，进程照常运行；
- 但注意：**删除后无法再次启动该程序**（除非进程永不结束）。

> 思考实验：写一个程序，运行起来之后把程序文件删掉，观察进程能否继续运行。

### 1.2 进程的产生过程

进程创建大体分四步：

1. 为进程**创建 0~4G 内存空间**（初始为空）；
2. **分配并建立 PCB**（进程控制块）；
3. 通过克隆等方式把执行数据**填充进 0~3G 用户空间**；
4. PCB 与用户空间就绪，进程进入就绪态，**可以运行**。

**为什么进程是最小的资源分配单位？** 系统中的执行单元有三种：进程、线程、纤程。区别在于：**线程和纤程创建时系统不会额外分配内存，只有进程创建时会分配独立的内存空间**。类比企业雇工：任何执行单元都必须是"调度单位"（首先得是个人），但只有进程会"领到一台电脑"（独立内存）。

微观上，进程 ≈ **一块独立内存空间（创建时分配）+ 一个默认的执行单元**。

> 能同时存在多少进程，与可用内存（物理/虚拟内存）大小相关。

### 1.3 地址空间总览

操作系统为每个进程分配地址空间：**32 位（x86）系统为 0~4GB**；64 位系统可用范围大得多（一般资料记作 0~16T 级，实际由 CPU 与操作系统决定）。

以 0~4G 为例，划分为两部分：

```
        ×86 32 位
   ┌──────────────┐
4GB│  内核空间     │  ← PCB（进程身份信息）
3GB├──────────────┤
   │              │
   │  用户空间     │  ← 栈 / 库 / 堆 / BSS / data / code（任务数据）
0GB└──────────────┘
```

- **3~4G 内核空间**：存放 PCB 等进程身份信息；
- **0~3G 用户空间**：存放进程的任务数据（代码、数据、堆栈等）。

两条重要结论（务必区分）：

- **用户空间独立、不共享**：两个进程若共享用户空间会产生访问冲突（我定义的变量你能改、重名的变量无法处理），所以每个进程的用户空间各自独立；
- **内核空间共享**：所有进程的内核数据在一块共享区域，PCB 集中存放，便于操作系统统一调度管理（类比公司只有一个档案室）。用户程序对 PCB 没有访问权限，不能直接修改内核数据——所以共享也不会冲突。

一句话：**内核空间存"身份信息"（你是谁、状态如何），用户空间存"工作信息"（能做什么、执行哪些代码）**。

### 1.4 用户空间布局

0~3G 用户空间自上而下分为：

| 区域 | 内容 |
|---|---|
| 命令行参数与环境变量 | 进程内存中的第一块数据，不用命令行参数时为空 |
| 栈 Stack | 存放函数内部的局部数据（函数之间有"栈隔离"） |
| 库空间（映射内存） | 程序加载的静态库、动态库（mmap 映射） |
| 堆 heap | 动态申请的内存 |
| BSS 段 | **未初始化**的全局变量、静态变量 |
| data 数据段 | **已初始化**的全局变量、静态变量 |
| code 代码段 | 程序逻辑（CPU 按代码执行） |
| 末尾节点 | 结束/跳转节点，CPU 执行到这里表示程序结束 |

**main 函数的参数**：

```c
int main(int argc, char *argv[])
// argc：参数个数        argv[0] = 程序启动路径
//                       argv[1]、argv[2]… 依次为传入的参数
// 例：./app -a -336 -n 0   →  argc = 4（启动路径也算一个参数）
```

### 1.5 进程控制块 PCB

**PCB（进程控制块）** 是内核空间里为每个进程建立的结构体，**详细记录进程的全部状态和信息**：

- PID（进程 ID，系统内唯一编号，类似身份证号）；
- 进程状态、启动时间、访问的资源、是否存活等。

类比：PCB 比户口本记录得还全——户口只记出生地、户籍、民族；PCB 记录进程每时每刻的状态。**PCB 不关心进程"在干什么任务"**——身份档案与工作内容分开存放（身份证上看不出你在哪上班，进公司后看工作证）。

想访问 PCB 里的数据（如 PID），要看系统是否提供接口：系统提供函数（如 `getpid()`）就能经上下文切换读取；不提供的就访问不了。

### 1.6 物理内存、虚拟内存与 Swap

**物理内存**是买电脑时说的内存条（16G、32G），有实体、在"关于本机"里可查；**进程分配到的内存都是虚拟内存**。

**为什么需要内存？** 早期计算机没有内存，CPU 直接与硬盘交互。CPU 只负责计算、本身没有存储能力，中间数据要存到盘里；而机械硬盘读写速度远远跟不上 CPU——CPU 算了很多次，盘只记下很少一部分，相当于"白算"。于是设计出在 CPU 与硬盘之间充当**高速缓存**的硬件：内存。内存造价高、容量小，不能替代硬盘。

**Swap（交换）机制**：内存小而贵，所有进程都要用，必然不够；于是把当前没人访问的内存数据**交换到外存（硬盘）**、腾出空间，需要时再换回来。类比饭馆包房：客人包了一整天但只来 4 小时，空档期可以转租他人——提高内存重复利用率。系统里把虚拟内存调大（如打游戏时调大几十个 G），本质就是借助外存。

**虚拟内存与物理内存的关系**：

- 虚拟地址像一个**指针**，指向一块物理内存，这种指向关系叫**映射**（虚拟地址映射）；CPU 通过映射访问物理内存；
- 二者**不是 1:1**：分配 1G 虚拟内存，背后实际指向的物理内存不一定是 1G；
- 映射数量庞大，由系统的**内存管理器**负责，映射记录保存在**内存映射表**中。
- 类比：物理内存像现金，虚拟内存像支票——支票（虚拟地址）指向现金（物理内存）。

**为什么不让进程直接访问物理内存？** 直接占用会是"强制独占"——就像打开的文件即使不读不写，删除时系统也提示"被占用"。虚拟内存是**间接访问**：真正使用时才映射到物理内存，不用时对应物理内存可以给别人；**间接访问永远比直接访问更灵活、更安全**。若每个进程都直接占物理内存，内存根本不够用（操作系统自身和大量系统程序也都是进程）。

### 1.7 页、寻址与内存权限

**页（Page）** 是内存分配的基本单位，不是字节。页大小分两种：**小页 4096 字节（4K，经典）**、**大页 16K**。

**多级间接寻址**（与文件系统的间接寻址同源）：

- 一级间接：一个 4K 块 ÷ 4（每个指针 4 字节）得到 **1024 个新指针**，指向 1024 个页面；往上二级、三级依此类推；
- **32 位系统**对应三级间接寻址，访问范围 0~4G；
- **64 位系统**支持四级间接寻址，可访问范围以 TB 计——这就是 32 位与 64 位系统地址空间差异的来源。

**内存权限**（以页为单位设置）：

| 权限 | 说明 |
|---|---|
| `PROT_READ` | 只读 |
| `PROT_WRITE` | 只写 |
| `PROT_EXEC` | 执行——**库空间（映射内存）需要执行权限**：动态库是外部编入的功能，必须能"跑起来" |
| `PROT_NONE` | 无权限——**内核空间对用户不可读、不可写、不可执行**，但系统自己可读写 |

这与文件的权限（所有者/同组/其他）类似：同一块内存可以从不同角度设置权限，例如"对内可读写可执行、对外不可访问"。

**系统开销：一次 8192 与 5000+3192 的对比**

```
A: malloc(8192)                  // 一次按整页（两页）申请，直接可用
B: malloc(5000); malloc(3192);   // 先占两页并做访问限制，再次申请时检查并解除限制
```

- 内存按页分配，没有"500 字节"这种单位，申请 5000 字节系统也给两页（8192），但加访问限制（只有 5000 可用）；
- B 第二次申请时系统先检查、发现上次两页未用完，解除限制继续用——**多了"检查、限制、解除限制"等与系统交互的步骤，系统开销更大**；
- 结论：**评价代码优劣不能只看代码行数，要看与系统交互的步骤是否更少**。申请内存按整页申请（4K/8K），不要写 1000、2000 这类零散数字。

常用单位对齐：**内存页 4096（4K）、内核缓冲区 4096、以太网帧 1500**。缓冲区大小与系统缓冲对齐，一次复制即可完成；不对齐就要分多次复制，增加系统开销。

### 1.8 进程状态与状态转换

**五种常态**（主流操作系统基本一致）：

| 状态 | 含义 |
|---|---|
| 就绪态 | 等待时间片——如同运动员在起跑线上等发令枪 |
| 运行态 | 获得时间片、占用 CPU 执行任务 |
| 阻塞态（睡眠态） | 执行中因等待资源等原因放弃 CPU，等待唤醒 |
| 挂起态 | 执行中被挂起，放弃 CPU、等待恢复 |
| 终止态 | 进程退出，释放资源 |

**状态转换**：

```
        ┌──────── 运行 ────────┐
        │         ↑  ↓          │
        ↑                    ↓
      创建(就绪)            终止
        │         ↑  ↓         ↑
        └──→ 阻塞/挂起 ←──────┘
```

- 就绪：获得时间片 → 运行；可直接 → 终止；**不能**直接转挂起（还没开始执行，谈不上挂起）；
- 运行：时间片耗尽 → 被强制切回就绪；可 → 阻塞、挂起、终止；
- 阻塞：被唤醒后**先回就绪**（不能直接运行，要等时间片）；可 → 终止；可被外部挂起（视系统支持）；
- 挂起：被唤醒（数据换回内存）后 → 就绪；可 → 终止；
- 终止：终点，不再转换。**任意状态都可能直接转终止**（类比"猝死随时可能发生"）。

**阻塞与挂起的核心区别（易混）**：

- **阻塞可以被强制中断**：如睡眠被闹钟提前叫醒——因为阻塞进程的内存数据还在内存中；
- **挂起不可被中断**，只能由系统恢复——因为挂起进程的内存数据被**全部交换到外存**（"假死"，灵魂被迁走）；**唤醒的本质就是把外存数据换回内存**。

**新生态**：进程刚创建、只有 PCB 而 0~3G 还是空的，无法执行、不可调度，这种"创建了但未初始化完毕"的状态叫新生态；初始化完毕即进入就绪态。

**死锁与饥饿**：多进程竞争资源时可能出现两类问题——**死锁**：多个进程互相等待对方持有的资源，谁也无法推进；**饥饿**：某进程长期抢不到所需资源（如时间片、锁），迟迟得不到执行。理解这两种现象是后续并发编程的基础。

**僵尸态与孤儿态**：Linux 中进程实际有 7 种状态，比五种常态多出**僵尸态**（子进程先退出、父进程未回收）和**孤儿态**（父进程先退出）——详见第 4 章。

### 1.9 僵尸态与孤儿态

- **僵尸进程（zombie process）**：子进程退出后，用户空间数据被全部释放，但 PCB 残留未回收——进程变为僵尸态（状态标识 `Z`），会造成内存泄漏；
- **孤儿进程（orphan process）**：**父进程先退出**，子进程还没有结束，此时子进程转变为孤儿进程。
- 两者的产生原因、危害与回收方法在第 4 章详细展开。

### 1.10 时间片与多进程并发

CPU 是计算机的核心，所有程序的执行都离不开它。CPU 资源有限——即使多核（8 核 = 8 个 CPU），操作系统里还有大量系统进程在请求 CPU，绝不允许某个进程一直独占。

**分时复用**：把 CPU 时间切成**时间片（如 10ms）**，多个进程轮流使用——每个进程跑一个时间片、快速轮转交替使用 CPU，称为**多进程并发执行**。

一个时间片够用吗？不要小看 CPU：3.2GHz 的 CPU 一纳秒可执行约 3.2 条指令（纳秒是秒的十亿分之一），10ms 已是相当长的时间；且很多进程一个时间片用不完（因阻塞等原因提前放弃 CPU）。用户感觉多个软件"同时"在跑，其实是 CPU 快速切换的结果——如同同时喝两瓶饮料，切换够快就相当于"同时喝"。

**串行 / 并发 / 并行**：

| 概念 | 含义 |
|---|---|
| 串行 | 有序执行，如代码从第 1 行执行到第 8000 行 |
| 并发 | 多进程共用**一个** CPU，按时间片交替执行 |
| 并行 | 需多核硬件支持，多个进程**同时**占用不同 CPU 执行；效率最高 |

并发的价值（两条）：**提高获得 CPU 的概率**（80 个进程竞争一个 CPU 时，你有 8 个进程参与轮转，被调度到的概率更大）；**减少时间片浪费**（某个进程阻塞放弃时间片，同批进程中的其他进程可以继续使用，时间片不会被白白占用）。

例：拷贝 300MB 文件，单进程 vs 8 个进程——8 个进程即使不能并行（核不够），也能靠上述两点加快拷贝。**无论并行还是并发，都能在一定程度上提高程序执行效率。**

> 历史背景：早期是单任务系统（一次只能干一件事，切换任务要换软盘），硬件资源被浪费（1 万美元的电脑只能发挥约 3000 美元的性能）；上世纪 60 年代硬件迅猛发展后，发展出多任务系统。

### 1.11 用户态、内核态与 CPU 特权级

用户态为什么访问不了内核空间？根源在 CPU 的权限级别。以 Intel 处理器为例，CPU 权限分为 **0~3 级共四级（同心圆环结构）**：

- **0 级最高（level 0）**：如同"上帝"，可访问所有软硬件数据，系统不设防——即**内核态**；
- **3 级最低（level 3）**：只能访问系统允许的部分数据——即**用户态**；程序员写的代码都运行在用户态（3 级）。

### 1.12 系统调用与上下文切换

以 `sleep` 为例：sleep 是用户层函数（3 级权限），无法控制 CPU 的定时器；系统为它对应了一个**系统函数（system call）**，该函数必须以 0 级执行才能操作硬件。于是需要把 CPU 权限从 3 级切到 0 级，执行完再切回来。

**上下文切换本质上就是 CPU 权限级别的切换**：

- **上切** = 提高权限（用户态 → 内核态）；**下切** = 降低权限（内核态 → 用户态）；
- 切换**总是成对出现**——不可能只上不下：用户态发起上切（一次），内核干完活后下切返回（一次）；
- 内核权限更高，需要用户空间数据时可直接访问，一般不必再向下切换。

**系统调用**：绝大多数系统函数都会触发"系统调用"事件——由它完成上切，内核执行完毕再下切回来。因此 main 函数执行过程中会经常因权限不足被"中断一下"：切换进内核干活、回来继续执行。

想访问 PCB 数据（如 PID）必须通过系统提供的接口函数（如 `getpid`），经上下文切换完成获取。

## 第 2 章 进程创建：fork

操作系统为了让开发者进行进程创建与使用，提供了一组系统库函数，核心有四个：**fork（创建）、exec（替换）、wait / waitpid（回收）**。本章讲 fork。

### 2.1 亲缘关系与 init 进程

系统中进程之间存在**亲缘关系**：父子进程最有代表性；爷爷和孙子、一级一级往下也都算亲缘关系。

- 每个进程必然有父进程；所有进程往上追溯，最终一定到达**1 号进程（init 进程）**——它是系统中最顶层的进程，一般是开机最先运行的程序；
- **init 没有父进程**，系统中所有进程都是它的"子集"。类比根目录：所有文件往上翻总能到达根目录，根目录之上再没有父级。

### 2.2 fork 原型与返回值

fork 用于进程创建：父进程在代码中调用 `fork()`，会创建一个子进程。**父进程调用一次，创建一个子进程**（不是创建"一对父子"）。

```c
#include <unistd.h>        // 系统核心方法都要加这个头文件

pid_t pid;                 // pid_t 是进程 id 类型
pid_t mypid = getpid();    // 返回当前调用进程的 pid；getppid() 返回父进程 pid
pid = fork();              // 调用后，当前进程会创建一个子进程
```

查看手册：终端里 `man fork`；或在编辑器中把光标停在函数上按 **Shift+K** 跳转手册，按 `q` 退出。

**fork 的返回值（三种情况）**：

| 返回值 | 含义 |
|---|---|
| `> 0` | 在**父进程**中返回，值是**子进程的 PID**（如父进程 3000 创建子进程 3001，父进程拿到 3001） |
| `== 0` | 在**子进程**中返回 0 |
| `== -1` | 创建失败，并设置 errno，供后续错误处理 |

**返回值的机制解释**（简化版）：fork 内部拆成"创建"（申请子进程的虚拟地址空间）与"克隆"（拷贝 PCB 与用户空间）两部分。父进程执行到 fork 完成创建与克隆后，把子进程 PID 写入寄存器；子进程被创建后**看不到 fork 的调用入口**（系统隐藏了），系统把寄存器重置为 0，因此子进程拿到的是"被重置后的返回值"——这就是子进程中 `fork()` 返回 0、并且不会继续 fork 的原因。

### 2.3 父进程与子进程的区分（标准模板）

父子进程共享同一份代码，只能靠**同一个变量在两边取值不同**来区分——fork 的返回值正是这样的变量（父进程 >0、子进程 ==0）：

```c
pid_t pid;
pid = fork();
if (pid > 0)            // 父进程分支
{
    printf("Parent pid %d Running...\n", getpid());
}
else if (pid == 0)      // 子进程分支
{
    printf("Child pid %d Running...\n", getpid());
    exit(0);            // 子进程执行完立即退出
}
else                    // fork 失败处理
{
    perror("fork call failed\n");
}
```

这是 Linux/Unix 下**区分父子进程的标准模板，必须会写**。配套代码示例（`区分父子进程模板.c`，拼写已修正）：

```c
#include <stdio.h>
#include <unistd.h>
#include <stdlib.h>
#include <string.h>

// Linux 和 Unix 系统使用 fork，用于区分父子进程的标准模板
int main(void)
{
    pid_t pid;
    pid = fork();
    if (pid > 0) printf("Parent pid %d Running...\n", getpid());
    else if (pid == 0) printf("Child pid %d Running...\n", getpid());
    else perror("fork call failed\n");    // fork 调用失败处理

    printf("Hello World\n");              // 父子进程都会执行到这里

    return 0;
}
```

最简示例（`fork使用.c`）——fork 之后父子都会继续执行，一句 printf 会打印两次：

```c
#include <stdio.h>
#include <unistd.h>
#include <stdlib.h>
#include <string.h>

int main(void)
{
    pid_t pid;
    pid = fork();
    printf("Hello World\n");    // 父进程打印一次、子进程打印一次
    while (1);                  // 卡住便于观察两个进程

    return 0;
}
```

**子进程的代码执行范围（重点）**：

- 默认情况下子进程执行与父进程相同的代码任务，但子进程**只从 fork 之后的位置往下走**（它是被 fork 创建出来的）；
- 父进程的代码从起始执行到末尾（除了 `if (pid==0)` 分支内不属于它的部分）；
- 若子进程不退出、踏出自己的代码段，就会把父进程专属的后续代码也跑掉——部分函数/资源只有父进程能用，子进程执行会出错。因此**严禁子进程踏出代码段**：规范写法是在自己分支内执行，执行完毕立即 `exit(0)`；要持续干活就写循环。

> 思考题：解释"子进程为什么不调用父进程的代码"——结合"子进程从 fork 之后执行、且 fork 入口被隐藏、返回值被重置为 0"理解。

### 2.4 子进程的继承与拷贝

多进程的两种用途：提高执行效率（多个进程获得更多 CPU 时间片）；任务多样性（不同进程干不同的活）。默认"世袭式"继承（子进程执行与父进程相同的代码）并不总是需要的，继承方案经历了三个版本：

**第一版：拷贝继承（早期全量拷贝）**

- **用户空间完全拷贝**：堆、栈、全局数据、代码段全部复制一份——父进程 fork 前声明的变量（如 `int A = 3000` 在栈上），子进程不声明也能用；但子进程修改 A 不影响父进程（一份变两份、各改各的）；
- **PCB 部分拷贝**：PID 等数据重新生成（父子"同名"但"身份证号"必须不同），其余大多从父进程拷来再改；
- 问题一：**开销大、创建慢**——内存页表若 100M 就要整份复制，fork 一次内存开销近似翻倍，多进程时内存压力暴增；
- 问题二：**无意义的强制拷贝**——`fork + exec` 场景中子进程本来就要用 exec 重载新程序（无需继承的数据），但拷贝是强制的：父进程花时间拷 100 兆，子进程随后全部覆盖，时间与内存全浪费。

**第二版：vfork（零拷贝）**

- 用 vfork 创建的子进程**不拷贝、没有 0~3G 用户空间**（用户层是空的）；
- 代价：不能直接使用父进程的数据，**必须结合 execl 使用**——先用 vfork 创建"壳子"，再用重载装载新程序；
- 本质是"打补丁"：不替换 fork，只是给用户多一个选择（要拷贝用 fork、不要用 vfork），没有根本解决拷贝慢的问题。

**第三版：COW 写时复制（当前版本）**

- 机制：**读共享、写复制**——创建子进程默认不拷贝任何数据，子进程直接访问父进程的内存（共享页表，零拷贝即可运行）；
- 系统把共享的内存页表统一标记为**只读**；当任意一方要**写**某页数据时，触发**缺页中断**，系统**按页（4K）**复制该页——修改方改的是自己的副本，另一方不受影响；
- **写复制是双向的**：子进程写 → 子写复制；父进程写（如循环变量 i++）→ 父写复制，子进程保留的是创建那一刻的**快照**值；
- 效果：不写时零开销、几乎无内存压力；即使写也只拷一页。当前 Ubuntu 即支持该版本。

> 读共享、写复制不只属于 fork，它是**共享内存**这一经典手段的体现：一个程序有 100M 数据要给另一执行单元处理，拷贝 100M vs 共享内存——共享内存 + 写复制显然更优。

### 2.5 循环创建子进程

多进程模型有两种：

- **二级多进程**：一父多子（最常用）；
- **多级多进程**：父创建子、子再创建孙，一层一层（需人为控制每层数量）。

**二级多进程标准写法**——循环 + fork + 子进程 break 跳出循环：

```c
int i;
pid_t pid;
for (i = 0; i < 3; i++)
{
    pid = fork();
    if (pid == 0)
        break;          // 子进程跳出循环，只让父进程继续创建
}
if (pid > 0)
{
    // 父进程：循环结束后回收（见第 4 章）
}
else if (pid == 0)
{
    // 子进程：执行自己的任务
}
```

- **不写 `if (pid == 0) break` 会失控**：子进程继承了循环变量，会回头继续执行循环、继续创建（变成多级多进程），进程数不可控；
- **进程数量公式**：循环 fork n 次，**不含父进程的子进程数为 `2^n - 1`**；含父进程共 `2^n` 个。推导：每 fork 一次进程数翻倍，n 次后总数 2^n，减去父进程本身。

**输出顺序与创建顺序无关**：

- 进程一定是**一个一个有序创建**的（PID 也连续），但谁先输出取决于谁先拿到时间片、谁先刷新缓冲区——**创建有序 ≠ 输出有序**，不同机器、不同终端结果都可能不同；
- 只核对**进程数量、PID 与循环变量 i 的快照**即可，输出顺序不必纠结。

**i 的快照**：子进程继承的 i 是"创建那一刻的快照"（i++ 是后置自增，第一个子进程拿到 0，之后父进程 i 变 1 再创建第二个）——三个子进程继承的 i 分别是 0、1、2。这也是"共享内存中父进程改了 i，子进程看到的却还是旧值"的原因：写时复制是双向的，父进程修改前先把该页复制一份、子进程侧保留快照。

**手算练习**：

```c
fork();                    // 第一行
fork() && fork() || fork();// 第二行（短路运算）
fork();                    // 第三行
```

- 本题**不适用 2^n 公式**，考察 fork 返回值与逻辑**短路**（`&&`、`||`）的组合：父进程中 `fork()&&fork()` 两个都返回 >0（真），短路跳过 `||` 后的 fork；
- 先看第一层：父进程自身在这些代码中创建了 4 个子进程），各"孩子"进程后续还能执行哪些 fork、创建多少；可用**画进程树**的方式逐层展开核对。

### 2.6 用 ps 观察父子进程

编译运行后，另开一个终端用 `ps aux` 查看进程信息：

- 能看到两个同名进程（父子）；
- Linux 下有亲缘关系的进程 **PID 一般连续（连号）**，小的在前是父、大的是子；但**连号不一定是父子**（其他进程也可能恰好连号），要结合父子关系判断。

进程状态标识（后续章节常用）：

| 标识 | 状态 |
|---|---|
| `R` | 运行 |
| `S` | 睡眠（可中断） |
| `D` | 不可中断睡眠 |
| `T` | 挂起/停止 |
| `Z` | 僵尸 |

### 2.7 常见问题

- **子进程为什么会执行父进程的后续代码？** 因为它们共享同一份代码；子进程从 fork 之后往下走，若不加限制就会继续执行分支之外的内容——用 `exit(0)` 在自己分支末尾退出即可；
- **输出顺序乱**：正常现象（时间片决定），只核对数量与编号；
- **循环创建数量对不上**：检查是否漏写 `if (pid == 0) break`；
- **父进程先退出后子进程怎么办**：子进程变成孤儿进程（第 4 章）；
- **查手册**：`man fork`；编辑器内光标停在函数上按 **Shift+K**、`q` 退出。

## 第 3 章 程序替换：exec 族

### 3.1 exec 的作用

exec 系列函数（以 **execl** 为代表）的作用是：**在进程身份信息（PCB、PID、父子关系）保持不变的情况下，替换进程要执行的任务代码**。

- 进程的任务数据存储在 0~3G 用户空间（堆、栈、代码段等）；execl 本质上就是对 0~3G 用户空间做一次**替换**，为进程建立全新的用户层，让进程"焕然一新"、拥有新任务；
- 与 fork 配合：fork（或 vfork）创建子进程 → 用 execl 替换其 0~3G——子进程不需要写功能代码，直接重载现成的程序即可；
- 父进程、子进程都可以执行重载，本文以"让子进程重载"为例。

**为什么用重载**（以"获取系统时间并输出"为例）：自己写要取时间种子（1970 年零点到现在的秒数）再换算年月日，还要处理中英文格式，需要好几行代码；而系统里本来就有现成的 `date` 命令——**命令本身也是程序**，让子进程直接重载 date，一行代码都不用写。同理，重载自己写的程序也行（如之前用正则写的匹配程序，子进程直接重载它去干活）。

### 3.2 execl 原型与参数

```c
int execl(const char *path, const char *arg, ... /* NULL */);
```

- 重载需要**目标程序的绝对路径**——函数按路径找到程序。用 `which` 命令查路径（如 `which date` 返回 /bin/date）；
- 参数列表：`argv[0]` 通常写命令/程序名本身，随后是 `argv[1]`、`argv[2]`……按需要的参数顺序逐个传入；
- **最后必须以 NULL 占位**：函数加载参数列表到 NULL 就认为结束；不传 NULL，调用会失败；
- 头文件：`#include <unistd.h>`；
- **失败返回 -1**（成功不返回），可据此做错误处理（如 `perror`）。

示例：

```c
execl("/bin/date", "date", NULL);            // 只有一个 argv[0]
execl("/bin/ls", "ls", "-l", NULL);          // argv[0]=ls、argv[1]=-l
```

> 注意：这里的"重载"与 C++ 中的函数重载没有关系，只是名字相近。

### 3.3 执行流程四步

1. **按路径找到程序**，访问其 **ELF 程序表头**（表头包含程序执行所需的数据信息，为加载做准备）；
2. **释放原有资源**：内核把当前子进程的 0~3G 用户层数据全部清空（堆、栈、代码段等释放干净——反正马上要被替换）；
3. **按程序表头申请新的 0~3G 空间并加载数据**：把目标程序的堆、栈、库等信息加载进去；
4. **收尾：重置命令行参数列表与程序入口**：新程序入口（`_start`）与旧的不一样，一并重置。

结果：进程身份信息不变（还是原来那个子进程），任务数据全部换成新程序的。

### 3.4 成功不返回与错误处理

- **若重载成功，execl 之后的原有代码永远不会执行**——正常情况下调用完就"交棒"了；
- 如果 execl 之后的代码还能打印出来，就说明**重载失败**；
- 失败返回 -1，用 `perror` 打印错误信息（如"没有那个文件或目录"）；
- **易错点**：子进程的自定义代码必须写在 **fork 之后、execl 之前**——execl 生效后旧代码全部被清空，写在后面就不起作用；
- 输出**务必加 `\n`**：Linux 下不回显刷新可能看不到输出（Windows 会自动刷新）。

### 3.5 实战：重载系统命令与自定义程序

**示例一：重载 date**

```c
#include <stdio.h>
#include <unistd.h>
#include <stdlib.h>
#include <sys/types.h>
#include <sys/stat.h>
#include <pthread.h>
#include <signal.h>

int main(void)
{
    pid_t pid;
    pid = fork();

    if (pid > 0)
    {
        printf("Parent %d alive\n", getpid());
        while (1);
    }
    else if (pid == 0)
    {
        printf("Child %d alive\n", getpid());        // 原稿 "Chile" 为拼写错误
        if (execl("/home/colin/test/process/while", "while", NULL) == -1)
            perror("execl call failed\n");           // 绝对路径按本机实际情况替换
    }
    else
    {
        perror("fork call failed\n");
    }

    return 0;
}
```

上面就是 `execl使用.c` 的内容：fork 出子进程后，子进程重载一个自定义程序（`while`）。被重载的 `while.c` 就是一个每秒打印一次的循环程序：

```c
#include <stdio.h>
#include <pthread.h>
#include <unistd.h>
#include <stdlib.h>

int main(void)
{
    while (1)
    {
        printf("Sleep 1 S\n");
        sleep(1);          // Linux 下 sleep 以秒为单位（Windows 以毫秒）
    }

    return 0;
}
```

运行效果：父进程打印并循环；子进程先打印自己的 pid，然后"变成"while 程序——屏幕上每秒输出一次 "Sleep 1 S"。**子进程 execl 之后的 printf 不再执行**，正是因为代码已被替换。

**示例二：重载 ls**：把参数改为 `execl("/bin/ls", "ls", "-l", NULL)`，同样成功。
**失败情形**：写一个不存在的路径——重载失败、返回 -1，perror 打印错误，execl 后面的代码继续执行。

**示例三：重载自定义程序（组件热更新）**

`mod/mod.c` 是"组件程序"（打印版本号）：

```c
#include <stdio.h>

int main()
{
    printf("V2.0\n");     // 组件升级时修改版本号并重新编译

    return 0;
}
```

`translate热更新演示.c` 是"主程序"——父进程循环创建子进程，子进程重载组件程序：

```c
#include <stdio.h>
#include <unistd.h>
#include <stdlib.h>

int main()
{
    pid_t pid;
    while (1)
    {
        sleep(1);
        pid = fork();
        if (pid > 0)
        {
            // 父进程：继续循环创建
        }
        else if (pid == 0)
        {
            if (execl("/home/colin/test/process/mod/mod", "mod", NULL) == -1)
                perror("execl call failed\n");    // 路径按本机实际情况替换
        }
        else
        {
            perror("fork call error\n");
        }
    }

    return 0;
}
```

操作流程：编译 mod 与主程序并运行（父进程持续创建子进程、子进程重载 mod）→ 输出 V2.0；**不动主程序**，直接修改 mod 代码（如升级 V3.0）重新编译 → 主程序新创建出的子进程执行的已是新版本。这就是**组件动态更新**的雏形。

### 3.6 应用：组件热更新

网站更新从来不停机（百度、淘宝从来不关站）——这叫**动态更新**：主程序不受影响，动态更新维护它的组件。用 exec 实现：

- 父进程 = 主程序；每个子进程 = 一个功能组件（天气查询、汇率查询、在线翻译、IP 查询……）；
- 子进程不写功能代码，而是分别**重载独立实现的功能程序**；
- 更新流程：开发者更新完组件代码 → 向运行中的父进程**发信号**（更新通知）→ 父进程检查该组件是否正被占用（被占用就暂缓）→ 空闲则退掉旧子进程、重新创建子进程并重载新版本——完成更新；
- 这样网站 7×24 小时运行，功能迭代始终发生在用户访问的空隙里。这类机制在网站领域一般称为 CI/CD（持续集成/持续部署的机制之一）。

> 上面的示例用"每秒创建一次子进程"来模拟触发更新；现实中更新完发一次通知即可。"通知"需要**信号**，信号尚未学习，所以未加入通知环节。

## 第 4 章 进程回收

### 4.1 为什么必须回收：僵尸进程

**产生过程**：子进程退出时，进程状态发生转变——**用户空间数据（0~3G）被全部释放，但内核空间的 PCB 保留未回收**，进程进入**僵尸态（状态标识 `Z`）**。

- 所有进程退出后都会经历这一状态，**无法避免**——不管是人为 `return 0`、调用 `exit(0)`，还是被其他进程杀死；
- 观察示例（`zombie.c`）：子进程 sleep 10 秒后退出，父进程不回收——10 秒前父子都是 S（睡眠）态，10 秒后子进程变为 Z（僵尸态），用 `ps` 肉眼可见。

**危害一：内存泄漏。** 进程退出时资源释放分两部分：用户空间全部释放（干净）；**内核空间 PCB 残留**、必然造成内存泄漏。对比 malloc 泄漏（一页内存不释放就一直被占用）——PCB 残留更严重：PCB 成员众多，有些成员还会额外申请内存，绝不止一页。

**危害二：占用 PCB，影响新进程创建。** 一个系统能创建的进程数量取决于 PCB 数量——假设最多支持 1000 个进程，已有 1000 个僵尸 PCB 残留，新进程就创建不出来（类比公司只有 10 个岗位，人不离职新人进不来）。所以僵尸进程要**早发现、早处理**。

**为什么系统不擅自释放 PCB？** 系统有能力释放，但没有"权利"——**父进程是第一责任人**。类比：孩子出意外去世，医院有处置能力，但必须等家属到场、不能擅自处理（更不能"毁尸灭迹"）——因为**父进程要给子进程"验尸"**：通过 PCB 中保留的退出信息了解子进程"怎么死的"。这引出了回收的两项工作：

1. **释放 PCB 内存**（处理内存泄漏）——必做；
2. **对子进程退出信息进行校验**（验尸）——可选。

> 真实案例（3Q 大战）：某安全软件不敢直接杀对手主程序，而是偷偷杀死它的某个核心服务进程，诱导用户提交崩溃报告；对手的反制是检测"是谁杀死了我的服务进程"，然后把相关子进程全部"托管"到对方程序上运行，导致对方 CPU 占用飙升。**如果无法校验子进程的退出信息，这样的反制根本设计不出来**——可见了解子进程退出原因很有必要。

**孤儿进程**：**父进程先退出**、子进程还未结束，子进程转变为**孤儿进程**（面试表述要规范："父进程退出，子进程转为孤儿进程"）。

### 4.2 wait：阻塞回收

```c
#include <sys/wait.h>       // 僵尸回收相关函数都在这个头文件里

int status;
pid_t zpid = wait(&status); // 阻塞回收
```

- **原型**：`pid_t wait(int *status)`；
- **阻塞特性**：子进程还活着就**阻塞等待**；子进程一退出立即回收——执行顺序由子进程的退出时机决定；
- **每次调用只回收一个僵尸**；多个子进程需要**循环回收**；
- **返回值**：成功返回被回收僵尸进程的 pid；失败返回 **-1**；
- **失败原因只有一个**：调用者**没有子进程**——没有子进程时必然失败；只要有子进程就不会失败（活着等、死了收）。
- **status 参数**：回收前 PCB 里保留一份 int 退出信息；不需要验尸就传 `NULL`（如上例未校验时可传 NULL）；要验尸则传入 `&status` 地址（见 4.4）。

配套示例（`zombie.c`）——循环创建 5 个子进程（第 i 个睡 i 秒后退出），父进程用循环 wait 全部回收：

```c
#include <stdio.h>
#include <unistd.h>
#include <stdlib.h>
#include <sys/wait.h>

int main(void)
{
    pid_t pid;
    int i;
    for (i = 0; i < 5; i++)
    {
        pid = fork();
        if (pid == 0)
            break;               // 子进程跳出循环
    }

    if (pid > 0)
    {
        pid_t zpid;
        while ((zpid = wait(NULL)) > 0)          // 循环回收：回收成功返回 >0
        {
            printf("parent wait sucess, zpid = %d\n", zpid);
        }
        while (1);                               // 卡住便于观察
    }
    else if (pid == 0)
    {
        printf("child i %d pid = %d\n", i, getpid());
        sleep(i);                                // 各子进程结束时间不同
        exit(0);
    }
    else
        perror("fork call failed\n");

    return 0;
}
```

运行观察：子进程陆续退出变成僵尸（Z），父进程每回收一个就打印一条记录，最终垃圾（僵尸）全部清空。

> 观察技巧：开两个终端——一个运行程序，另一个用 `ps` 观察状态变化。

### 4.3 waitpid：指定对象与非阻塞回收

`waitpid` 是回收的**升级版本**：不仅支持**非阻塞回收**，还能**指定回收方式**，比 wait 更灵活。

**为什么需要非阻塞回收？** 阻塞回收会让父进程"瘫痪"：子进程不退出，父进程就一直阻塞在回收函数上，自己的任务完全执行不了。**非阻塞模式（轮询回收）**是"尝试回收"：能回收就回收，不能就立即返回、去干别的，稍后再询问——父进程在**回收与自定义任务之间交替执行**。

```c
#include <sys/wait.h>

pid_t zpid = waitpid(pid_t pid, int *status, int options);
```

**参数一 `pid`：指定回收对象**

| 取值 | 含义 |
|---|---|
| `> 0` | 指定回收某一个子进程（传子进程 pid） |
| `-1` | 回收**任意一个**子进程（最方便、使用比例最高） |
| `0` | **同组回收**：回收与父进程同组的子进程（进程组是系统提供的组织结构，同组概念类比学校"系/级/班"） |
| `-pgid`（如 `-3000`） | **跨组回收**：回收 pgid 组内的（我的）子进程，值是该组 pgid 的相反数 |

**参数二 `status`**：接收子进程退出信息（验尸），不校验传 `NULL`。
**参数三 `options`**：`WNOHANG` 是**非阻塞关键字**（"no hang"：不希望挂起等待）——不加还是阻塞；加上即变为非阻塞。

**返回值（三种）**：`> 0` 回收成功（返回僵尸 pid）；`0` 非阻塞模式下当前没有可回收的子进程；`-1` 失败。

**非阻塞循环回收的标准写法**（配合自定义任务交替执行）：

```c
#include <unistd.h>
#include <sys/wait.h>
#include <stdio.h>
#include <stdlib.h>

void busines(void)
{
    printf("parent pid %d,exec busines..\n", getpid());
}

int main()
{
    pid_t pid;
    int i;
    for (i = 0; i < 3; i++)          // 创建 3 个子进程（分别睡 5、6、7 秒后退）
    {
        pid = fork();
        if (pid == 0)
            break;
    }

    if (pid > 0)
    {
        // 非阻塞循环回收，并执行自定义任务
        pid_t zpid;
        while ((zpid = waitpid(-1, NULL, WNOHANG)) != -1)
        {
            if (zpid > 0)
                printf("parent %d wait zombie sucess, zpid %d\n", getpid(), zpid);
            else
                busines();           // zpid == 0：暂无可回收，执行自定义任务
            sleep(1);                // 间隔 1 秒，让回收与任务交替
        }
    }
    else if (pid == 0)
    {
        sleep(i + 5);
        printf("child process pid %d, sleep %d exit\n", getpid(), i + 5);
        exit(0);
    }
    else
    {
        perror("fork call failed");
        exit(0);
    }

    return 0;
}
```

（以上即 `waitpid使用方法.c`。）

**逐点解读（易错重点）**：

- **循环条件用 `!= -1` 而不是 `> 0`**：非阻塞还会返回 0（暂时没有可回收的子进程），只写 `> 0` 就覆盖不到这种情况、也无法在等待间隙执行自定义任务；`!= -1` 把"回收成功"与"暂时没有"两种情况都覆盖，返回 -1（已无子进程可回收）时循环才结束；
- **`sleep(1)` 的作用**：不加延迟轮询频率过高、疯狂打印；加一秒间隔让"回收 ↔ 任务"交替执行；
- 运行效果：父进程在"询问—执行任务—睡眠"之间交替，子进程陆续退出被即时回收。

### 4.4 status 与退出信息检验

回收时可以对子进程的退出信息进行**读出与验证**（验尸）：

- **正常退出**：返回**退出码**（return / exit 的返回值）；
- **异常退出**：被某个**信号杀死**，可以解码出**信号编号**。

四个系统提供的判断/取值函数：

| 函数 | 作用 |
|---|---|
| `WIFEXITED(status)` | 判断是否**正常退出**（是返回真） |
| `WEXITSTATUS(status)` | 正常退出时取出**退出码/返回值** |
| `WIFSIGNALED(status)` | 判断是否**被信号杀死**（异常退出，是返回真） |
| `WTERMSIG(status)` | 异常退出时取出**信号编号** |

配套示例（`status.c`，含修正）：

```c
#include <unistd.h>
#include <sys/wait.h>
#include <stdio.h>
#include <stdlib.h>

int main(void)
{
    int i;
    pid_t pid;
    for (i = 0; i < 2; i++)          // 创建两个子进程
    {
        pid = fork();
        if (pid == 0)
            break;
    }

    if (pid > 0)
    {
        pid_t zpid;
        int status;
        while ((zpid = wait(&status)) > 0)       // 原稿误写为 wait(status)，缺 & 取地址
        {
            if (WIFEXITED(status))
                printf("parent wait sucess,child exitcode or return value = %d\n",
                       WEXITSTATUS(status));     // 原稿此处漏了取值的参数
            if (WIFSIGNALED(status))
                printf("parent wait sucess,kill child signal number %d\n",
                       WTERMSIG(status));        // 原稿误写为 WIERMSIG（拼写错误）
        }
    }
    else if (pid == 0)
    {
        if (i == 0)
        {
            sleep(i + 5);
            printf("child index %d pid %d,exit\n", i, getpid());
            exit(6);                             // 老大：5 秒后正常退出，退出码 6
        }
        else
        {
            while (1)                            // 老二：死循环，等待被信号杀死
            {
                printf("child index %d pid %d,while...\n", i, getpid());
                sleep(1);
            }
        }
    }
    else
    {
        perror("fork call failed");
    }

    return 0;
}
```

运行结果：老大 5 秒后正常退出，父进程解码打印退出码 **6**；老二仍运行，用 `ps aux` 查到它的 pid 后 `kill -11 <pid>` 将其杀死，父进程解码打印信号编号 **11**。

> 易错点：① `wait(status)` 少了取地址符，应写 `wait(&status)`；② `WIERMSIG` 是拼写错误，正确为 `WTERMSIG`；③ printf 有 `%d` 就必须给出对应参数。必要时可以封装自定义头文件（如 `check_child.h`）集中存放退出信息的校验代码。

### 4.5 信号与异常退出

- **结束进程必须用信号**：无论是程序杀程序、还是系统杀程序（Windows 任务管理器结束进程本质也是发信号），都通过信号完成——所以父进程能获取"是哪个信号杀的"；
- 常用操作：`ps aux` 查看进程 pid → `kill -9 <pid>`（强制杀死）或 `kill -11 <pid>`（11 号信号，用于异常退出解码）；
- 结合 4.4：被子进程信号杀死后，`WIFSIGNALED` 为真、`WTERMSIG` 给出信号编号。

### 4.6 循环回收与常见坑

- **批量回收就写"循环套 wait/waitpid"**，用返回值作循环条件：`while ((zpid = wait(NULL)) > 0)` 或 `while ((zpid = waitpid(-1, NULL, WNOHANG)) != -1)`；
- **坑一：循环条件写错**——只写 `> 0` 会漏掉非阻塞返回 0 的情况（无法在轮询间隙执行自定义任务）；
- **坑二：非阻塞回收让父进程提前退出**——父进程如果还有任务（如等待全部拷贝完成），非阻塞循环一旦"暂时没有可回收的子进程"就返回，处理不当会导致父进程先溜、任务没完成（该问题在 Process_copy 调试中真实踩坑，见 5.9）；
- **坑三：子进程踏出代码段执行 wait**——子进程自己并没有子进程，执行 wait 必然失败/出错，回收代码要写在父进程分支；
- **结论**：只要在 Linux/UNIX 上写进程程序，`wait`/`waitpid` 都是必用的——僵尸进程必然产生、必须回收。

## 第 5 章 多进程并发实战：Process_copy

### 5.1 需求与总体设计

**目标**：实现一个多进程拷贝程序（一个完整的多进程并发实例）——把源文件分块，用多个子进程**各拷一段**，提高拷贝速度。

**并发程序的优势与适用场景**：

- 优势一：多个执行相同任务的进程申请 CPU 资源，可以**得到更多时间片**、被调度的概率更大；
- 优势二：**并发利用率**——某个拷贝进程阻塞、放弃时间片时，时间片按"就近原则"交给相邻的同类进程继续执行，而不是给无关进程；
- 优势三：多核上**可能并行**——不同拷贝进程挂载到不同 CPU 同时执行，效率更高。

**不能盲目使用并发**：多进程会带来内存开销与调度开销。例如**下载**环节受带宽限制（100M 带宽跑满约 10MB/s，开 10 个进程也不会变快）；但下载的**落盘**环节分块多进程写盘可以更快——所以要不要并发，取决于具体任务与场景；**小文件单进程足够，大文件才体现价值**。

**运行形式与参数约定**（编译产物为 ELF 可执行文件 `Process_copy`）：

```bash
./Process_copy <源文件> <目标文件> [进程数]
```

- 前两个参数必传；第三个参数**pronum（进程数量）可缺省，默认值为 3**；
- 进程数取值范围 **3~100**，不允许乱传（如 3000 万）；
- 示例：`./Process_copy 1.png 2.png 5`。

**处理流程**：接收命令行参数 → 判断 pronum 缺省 → 参数验证 → 按文件大小**切片**（算每个进程的任务量与偏移）→ 循环 fork 创建子进程、各自 exec 加载拷贝程序 → 父进程循环回收全部子进程。

### 5.2 模块划分与接口设计

工程模块化拆分（不要把代码都写在一个文件里）：

int main(int argc, char *argv[])

### 5.3 参数校验：check_pram

用户完全可能瞎传（源文件不存在、进程数传 3000 万），所以必须校验参数。**三项校验，任一失败即退出程序**：

```c
#include "process_copy.h"

// 参数验证
int check_pram(int argc, const char *srcfile, int pronum)
{
    if (argc < 3)                       // ① 参数数量：少于源文件+目标文件
    {
        printf("参数错误\n");
        return 0;
    }
    if (access(srcfile, F_OK) == -1)    // ② 源文件是否存在（access 比 open 简洁）
    {
        printf("文件不存在\n");
        return 0;
    }
    if (pronum < 3 || pronum > 100)     // ③ 进程数范围 3~100
    {
        printf("进程数错误\n");
        return 0;
    }

    return 1;
}
```

- 判断源文件存在性：用 `access(文件名, F_OK)`——存在返回 0，不等于 0 表示不存在，比 `open` 再处理返回值更简单；
- 三项全部通过才返回 1，主程序才会继续执行。

### 5.4 分块计算：block_cur

```c
#include "process_copy.h"

// 切片
int block_cur(const char *srcfile, int pronum)
{
    struct stat st;
    stat(srcfile, &st);                 // 取文件大小
    int filesize = st.st_size;
    if (filesize % pronum == 0)         // 能整除：直接分
        return filesize / pronum;
    return (filesize / pronum) + 1;     // 不能整除：商 + 1，每个进程多分一点
}
```

**为什么要切块**：类比施工——100 米路段交给 5 个工人，先算每人干多大（每人 20 米），再分配各自的起点（0~20、20~40……）；位置都一样就会重复干活、有的路段没人干。大数据处理同理：30G 文件不可能一次读进缓冲区，只能切片处理。

**余数处理**：数据最小单位是**字节**；除不尽的余数一定小于进程数（5 个进程最多余 4 字节）。本程序采用"每个进程多分 1 字节"的方案——前几个进程多拷一个字节就把余数覆盖完，后面的进程读空写空也无妨（多写的数据会被后续进程覆盖）；另一种方案（单独建一个进程处理余数）未采用。

### 5.5 进程创建与任务分配：process_create

```c
#include "process_copy.h"

// 创建子进程
int process_create(const char *srcfile, const char *destfile, int pronum, int blocksize)
{
    int i;
    pid_t pid;
    char str_offset[100];
    char str_blocksize[100];

    for (i = 0; i < pronum; i++)        // 循环创建 pronum 个子进程
    {
        pid = fork();
        if (pid == 0)
            break;                      // 子进程跳出循环
    }

    if (pid > 0)
        process_wait();                 // 父进程：循环回收
    else if (pid == 0)
    {
        sprintf(str_offset, "%d", i * blocksize);       // 偏移量 = i × blocksize
        sprintf(str_blocksize, "%d", blocksize);        // 整型转字符串
        execl("/home/ubuntu/projects/process_copy/MOD/copy",   // 路径按本机实际调整
              "copy", srcfile, destfile, str_offset, str_blocksize, NULL);
        exit(0);
    }
    else
        return 0;

    return 1;
}
```

要点：

- **偏移量 = i × blocksize**：每个子进程的 i 独立（0、1、2……），例如 100 字节文件、5 进程、每块 20 字节，偏移量分别是 0、20、40、60、80——各段不重不漏；
- **整型转字符串**：外挂程序从命令行接收的都是字符串，偏移与块大小是整型，必须用 `sprintf` 转进字符数组后传参；
- **execl 传参**：可执行文件绝对路径、"copy"（argv[0]）、源文件、目标文件、偏移字符串、块大小字符串，**末尾 NULL**；
- 子进程执行完 `exit(0)`；父进程调用 `process_wait()` 回收（父进程自己不拷贝）。

### 5.6 复制子程序：MOD/copy

真正干"拷贝"活的是外挂程序 `MOD/copy.c`（由各子进程 execl 加载）：

```c
#include <stdio.h>
#include <unistd.h>
#include <stdlib.h>
#include <string.h>
#include <sys/types.h>
#include <sys/stat.h>
#include <sys/fcntl.h>

int main(int argc, char *argv[])
{
    int sfd;                                    // 源文件描述符
    int dfd;                                    // 目标文件描述符
    int offset = atoi(argv[3]);                 // 偏移量
    int blocksize = atoi(argv[4]);              // 块大小

    if ((sfd = open(argv[1], O_RDONLY)) == -1)              // 打开源文件（只读）
        perror("open srcfile,failed");
    if ((dfd = open(argv[2], O_WRONLY | O_CREAT, 0664)) == -1)  // 打开/创建目标文件
        perror("open destfile,failed");

    // 跳转偏移量：源文件、目标文件都要偏移
    lseek(sfd, offset, SEEK_SET);
    lseek(dfd, offset, SEEK_SET);

    char buffer[blocksize];
    int len;
    printf("child p %d execl Copy,offect %d,blocksize %d\n", getpid(), offset, blocksize);

    // 读写操作
    len = read(sfd, buffer, sizeof(buffer));
    write(dfd, buffer, len);
    close(sfd);
    close(dfd);

    return 0;
}
```

要点与易错：

- 参数依次是：源文件、目标文件、偏移量、块大小；两个文件都用 `lseek` 偏移到指定位置后再读写（各进程分工完成各自的片段）；
- **write 的数据量必须用 `read` 的返回值**（读多少写多少）——**绝不能用 strlen**（strlen 按字符串规则统计、遇到 `'\0'` 就截断，用于二进制数据会少算，详见 5.9）；
- `read` 不保证一次读满（可能被中断读少），严格实现应**循环续读**直到读满（见 5.9）；
- open 的返回值判断要用 `==`（两个等号）；缓冲区按块大小声明即可。

### 5.7 进程回收：process_wait

```c
#include "process_copy.h"

// 父进程循环回收
void process_wait(void)
{
    pid_t pid;
    while ((pid = waitpid(-1, NULL, WNOHANG)) != -1)
    {
        if (pid > 0)
            printf("子进程%d已回收\n", pid);
    }
}
```

- 父进程自己没有拷贝任务，职责就是**等所有子进程干完并回收干净**——多进程模型必须回收，僵尸进程一定要管；
- **回收方式的选择（重要）**：上面是非阻塞轮询写法；本项目父进程的唯一职责就是等子进程，**用阻塞回收最简单、最可靠**——实际调试中正是把非阻塞改回阻塞才解决了"父进程提前退出、拷贝不完整"的问题（配合循环回收全部子进程）；非阻塞回收适合"父进程自己有任务要干"的场景。

### 5.8 编译、运行与验收

**编译**（两步，先编外挂、再编主程序）：

```bash
gcc copy.c -o copy                      # 先编译拷贝子程序（生成 MOD/copy）
gcc source/*.c -I include -o Process_copy   # 再编译主程序（-I 指定头文件目录）
```

> 编译命令形如 `gcc *.c -g -I./include -o Process_copy`：`-g` 加入调试信息、`-Wall` 打开严格警告（不规范的写法会被直接报出来，借它排查问题）；**修改代码后必须重新编译**，否则运行的还是旧程序。工程 README 中记录的编译命令：

```bash
gcc source/*.c -I include -o Process_copy
gcc MOD/copy.c -o MOD/copy
```

**运行**：

```bash
./Process_copy <源文件> <目标文件> [进程数]
# 进程数可选，默认 3，取值 3~100
# 例：./Process_copy file1.txt file2.txt 5
```

**验收标准**：

- 拷贝完成后**目标文件字节数与源文件完全一致**；
- **图片能正常打开**（修复前 720 万字节只拷到 640 多万，图片只显示一半或打不开）；
- 文档、压缩包、音频等任何类型（按字节的数据流）都能完整拷贝；
- 建议分别用文本、图片、压缩包，以及 10 个、20 个进程等多种组合测试。

> 工程中的编译产物：`Process_copy`（主程序）、`MOD/copy`（拷贝子程序）都是 ELF 可执行文件；`mod/mod`（32 位 ELF）是前面组件热更新示例中所用的组件程序。`README.md` 是工程自述文档，记录了项目结构、编译命令、使用方式与工作原理（本节的编译与使用部分即来源于它）。

### 5.9 调试记录与问题分析

实际开发调试中踩到的问题及修正（每一条都是真实教训）：

**① 非阻塞回收导致父进程提前退出、拷贝不完整**

- 现象：父进程用 `WNOHANG` 非阻塞循环回收——这一轮没回收到（子进程还在拷），父进程就退出，拷贝不完整；
- 修正：改回**阻塞回收**（`waitpid` 去掉 WNOHANG，循环收全）。适用场景区分：父进程有自己任务 → 非阻塞轮询；父进程职责就是等子进程 → 阻塞回收。

**② 切片计算错误（数据量为 0）**

- 现象：打印出的块大小是 0；
- 排查：参数验证没问题 → 定位到切片模块；
- 原因：赋值写成了条件判断；"不能整除"的处理写错（正确是"商 + 1"）；
- 修正后：10 个进程、720 万字节文件，每个子进程分到约 72 万字节，偏移量 0、72 万、144 万……

**③ 二进制数据拷坏图片：strlen 不能算 write 的数据量**

- 现象：720 万字节的图片只拷了 640 多万——图片显示一半或打不开；
- 原因：write 的数据量用 **strlen** 计算——strlen 按字符串规则（遇到 `'\0'` 截断）统计，用于二进制数据会偏小；
- 修正：**用 read 的返回值作为 write 的数据量**——"读多大数据、写多大"；
- 口诀：**永远用 read 的返回值作为 write 的数据量**。

**④ read 不保证一次读满**

- read 可能因中断等原因提前返回（请求 1M 只读到 10K 也可能）；"默认一次读满"是不严谨的；
- 标准做法：**判断返回值是否小于请求大小，小于就循环续读**，直到读满；write 用本次实际读到的字节数。

**⑤ execl 的路径与传参问题**

- 加载的必须是**编译后的可执行文件**（不能指向 .c 源文件）；
- 路径要**拼接完整**（加 `./` 前缀或写绝对路径）；
- 验证方法：在 copy.c 里加一句打印，**能打印说明加载成功**；"压根没有输出"基本可断定加载失败——要么路径不对、要么参数不对。

**⑥ 其他要点**：打印 argv[1]~argv[4] 逐一核对传参；open 的返回值判断用 `==`；注意循环变量作用域；程序卡死时用打印定位卡在哪一段；改完代码先重新编译再运行——按模块逐层排查（参数验证 → 切片 → 加载与传参）。

## 第 6 章 make 与 makefile

### 6.1 make 的作用与执行原理

**make** 是工程管理与自动编译工具，配合 makefile 使用。核心价值：**只重新编译改动过的文件**——未改动的 `.o` 直接复用，最后一起链接。

- 类比公司组织：大老板做调度——谁改动了重新处理谁，没动的用现成的；
- 规模效应：塞班（Symbian）系统当年在普通电脑上编译要两三天、开发机上也要八九个小时，用 makefile 增量编译后可缩短到二十多分钟；小项目看不出优势，**工程一大非常明显**；
- 一次编写终身受用：makefile 写好后基本通用，换工程稍微改一改即可。

**编译三步本质**：`.c` 源码 →（编译）`.o` 可重定位二进制目标文件 →（链接）可执行程序。

**依赖的建立与执行**：

- **自顶向下建立依赖**：从最终目标开始分析——它需要哪些 `.o`，`.o` 又由哪些 `.c` 生成（先看"答案"再倒推"过程"）；
- **自底向上执行**：先把所有 `.c` 编译成 `.o`，最后链接生成可执行文件；
- 命令的执行顺序由依赖关系决定，而不是按 makefile 里书写的先后顺序。

### 6.2 makefile 基本语法

三要素：**目标、依赖、命令**（规则写作"目标: 依赖"，下一行写命令）。工程里的编译型 makefile（`source/makefile`）：

```makefile
TARGET=process_copy
INCLUDE_PATH=../include/
LIBRARY_PATH=

SRCFILE=$(wildcard *.c)                        # 取出当前目录所有 .c
DESTFILE=$(patsubst %.c,%.o,$(SRCFILE))        # 模式替换：.c → .o
CFLAGS=-I$(INCLUDE_PATH) -g -Wall              # -I 头文件路径、-g 调试信息、-Wall 严格警告
CC=gcc

$(TARGET):$(DESTFILE)                          # 目标程序依赖所有 .o
	$(CC) $^ -o $@                             # 链接（$^ 全部依赖、$@ 目标）

%.o:%.c                                        # 静态模式规则：每个 .c 编译成 .o
	$(CC) $(CFLAGS) -c $<
```

要点：

- **变量**：`TARGET`（最终程序名）、`CC`（编译器）、`CFLAGS`（编译选项）；引用变量必须写 `$(变量名)`；
- **两个内置函数**：`wildcard` 把所有 `.c` 文件名取出存到变量；`patsubst` 做模式替换（a.c b.c → a.o b.o）；
- **静态模式规则** `%.o: %.c`：自动为每个 `.c` 匹配生成对应的 `.o`；命令里 `-c` 后面带上 `$(CFLAGS)`（含 -I 头文件路径）；
- **自动变量**：`$@` 表示目标、`$^` 表示所有依赖、`$<` 表示依赖中的第一个；
- **命令前必须用 Tab 缩进**（不能用空格）；
- 执行 `make`：先编译各 `.c` 生成 `.o`，再链接；改一个文件再 make，只重编那一个文件，新 `.o` 与老 `.o` 一起链接。

### 6.3 多目录与工程组织

多模块工程一般写两个版本：

- **编译型 makefile**：放在具体工程目录（如 `source/`），负责真正的编译链接；
- **调度管理型 makefile**：放在上层，不负责编译，负责"跳转与执行"——用 `make -C ./子目录` 跳转到指定目录执行那里的 makefile。

工程根目录的 makefile（`install:source` 模式）：

```makefile
install:source
	make -C ./source
```

场景：一个工程有多个子目录、要生成不同程序时，不必每次逐个手动进入编译——在管理型 makefile 里多写几条 `make -C` 指令，一条 make 就能把各子目录依次编译完成。

## 第 7 章 进程间通信：管道

到这里，进程部分从"单个进程"讲到了"多个进程协同"——**多进程模型中，需要在多个进程间传递同步消息，这类技术统称进程间通信（IPC）**。本章讲其中最经典、也是最基础的一类：**管道**（匿名管道与命名管道）。

### 7.1 进程间通信（IPC）概述

**IPC** 是进程间通信技术（Inter-Process Communication）的英文缩写，用于在多个进程之间传递消息。

> 类比红绿灯：多个方向的车道靠红绿灯调度配合、有序通行——红绿灯之间的信息需要同步（不能全红或全绿）；进程之间也一样，多个进程完成某个任务时，需要数据信息在进程间传递、同步和收发。

进程间通信技术种类很多：

| 技术 | 说明 |
|---|---|
| 管道 | pipe（匿名管道）、fifo（有名管道） |
| 消息队列 | 经典的两套：systemV、posix |
| 信号 | 也能实现进程间通信 |
| socket 编程 | 网络通信也是进程间通信（QQ、微信都是进程） |
| mmap 内存映射 | 共享内存方式实现通信 |

**本阶段主要讲**：pipe、fifo、mmap 三种；**信号是独立章节**——需要先讲完信号基础，才能教如何用信号实现进程间通信。

### 7.2 管道的基本特征

先不考虑计算机里的管道，想想生活中的排水管道、通风管道，它们的共同特征：

| 特征 | 说明 |
|---|---|
| 传输介质 | 管道一般是空心的容器——是一种传输介质 |
| 方向性 | 使用传输介质需要指定方向（马桶冲水不会从地漏喷上来） |
| 临时存储 | 可以暂存（嘴里咬住吸管、手指堵住另一头，饮料暂存在管内），无法持久化存储数据 |
| 数据结构 | 环形队列——通信类技术多用队列实现（先进先出、有实时性） |

**为什么用队列**：通信类技术讲究实时性与时效性、数据先进先出，所以很多通信技术都用队列实现；队列又分线性队列与环形队列——**环形队列循环访问，访问的都是申请分配的有效空间，有效避免了线性队列的越界问题（碰野地址）**。

**管道的大小**：**4096 字节（4K）**。不同 Linux 版本管道大小可能不同——这是经典面试细节：

> 面试场景：面试官问"管道多大？"，同学答 4K，面试官说"不对，再想想"。其实两个人都没错——课程环境 Ubuntu 16.04 及之后版本管道是 4K；老版本 Ubuntu 14.04 是 16K（早期系统使用大内存页，页大小可能是 8K、16K）。以后被问到这类问题，要先说明系统版本再给答案，避免版本差异带来的乌龙。

**为什么管道创建在内核层**：几乎所有的进程间通信技术都是**在内核层完成**的，因为**内核层是内存共享**（所有进程的内核数据在一块共享区域）；而**用户层是独立内存**——用户层定义的数据资源，其他进程是无法访问的（你在自己进程的堆/栈里声明变量，别的进程看不到——管道建在用户层就不可能共享）。

### 7.3 匿名管道 pipe

**什么是匿名管道**：创建后直接可以使用、访问管道完成进程间通信，**无需为管道命名**。

**创建与使用**：

```c
#include <unistd.h>

int fds[2];
pipe(fds);        // 匿名管道创建
fork();           // 亲缘进程使用：先创建管道，再创建子进程
// 创建成功后，使用 fds[0] 或 fds[1] 进行数据收发，
// fds 数组中存储管道的访问描述符，后续用 read / write 读写管道数据
read(fds[0], buffer, sizeof(buffer));      // 读取管道数据
write(fds[1], buffer, strlen(buffer));     // 写管道数据
```

- `pipe(fds)` 传入一个**长度为 2 的整型数组**，内核创建一条管道（4K 环形队列），并生成**两个指向管道两端的描述符**：`fds[0]` 是**读端**（用它 read 读数据）、`fds[1]` 是**写端**（用它 write 写数据）；
- 管道**创建者**持有这两个描述符；另一个进程怎么拿到？——**继承**。fork 时子进程拷贝父进程的描述符表，于是不需要重新创建管道就能拿到同样的两个描述符；
- 所以顺序必须是：**先 pipe、再 fork**。如果先 fork 再 pipe，父子各创建各的管道，就是两条管道各玩各的，无法通信。

**匿名管道的局限**：只能完成**亲缘进程间**的通信——父子、爷爷孙子都可以（描述符一辈一辈传下去），但**两个没有亲缘关系的进程用不了**。

> 匿名管道靠"继承"工作，没有继承关系描述符就传不过去——这是它最大的弊端，也引出了后面的命名管道。

### 7.4 匿名管道示例

`pipe.c`——父进程写、子进程读：

```c
#include<unistd.h>
#include<stdio.h>
#include<stdlib.h>
#include<string.h>

#define msg "hi son can you hear me?"

int main(void)
{
	pid_t pid;
	int fds[2];
	pipe(fds);
	pid = fork();

	if(pid > 0)
	{
		write(fds[1],msg,strlen(msg));
		printf("parent pid %d.write success\n",getpid());
		while(1)
			sleep(1);
	}
	else if(pid == 0)
	{
		char buffer[1024];
		bzero(buffer,sizeof(buffer));
		read(fds[0],buffer,sizeof(buffer));
		printf("child pid %d.buffer = \"%s\"\n",getpid(),buffer);
	}
	else
		perror("fork call failed");

	return 0;	
}
```

编译运行：`gcc pipe.c -o app`，`./app`。现象：父进程打印 `parent pid xxx.write success`，子进程打印 `child pid xxx.buffer = "hi son can you hear me?"`（读到了父亲发的消息）。

要点与观察：

- 消息内容由 `#define msg "hi son can you hear me?"` 定义，写入长度用 `strlen(msg)`；
- 子进程读之前用 `bzero(buffer, sizeof(buffer))` 清空缓冲区；
- 父进程写完消息后 `while(1) sleep(1)` **不退出**，子进程读完后正常退出——子进程退出后、父进程不回收就会成为僵尸（回看第 4 章）；实际项目里父进程要配合 wait/waitpid 回收。

**确定通信方向的标准写法**（完整版）——父写子读，配合 close 确定方向 + wait 回收：

```c
#include <unistd.h>

int main(void)
{
    int fds[2];
    pipe(fds);
    fork();
    // 父写子读
    if (pid > 0){
        close(fds[0]);
        父进程写操作
        close(fds[1]);
        wait(NULL);    // 僵尸回收
    } else if (pid == 0){
        close(fds[1]);
        子进程读取数据
        close(fds[0]);
        exit(0);
    } else {
        perror("failed");
    }
}
```

- 父进程一上来 `close(fds[0])`——不要读端，丧失读能力；写完 `close(fds[1])` 彻底关闭；`wait(NULL)` 回收子进程；
- 子进程一上来 `close(fds[1])`——不要写端，丧失写能力；读完 `close(fds[0])`；`exit(0)` 退出；
- 两个进程一共 4 个描述符，用完后全都要 close（原因见 7.5 的引用计数）。

### 7.5 通信方向与传输模式

通信类技术（管道、消息队列、网络编程）都涉及**传输模式**，分三种：

| 模式 | 含义 | 举例 |
|---|---|---|
| 单工传输 | 指定通信方向，进程非读即写，**确定后任何时刻不可变更** | 父写子读 / 子写父读 二选一；单行道 |
| 半双工传输（可变单工） | **不同时刻**可以在读、写之间切换，但**一个时刻内**非读即写 | 这一刻 A 写 B 读，下一刻 A 读 B 写 |
| 双工传输 | 任意时刻支持**同时读写** | 网络的上行与下行同时跑（上传与下载同时进行） |

- 管道**不支持双工**——只考虑单工与半双工；
- 单工比半双工**更安全、更简单**：半双工控制不好会产生数据冲突（两人同时写、两人同时读、自己读自己写等读写异常）；
- 实际使用中**单工更常见**：确定通信方向后谁读谁写一目了然。

**确定通信方向不是口头约定，而是实际操作**：需要 `close(fds)` 让进程**丧失部分读写能力**——

- 父写子读：父进程 close(fds[0])（不要读端）、子进程 close(fds[1])（不要写端）；
- 不 close 的话，进程同时具备读写能力，模式就成了半双工。

**管道何时释放（引用计数机制）**：

- 每有一个描述符指向管道，管道的**引用计数 +1**；`close()` 使引用计数 -1；**引用计数为 0 时，系统自动释放管道队列**（4K 环形队列的内存）；
- 前面父写子读两人共 4 个描述符（父子各持读端+写端），引用计数为 4——最先两次 close 是"确定通信方向"，最后两次 close 是"用完后彻底关闭"，4 次 close 后计数归零、系统释放管道；
- **多进程模式下使用 pipe 一定要 close，避免内存泄漏**——哪怕漏掉一次，管道都会一直驻留在内存中；
- `shutdown()` 可以让引用计数**直接归 0**（一次清零）——**一定要最后使用**：一旦调用，所有进程的管道全部失效，必须确保管道确实用完了，避免管道提前被释放。

### 7.6 四种特殊情况

匿名管道使用时有四种特殊情况——它们**具有普遍意义**：消息队列、socket 编程中都能看到这四种情况的影子，网络编程中的很多异常都能对号入座：

| 情况 | 现象 | 说明 |
|---|---|---|
| 读阻塞 | 读取管道时管道为空 → 读端阻塞 | 等待写端写入数据 |
| 写阻塞 | 向管道写数据时管道已满 → 写端阻塞 | 等待读端取走数据 |
| 写关闭 | 写端关闭，读端读完管道剩余数据后，再次 read 返回 0 | 返回 0 表示写端进程异常关闭、管道里也没数据了——看到 read 返回 0，要意识到"写端死了" |
| 读关闭 | 读端关闭后，系统不允许任何进程再向管道写数据；写则向进程发送 **SIGPIPE 信号**（管道信号），杀死进程 | 没人会读的数据是垃圾数据，系统直接介入 |

> 网络编程延伸：客户端发送请求后异常退出，服务端处理完请求发送结果时，对端已经关闭——服务端写入触发 SIGPIPE、被判"管道异常"杀死。以前用 `send(sockfd, buf, size)` 收发消息其实是不安全的写法，标准做法是加 `MSG_NOSIGNAL` 选项：`send(sockfd, buf, size, MSG_NOSIGNAL)`——发送网络数据时忽略信号，避免被 SIGPIPE 杀死。管道是很多通信技术的"原型"（最早的通信技术之一），它的四种情况在消息队列、socket 里都能找到对应。

### 7.7 优缺点

**优点**：

- 使用简单；
- 系统开销比较小（内存资源）——底层用队列，不像一些技术要用树、图这类复杂结构；
- 传输效率较高（先进先出，有实时性）。

**缺点**：

- 匿名管道只能完成亲缘进程的通信；
- **默认管道传输的是无格式字节流，需要用户自行封装**——直接发字符串，读的那边不好读（长度不好把握：读长了好办、读短了没法办）；通信时一般把数据打成**消息包**（消息类型 + 消息数据，比如消息编号 123 + 数据内容）再发送。

> 对比消息队列：消息队列提供了现成的结构体，把信息放进结构体即可；管道没有现成的消息包，需要用户自己定义协议、自己封装——用起来麻烦一些，这是设计使然。

### 7.8 命名管道 fifo 概述

**有什么不同**：匿名管道靠继承、只有亲缘进程能用；**命名管道**（有名管道 fifo）不依赖继承——**需要用户先创建管道文件**，文件类型是 **p（设备文件）**，然后开发者像打开普通文件一样打开管道文件，多个进程就可以通信收发消息。

创建管道文件后，`ls -l` 看第一位十位码：第一位是 **p** 就是管道文件（普通文件是 `-`）；而且管道文件的颜色也不同（一般高亮显示）。

**管道文件不能存储、不能编辑**：用 vim 打开管道文件是黑屏，无法编辑、无法正常保存退出（只能强制关掉终端）；想往里面写东西也写不了——**管道文件不分配磁盘扇区**（分配扇区数为 0）。对比普通文件：按块分配扇区（一个块 8 个扇区、一扇区 512 字节，默认 4K）；管道文件一个扇区都不分，自然存不了数据。

**为什么不用普通文件通信**：普通文件确实能实现通信效果（一个进程写、另一个进程读），但很少有人用：

1. **读写速度慢**——数据实体化到磁盘，磁盘寻道特别慢（内存读写快得多）；
2. **数据是持久化存储**——先进先出的数据读完就该没了，但磁盘文件里写了"你好"，别人读走后"你好"还在，其他人还能看到，不适合通信场景。

**创建管道文件的目的**：让系统中的**所有进程都能查看访问此文件**——打开这个文件后，指向的**不是磁盘空间，而是管道队列（4K）**。文件成了一种"共享入口"：所有进程打开它、拿到的都是同一条 4K 管道队列，从而让**不相干（无亲缘）的进程**也能用管道通信。

> 一句话：命名管道的管道文件是"门牌号"，真正住人的还是内核里那条 4K 环形队列。

### 7.9 命名管道的基本使用

**创建管道文件的两种方式**：

```bash
mkfifo Name      # 终端命令创建（后面跟管道名）
```

```c
mkfifo(char *Name, 0664);    // 函数创建管道文件（第一个参数管道名，第二个参数权限）
```

**基本步骤**：创建管道文件 → 多个进程打开管道文件 → 确定通信方向 → 读写即可。

写端 `write.c`：

```c
#include<unistd.h>
#include<sys/types.h>
#include<sys/stat.h>
#include<fcntl.h>
#include<stdio.h>
#include<stdlib.h>
#include<string.h>

int main()
{
	mkfifo("FIFO",0664);

	int fd;
	fd = open("FIFO",O_WRONLY);
	char *msg = "908129083908123\n";
	write(fd,msg,strlen(msg));
	close(fd);
	
	return 0;
}
```

读端 `read.c`：

```c
#include<unistd.h>
#include<sys/types.h>
#include<sys/stat.h>
#include<fcntl.h>
#include<stdio.h>
#include<stdlib.h>
#include<string.h> 

int main(void)
{
	int fd;
	fd = open("FIFO",O_RDONLY);
	char buffer[4096];
	bzero(buffer,sizeof(buffer));
	read(fd,buffer,sizeof(buffer));
	printf("%s\n",buffer);
	close(fd);

	unlink("FIFO");

	return 0;	
}   
```

编译与运行：

```bash
gcc write.c -o wr
gcc read.c -o rd
# 打开两个终端：先执行 ./wr，再执行 ./rd
```

运行现象：先执行 `./wr` 时它**卡住不动**（只有写端权限，open 在等待读权限），在另一个终端执行 `./rd` 后，wr 立即写数据退出、rd 打印出写入的消息——一次经典的命名管道通信完成。

要点：

- 写端代码里用 **mkfifo 创建管道文件**，再 open 打开、write 写入、close 关闭；
- 读端只 open（管道文件已由写端创建）、read 读出、printf 打印、close 关闭；缓冲区 4096 与管道大小保持一致；
- **读端使用完毕后 unlink("FIFO") 删除管道文件**——管道文件由谁创建、由谁（使用完后）删除，一般让读端负责收尾（删除方式和删除系统普通文件一样）；
- 命名管道**没有任何亲缘限制**——不管是父子、还是不认识的进程，只要能访问到管道文件就能打开通信。

### 7.10 命名管道使用时的特殊情况

**特殊情况一：打开权限——必须凑齐 RDWR**

想要成功打开管道文件，必须**单进程或多个进程满足 RDWR 两个访问权限**：如果只是使用 O_RDONLY 访问，会在 **open 函数阻塞**，等待另一个权限；同样只写 O_WRONLY 也会在 open 阻塞。

> 类比金库双钥匙：电影里金库要两把钥匙同时插入才能开门——open 打开管道文件也一样，读权限、写权限两把"钥匙"凑齐才能打开。7.9 的运行现象就是这样来的：单独跑 ./wr 时只有写权限一把钥匙，open 阻塞在那里等读权限。

- 单进程用 O_RDWR 满足 RDWR 权限**也可以打开管道**，但一般管道都是多进程访问通信的，单进程自己写自己读没有意义；
- 一般使用管道文件都是多进程 + 确定通信方向（一个人写、另一个人读）。

**特殊情况二：多读序列**

一个进程中有多个读序列（多个执行单元读同一个管道），**只有第一个读序列是阻塞读，其他读序列系统设置成非阻塞**：

- 无论写多少行 read 还是一个循环 read，串行执行都只算**一个**执行序列；**多个执行单元（多线程）同时读取，称为多读序列**；
- 只需要安排**一个线程阻塞等待管道数据**即可；其他线程非阻塞读取，无数据立即返回、执行其他任务——避免进程中所有的执行单元全部阻塞、导致进程卡死。

> 类比医院挂号：同一位专家的号开了 4 个窗口，家里去 4 个人一人排一队，谁先排到拿一个号即可，其他人可以去干别的——因为最终只需拿到一个号；进程里也一样，数据只被读一次，没必要 5 个线程都死等。

## 第 8 章 进程间通信：内存映射 mmap

上一章的管道靠"队列"传递数据，本章的 **mmap** 换了一种思路：把文件数据映射到一块共享内存里，多个进程直接"看"同一块内存。它既是大文件处理的主流手法，也是五大类进程间通信技术之一。

### 8.1 概述

**mmap（memory map）** 是一种内存映射技术，准确的叫法是**文件映射**：

- 主要作用：**共享内存**——可以将文件的数据映射到一块内存中，这块内存可以被多个进程共享，实现进程间共享数据的效果；
- 与管道不同：管道是**队列**，通过入队出队的方式读写数据；mmap 是**将数据写入共享内存、其他人查看**——一个进程往映射内存里写"你好"，另一个进程映射同一块内存就能看到；
- **文件映射技术主要做文件处理**：处理一个 200 兆的文件，传统做法是 open+read 一点一点读进缓冲区、一点一点处理，效率较低；映射做法是把文件直接映射到内存中处理，效率更高。所以 mmap 的主业是文件处理；
- **完成 IPC 进程通信是它的附加功能**——但它确实能实现通信（写内存对方可见），本小节按通信的用法使用它。

### 8.2 mmap 函数原型与参数

```c
#include <sys/mman.h>

void *ptr = mmap(NULL, size, PROT_READ | PROT_WRITE, MAP_SHARED, fd, offset);
```

**返回值**：成功返回**映射内存首地址**；失败返回关键字 **MAP_FAILED**——错误处理判断 `ptr == MAP_FAILED` 即可。

**六个参数**（目前参数比较多的一个函数）：

| 参数 | 含义 | 说明 |
|---|---|---|
| `addr` | 映射内存地址 | 可以先用 malloc 申请一块堆区空间、把地址传进来指定映射位置；**传 NULL** 表示系统默认在进程堆栈之间的**映射内存（库空间）**位置分配空间 |
| `length` | 映射大小 | 一般传入映射文件的大小 |
| `prot` | 映射内存权限 | PROT_READ / PROT_WRITE / PROT_EXEC / PROT_NONE，可组合 |
| `flags` | 映射方式 | MAP_SHARED（共享映射）与 MAP_PRIVATE（私有映射）**二选一** |
| `fd` | 映射文件描述符 | 通过 open 打开映射文件得到 |
| `offset` | 映射的偏移量 | 不偏移传 0 |

### 8.3 私有映射与共享映射

| 映射方式 | 机制 | 特点 |
|---|---|---|
| `MAP_PRIVATE` 私有映射 | **拷贝映射**：将映射文件的数据拷贝一份到映射内存 | 两份数据互不干涉——改文件不影响内存、改内存不影响文件 |
| `MAP_SHARED` 共享映射 | **同步机制**：映射文件与映射内存的数据实时保持一致 | 修改映射内存的数据会（通过 sync 同步机制）写回文件；反之文件被修改，内存也保持一致 |

**使用场景**：处理数据、**不改变数据源**时用私有映射；需要对数据源**实时同步变更**、或做进程间通信时用共享映射。

> 例：公司给你一个含 100 万条用户信息的文件要求过滤处理——处理过程中可能修改数据，用私有映射，改的是副本，源文件安然无恙（用共享映射就把原始数据改坏了）。

**用 mmap 做进程间通信，必须用共享映射**：A、B 两个进程都共享映射同一个文件，A 改内存 → 同步到文件 → B 从映射内存里就能看到——通信成立。

### 8.4 共享映射验证示例

`mmap.c`——对映射内存的修改会同步到文件：

```c
#include<stdio.h>
#include<unistd.h>
#include<stdlib.h>
#include<string.h>
#include<sys/types.h>
#include<sys/stat.h>
#include<sys/fcntl.h>
#include<sys/mman.h>

int main(void)
{
	int fd = open("Mapfile",O_RDWR);
	int size = lseek(fd,0,SEEK_END);

	char *ptr = NULL;
	if((ptr = mmap(NULL,size,PROT_READ|PROT_WRITE,MAP_SHARED,fd,0)) == MAP_FAILED)
	{
		perror("mmap failed");	
	}
	close(fd);
	ptr[0] = 'A';//共享映射更新文件数据

	return 0;	
}
```

操作流程：先在当前目录创建一个 **Mapfile**（里面随便写点内容）→ 编译运行本程序 → 观察 Mapfile 的内容被修改（首字符变成 'A'）。

要点：

- 用 `lseek(fd, 0, SEEK_END)` 取文件大小，作为映射大小；
- 共享映射 `MAP_SHARED`；
- 映射建立之后，文件描述符其实没用了，**可以直接 close**，不影响映射内存的使用；
- 注意：程序里**并没有调用 write 修改文件**——改的是映射内存，文件是被同步机制改掉的。

### 8.5 用 mmap 实现 IPC 的两个前提

**前提一：映射文件作为读写缓存——有大小、无有效数据**

管道队列 4K、队列里初始是空的；对应地，映射文件也要"**有大小但不能有东西**"——否则写端还没写，读端就能看到文件里原有的内容，不合理。方法：**ftruncate 截断文件**——

```c
ftruncate(fd, sizeof(shared_t));    // 文件拓展/结算为指定大小，体积用 \0 填充
```

文件被截断为指定大小，内容全是 \0——有 size、无有效数据。

**前提二：缓存的是结构体消息包**

文件中缓存的一般不是无格式字节流（"你好"这种字符串），而是**结构体数据**——把映射内存当作一个**结构体数组**，每个结构体都是一个**消息包**：

```c
typedef struct
{
    int msg_id;            // 消息编号
    char msg_data[1024];   // 消息数据
} shared_t;
```

**映射文件截断成多大，取决于开发者想缓存多少条消息**：只截断一个结构体大小 → 第二条消息来就替换覆盖第一条（实时消息）；截断成 `结构体大小 × N` → 相当于数组，可以从下标 0 往后写、读端按序读，**支持一定缓存**。

### 8.6 mmap 通信示例

写端 `mmap_wr.c`——负责创建文件、截断、映射、循环改数据：

```c
#include<sys/types.h>
#include<sys/stat.h>
#include<fcntl.h>
#include<sys/mman.h>
#include<unistd.h>
#include<stdlib.h>
#include<stdio.h>
#include<string.h>

typedef struct
{
	int msg_id;
	char msg_data[1024];
}shared_t;

int main()
{
	int fd = open("Mapfile",O_RDWR|O_CREAT,0664);
	//截断处理
	ftruncate(fd,sizeof(shared_t));
	//映射
	shared_t *ptr = NULL;
	if((ptr = mmap(NULL,sizeof(shared_t),PROT_READ|PROT_WRITE,MAP_SHARED,fd,0)) == MAP_FAILED)
	{
		perror("mmap call failed");	
	}

	close(fd);
	//初始化映射内存数据
	ptr->msg_id = 0;
	bzero(&ptr->msg_data,1024);
	//写端循环修改
	while(1)
	{
		++(ptr->msg_id);
		sprintf(ptr->msg_data,"test message,id %d\n",ptr->msg_id);
		sleep(1);
	}

	return 0;
}
```

- 写端：open（不存在则创建）+ **ftruncate 截断** + 共享映射 + 初始化映射内存 + 循环改数据（每秒一次）；
- 读端：只需要 open + 共享映射 + 循环打印——**不能截断**（会把写端的数据清掉）、**不需要初始化**（初始化是写端的职责），所以读端里这些代码都被注释掉了；
- 读端开始执行时不一定能看到第一条消息：映射内存只有一个结构体、不支持缓存，写端覆盖得快，读端读到哪条算哪条（如 3、4、5、6……）——像**直播**：实时推流，什么时候进去看哪一段；不像录播可以拖进度条。

### 8.7 分段映射：offset 的作用

大数据文件（GB 级以上）一次映射不下（内存没那么大），经典方案是**分段映射**：切片、分批次映射、分段处理文件数据（一次映射一兆或几兆都行）。这正是 **offset 参数**的用途——小文件一次映射完无所谓，大文件必须分段。

```c
int offset = 0;
int map_size = 0x100000;        // 一次映射 1MB
while (true)
{
    mmap(NULL, map_size, prot, map_private, fd, offset * map_size);
    ++offset;                    // 偏移量累加：0、1MB、2MB……
}
```

常用十六进制常量（大文件处理时的方便写法）：

| 十六进制 | 十进制 |
|---|---|
| 0x1000 | 4096（4K） |
| 0x10000 | 65536（64K） |
| 0x100000 | 1MB |

文件处理场景常用私有映射（MAP_PRIVATE）——分段只是每次映射的位置不同，其余参数不变。

### 8.8 映射失败的常见原因

**原因一：权限——映射权限必须小于等于 open 权限**

设想：对某文件我们只有 other（其他人）的**只读权限**，却要做**共享映射 + 读写内存**——内存一改就同步到文件，等于绕过文件权限篡改文件，这样文件就没有安全性可言了，必然行不通。系统如何检测？

- **思路一**：映射时访问用户的权限列表，查看用户对目标文件的权限，发现只读就不允许写映射。可行但**不可取**——进程获取数据信息有三个距离：**近：进程内存数据；中：磁盘数据；远：网络数据**。翻权限列表要读磁盘文件，属于"中距离"，影响进程执行效率；
- **思路二（系统的实际做法）**：**只看 open 的权限**——用户 open 打开文件时，权限已经被系统校验过一次（只有读权限就只能只读打开）；后续 mmap 时，**只要映射的权限小于等于 open 的权限即可**，大于就失败。不用访问磁盘权限数据，效率更高。

所以：open 只读打开 → 只能只读映射。注意系统**不管你是谁**（哪怕你是文件所有者、本来有读写权限），只看你这次 open 是怎么打开的。

**原因二：大小——映射大小必须小于等于文件大小**

"欺骗 mmap"：文件实际只有 20 字节，映射却传 1MB——**映射会成功**，但后续访问超出文件有效长度的部分会出问题：系统在映射时会检查**文件的有效长度**，按此长度开放用户可访问的内存大小；一旦超出这个长度访问，产生**内存访问越界**——Linux 下这种错误叫**总线错误（SIGBUS，会产生 core dump）**，进程被系统直接杀死。

> 与 malloc 一脉相承：malloc 默认按页（4K）分配，申请 100 字节也给一页，但只开放 100 字节的使用权限；映射同理，申请 1MB 却只给 20 字节的使用权限。

结论：**映射内存的大小必须小于等于文件大小，不能大意，避免越界访问。**

## 第 9 章 进程间关系

前面几章一直在用"父子进程"的概念，本章把进程之间的组织关系系统梳理一遍，包含三层：**亲缘关系**（谁创建了谁）、**进程组**（系统按组管理进程）、**会话**（终端按会话管理进程），最后落到两个实际问题：**控制终端**（怎么让程序不被终端拖累）与**孤儿进程**（异常进程的托管）。本章偏理论、代码不多，但都是面试与后续开发的高频内容。

### 9.1 亲缘关系

进程之间的血缘关系分两种强度：

- **较强的亲缘关系（父子关系）**：父进程创建子进程；读共享写复制继承数据；子进程退出后父进程回收僵尸；子进程的整个生命周期，父进程**全程参与**——判断强亲缘就一句话：创建、继承、回收三大环节是不是父进程全程在场；
- **稍弱的亲缘关系（多级进程）**：如爷爷与孙子（父进程的父进程），一般**只有继承**——数据经父亲一代代传下去，但创建与回收都与爷爷无关。

> 和现实中的"隔辈亲"相反：计算机里最强的血缘关系就是父子，隔代反而弱。

**fork()+execl() 的广泛使用**。前面几章多次提过这个组合，它的真实使用场景远比示例广泛——电脑**开机的整个登录流程**就靠它运转：

- 开机后启动 **init 进程** → call **login 函数** → 用户输入用户名与密码，列表匹配 → 匹配成功 → `login -> fork -> 子进程 -> execl -> bash`，登录成功后系统给你的第一个终端就是这样"重载"出来的；
- 平时在终端执行一个程序 `./app`：实际是 `bash -> fork() -> 子进程 -> execl() -> app`——bash fork 出子进程，子进程重载 app 程序，所以平时运行的进程都是终端的"亲儿子"。

也就是说：**你敲的每个命令、启动的每个程序，都是 bash 用"fork + execl"组合创建出来的**——这也解释了 9.4 控制终端的一切现象。

查看进程间关系的两个常用命令：

| 命令 | 用途 |
|---|---|
| `ps ajx` | 查看进程间关系：ppid（父进程）、pid、pgid（进程组）、sid（会话） |
| `ps aux` | 查看进程详细信息 |

### 9.2 进程组

**概述**：系统中为了保存管理大量的进程，衍生出**进程组（process group）**结构，由进程管理器负责，系统中分为若干进程组。

**进程组结构**：每个组由一个**组长进程**和多个**组员进程**构成。进程组中可以**没有组员**（组员都退出或转移后只剩组长），但**必须有组长**。

> 类比注册公司：公司可以只有老板一个人（自媒体工作室），但不能没有老板——组员可以光杆，组长不能缺席。

**组长身份标识**：每个进程组，组长用自己的 **pid** 申请组 id（**pgid**）——所以某个进程 **pid == pgid**，它就是组长进程。

> 类比用自己名字命名公司：北方有位"小品之王"用自己的名字成立公司——组长进程也一样，用自己的 pid 当组号，一看组号就知道是谁的组。

**进程组的生命周期**：组中**最后一个进程终止或转移**、进程组为空时，系统释放进程组；**组的存在与否，与某个特定的进程无关**——组长退出了，只要组里还有组员，这个组依然存在并被系统管理，直到组内一个人不剩。

> 类比公司老板出事：某直播平台老板因故离职，公司只要还有员工在就照常存在——进程组不与"某个特定的人"绑定。

**获取组 id**：

```c
pid_t pgid = getpgrp(void);    // 调用返回进程组 id
```

当前终端上直接运行的程序（终端进程）**默认就是组长**——在终端敲 `./app` 的那一刻，它创建的终端进程默认是一个组长进程。

**创建新进程组或转移组中进程**——都用 `setpgid`：

```c
setpgid(getpid(), getpid());    // 创建进程组
setpgid(getpid(), 8000);        // 转移进程，将目标进程转移到 8000 组
```

转移失败有两种情况：

1. 目标组 **8000 不存在**；
2. **权限不足**——必须对目标组（如 8000）有足够的访问权限，否则失败（想往 root 的组里放进程，你自己也得是 root）。

**无论是转移还是创建，只有组员进程可以进行**：

- 组长**不能创建新组**：它的 pid 已经申请过组 id，再用同样 pid 申请必然失败（组 id 已存在）；
- 组长**不能转移**：假设组长（pid=组id=3000）转移到 8000 组，原 3000 组还存在、它还挂着组长的身份——就有了两个身份，身份模糊。系统不允许，所以组长进程无法转移。

**子进程默认与父进程同组**：如果父进程是**组长进程**，那么它创建的子进程**默认归纳到父进程同组**作为组员——这叫**就近归纳**。因为不然系统要翻组列表、检查权限、寻找"有权限的目标组"，费力；而父进程所在的组是现成且必定有权限的，直接放进去最省事。

> 思考题：看到一个进程组，是否可以直接断定"组长是父、组员都是子"？**不可以**——组成员是允许转移的，后续组构成可以特别复杂，可能一个组里的 10 个组员跟组长毫无血缘关系。**组关系与亲缘关系没有必然联系**。（第 4 章 waitpid 的"同组回收、跨组回收"参数，用的就是本章的进程组概念。）

### 9.3 会话

**概述**：会话（session）结构一般用于**管理终端中的所有进程**——一个终端上可能同时跑着很多进程（多进程模型一跑几十个），系统需要把它们组织起来统一管理，这就是会话。

以终端窗口的典型层级为例：

```
Bash（终端本身）                      ← 会话发起者
  └── ./app（终端进程，组长）           ← 终端 fork + execl 出的直接子进程
        └── app fork 出的子进程（组员）  ← 终端子进程
```

- **终端进程**：终端（bash）的直接子进程（如 `./app`），默认是组长；
- **终端子进程**：终端进程再 fork 出的子进程，是组员。

**会话的结构**：会话由**一个发起者（Bash）**和**所有会话参与者**构成，参与者一般**按组归纳**——把终端进程那个组整体算作会话参与者（孙子们都在组里，一网打尽）。

**会话发起者身份标识**：**pid == pgid == sid**（三个 id 相等）——终端（bash）的进程号、组号、会话号相同，它就是会话发起者。

**终端与它的直接子进程：不同组，同会话**——bash 与它 fork 出的终端进程各自的组长身份独立（不同组），但处于同一个会话里。

**如何获取会话 id、以及如何创建新会话**：

```c
pid_t sid = getsid(getpid());    // 返回当前进程会话 id
setsid(void);                    // 先进行组创建，成功后进行会话创建；只有组员进程可以创建新会话
```

`setsid` 内部第一步是**先创建组**——所以和 `setpgid` 一样，**只有组员进程可以调用**（组长创建组必然失败）。

### 9.4 控制终端与脱离

**会话发起者退出，对整个会话内进程的影响**：当会话发起者 bash 退出（终端窗口被关闭），系统**以组为单位，杀死全部会话参与者**（杀掉终端进程那一组）——终端进程受限于终端。

> 实际现象：写一个死循环程序在终端里跑，关闭终端窗口时——系统提示"该终端仍有一个进程在运行，关闭该终端将杀死该进程"。提示说得太谦虚了（只说"一个"），实际是**按组**杀的：终端进程、终端子进程，一组全杀。

**何为控制终端、终端进程是否会被会话影响**：

- **终端进程**（终端的直接子进程）**无法脱离控制终端**：它是组长——不能创建新组、不能转移、不能创建新会话（创建会话要先建组，组长做不了）；
- **终端子进程可以存活**：它是组员，可以通过以下任一方式**脱离控制终端**：
  1. 让进程**创建新组**；
  2. 让进程**转移到其他组**；
  3. 让进程**创建新会话**（创建会话内部先创建组，同样只有组员能做）。

**课后实验**：创建一父三子，让子进程脱离控制终端（创建组或成立新会话都可以），然后手动关闭 bash，查看子进程是否存活。

> 实际意义：以后写的服务器程序、后台常驻程序（类似 QQ），必须脱离控制终端——否则程序会"绑"在某个终端上，终端一关程序就跟着没了。

### 9.5 孤儿进程

**概述**：父子进程中，**父进程先于子进程退出**，子进程变为**孤儿进程**。当进程变为孤儿进程后，系统的**托管机制**生效：

- 孤儿进程的**父进程自动变更为托管进程**；
- 孤儿进程退出转变为僵尸后，由**托管进程负责回收**（Ubuntu 16.04 的托管进程是 **upstart/user**——它本身还负责图形界面）。

> 类比人类社会：孤儿由福利院托管——操作系统也一样，父亲没了，系统指派一个"养父"，养父负责回收孩子（进程）。

**演示验证**：写一个程序让父进程先退出、观察子进程的父进程 ID 变化：

```c
#include <stdio.h>
#include <unistd.h>
#include <stdlib.h>

int main(void)
{
    pid_t pid;
    pid = fork();
    if (pid > 0)
    {
        sleep(10);      // 父进程睡 10 秒后先退出
    }
    else if (pid == 0)
    {
        printf("child pid %d , ppid %d\n", getpid(), getppid());
        sleep(11);      // 子进程跨过父进程的退出时刻
        printf("child pid %d , ppid %d\n", getpid(), getppid());
        exit(0);
    }

    return 0;
}
```

编译运行后观察：第一行打印中，子进程的 ppid 是父进程的 pid（如 3313）；等父进程 10 秒后退出、子进程 11 秒后再打印，ppid 已经变成托管进程（如 1616）。用 `ps aux` 查 1616，正是 upstart 相关进程——托管成立。

**危害**：孤儿进程是异常进程，残留在系统中不处理，会影响新进程的创建与使用；而且它的危害是"**弹性**"的：

- 僵尸进程危害**固定**——就残留一个 PCB，大小是固定的；
- 孤儿进程危害**取决于它在干什么**：如果它只是挂着睡大觉（低开销执行），危害可以忽略；如果它持续申请、占用系统资源（比如死循环申请内存），危害巨大——某些资源被它占着，其他人就不能用了；
- **托管进程只负责回收僵尸，不控制、不限制孤儿进程的行为**——所以孤儿进程可能一直在执行，这是最麻烦的地方。

> 类比：末世环境下，死人（僵尸）的威胁是固定的；活人（孤儿）的威胁取决于他在干什么——他可能什么都不干，也可能持续作恶。

应对原则：**孤儿进程，早发现、早处理（杀死孤儿进程）**。那么问题来了：怎么杀？托管进程能杀吗？

**处理方式**：

- **不能杀托管进程**：upstart 负责图形界面等系统职责，把它杀掉会导致系统注销；而且就算杀掉它，托管机制还在、换一个进程继续托管，没有意义。只能针对孤儿进程本身下手；
- **定位与批量处理**：用 `ps ajx` 查出这一批孤儿进程的组号（pgid），然后按组杀：`kill -9 -<组号>`（组号前加负号表示整组）；单个杀也可以，但进程多了很麻烦；
- **管道方案（本节重点）**：利用匿名管道"读端关闭、写端写数据会被 SIGPIPE 杀死"的特性——父进程作为读端、子进程作为写端；父进程一退出（读端关闭），子进程再往管道写数据就会被系统以 SIGPIPE 杀死。**管道在这里不是为了通信，而是作为孤儿进程的检测装置**——父进程不读数据都没关系；
- **信号处理**：使用第三方检测进程，检测到孤儿进程后，手动发送信号杀死孤儿进程（信号的具体用法见第 10 章）。

管道方案的完整示例（`orphan.c`）——一父五子，父进程退出后子进程被系统自动清理：

```c
#include <sys/types.h>
#include <sys/stat.h>
#include <fcntl.h>
#include <sys/mman.h>
#include <unistd.h>
#include <stdlib.h>
#include <stdio.h>
#include <string.h>

int main()
{
	pid_t pid;
	int i;
	int fds[2];
	pipe(fds);
	for(int i=0;i<5;i++)
	{
		pid = fork();
		if(pid == 0)
			break;
	}

	if(pid>0)
	{
		close(fds[1]);
		int seconds = 5;
		while(seconds--)
		{
			printf("parent exec busines..\n");
			sleep(1);
		}
		exit(0);
	}
	else if(pid == 0)
	{
		close(fds[0]);
		while(1)
		{
			write(fds[1],"1",2);
			printf("child pid %d execl business\n",getpid());
			sleep(1);
		}
	}
	else
		perror("fork calling failed");
	
	return 0;	
}
```

运行现象：

- **不加处理时**（把子进程写管道的代码注释掉）：父进程退出后，5 个子进程全部变成孤儿、一直常驻（它们会一直输出），关闭终端都杀不掉；
- **加上管道处理后**：父进程 5 秒后退出的瞬间，5 个子进程写管道触发 SIGPIPE，全部被系统杀死——孤儿进程被自动清理。

要点：

- `pipe(fds)` 必须在 `fork()` **之前**创建——所有子进程才能继承同一组描述符；
- 父进程 close(fds[1])（不要写端）、子进程 close(fds[0])（不要读端）——确定通信方向、完成引用计数收尾；
- 子进程 `write(fds[1], "1", 2)` 每写一次就相当于一次"生命探测"：父进程还活着（读端还开着）时写入正常；父进程退出（读端关闭）后再写，SIGPIPE 立即杀死子进程；
- 孤儿进程退出后的回收由托管进程负责，不再由原父进程处理。

> 记忆口诀：**子进程先于父进程死，父进程要回收；父进程先于子进程死，子进程变孤儿要处理。**

## 第 10 章 信号（Signal）

前面几章反复用到"杀进程靠信号"——本章正式进入信号。它是 Unix/Linux 系统最经典的消息机制：既能用来处置进程（杀死、挂起），也能在开发中做条件触发（信号捕捉）。本章覆盖信号的概念、分类、五种触发方式、三种行为与五种默认处置动作，以及用 sigaction 修改信号行为。

### 10.1 信号概述

**信号**是 Unix 和 Linux 操作系统经典的消息机制。

- **主要用途：处置进程**——利用信号杀死、挂起进程（第 4 章用 `kill -9`、`kill -11` 结束进程，第 7 章被信号杀死后解码信号编号，都是信号的应用）；
- **开发用途：信号捕捉**——让信号绑定一个行为（捕捉函数），信号递达时系统自动调用对应函数。

> 与 QT 信号槽的关系：QT 的"信号与槽"（点击按钮触发 click 信号、自动调用绑定的槽函数）**灵感来源正是操作系统的信号**；但信号槽技术并不是用 Linux 信号实现的——只是设计思想同源。用 Linux 信号也能做出"绑定触发"的效果：给某个信号绑定一个函数，信号来了自动执行。

### 10.2 系统支持的信号与分类

**查看系统支持的所有信号**：

```bash
kill -l      # 列出系统支持的所有信号
```

一共 **64 个信号**，编号 1~31、34~64（中间没有 32、33）：

| 类别 | 编号范围 | 说明 |
|---|---|---|
| UNIX 经典信号 | 1~31 | 系统经典信号 |
| 自定义信号（实时信号） | 34~64 | 用户可自定义使用 |
| 隐藏保留 | 32、33 | 被系统隐藏，预留给 **NPTL 线程库**使用，用户无法直接使用 |

### 10.3 五种触发信号的方式

#### 10.3.1 终端组合按键触发

在终端（bash）中，**前台进程是唯一的**（`ps` 里带 `+` 标识，如 `S+`、`R+`），三个组合键都只对前台进程生效：

| 组合键 | 触发的信号 | 效果 |
|---|---|---|
| Ctrl+C | SIGINT（2 号） | 杀死前台进程 |
| Ctrl+\ | SIGQUIT（3 号） | 杀死前台进程（带核心转储，退出信息略有区别） |
| Ctrl+Z | SIGTSTP（20 号） | 挂起前台进程 |

**前后台与作业控制**：

- 挂起后进程状态从 `R`（运行）变成 `T`（挂起），用 `jobs` 查看被挂起的作业（作业编号 1、2……）；
- `fg %1`：把 1 号作业唤醒到**前台**执行——前台进程占用终端，此时敲其他命令没有反应（终端被它占着）；
- `bg %1`：把 1 号作业唤醒到**后台**执行——终端照常可用，但 `ps` 里它的状态不带 `+`；
- 后台进程想杀死：Ctrl+C、Ctrl+D 都无效（组合键只对前台有效），只能 `kill -9 <pid>`。

> 前后台的现实类比：Windows 桌面上同时开着音乐播放器、文档、电影三个程序，但人一次只能操作一个——鼠标点谁，谁就是"前台"（焦点），其余都在后台。终端的道理一样：前台只有一个，后台可以有多个。

> 为什么 Ctrl+Z 对应 20 号而不是 19 号？19 号是 SIGSTOP，20 号是 **SIGTSTP**——"TSTP" 里的 T 指终端（TTY），所以终端组合键挂起用的是 20 号。

**组合键是怎么被识别的（线路规程）**：终端也是一个进程，用户输入的数据先经过**线路规程（line discipline）**：

- 普通数据（如输入 ABCD）→ 线路规程放行 → 进入输入缓冲区 → 被进程读取处理；
- 功能键（如 Ctrl+C）→ 被线路规程**拦截识别** → 生成对应消息包交给操作系统 → 系统解析后，向当前唯一的前台进程发送对应信号（如 2 号信号）。

> 这就是"为什么终端里 Ctrl+C 是杀进程、而在编辑器里 Ctrl+C 是复制"——不同软件对组合键的定义不同；终端里的组合键由线路规程统一识别处理。

**三种组合键对后台进程无效**——因为前台只有一个，系统只会把信号发给前台进程，不会误杀。

#### 10.3.2 命令触发信号

`kill` 命令本身就是"发信号"的命令：

```bash
kill -signo pid            # 向指定进程发送信号
kill -9 -<pgid>            # 向指定进程组发送信号（组号前加负号，整组杀）
kill -l                    # 查看信号列表
```

- `signo` 是信号编号（-1、-2、-9……）；
- 可能**因权限不足而失败**——必须对目标进程或目标组有足够的权限（普通用户杀不掉 root 的进程）；
- 按组杀的用法在 9.5 处理批量孤儿进程时已经用过：`ps ajx` 查组号 → `kill -9 -组号`。

#### 10.3.3 函数触发信号

发信号一共四个常用函数，都需要 `#include <signal.h>`：

| 函数 | 原型（要点） | 说明 |
|---|---|---|
| `kill` | `int kill(pid_t pid, pid_t signo);` | 向任意进程或组发送任意信号 |
| `raise` | `int raise(pid_t signo);` | 向**当前进程**发送任意信号 |
| `abort` | `void abort(void);` | 无参数无返回值，向当前进程发送固定的 **SIGABRT** 信号 |
| `sigqueue` | `int sigqueue(pid_t pid, pid_t signo, union sigval val);` | 向任意进程发送任意信号，**同时携带 union 消息包**，支持 IPC |

- `kill` 函数与 `kill` 命令**参数顺序正好相反**：命令是"信号编号在前、pid 在后"，函数是"pid 在前、信号编号在后"；命令本身就是用这个函数实现的；
- `raise` 不能指定进程 ID——只能给自己发；
- `abort` 连发什么信号都不能指定——固定 SIGABRT；
- `sigqueue` 是"加强版 kill"：发信号的同时携带数据（union sigval），**信号实现进程间通信**靠的就是它。

#### 10.3.4 硬件异常产生信号

代码里对硬件的非法访问（本质是代码写错）会触发硬件异常，系统随后发信号把进程杀掉——这就是"运行时崩溃"的来源。三种经典异常：

| 错误 | 触发原因 | 系统发送的信号 |
|---|---|---|
| 段错误 | 进程内存访问异常，如**对只读内存进行写操作**（内存越权访问）、野指针 | SIGSEGV（11 号），杀死进程 |
| 总线错误 | 内存**越界访问**、访问野地址（如 mmap 映射大小超过文件大小，见 8.8） | SIGBUS（7 号），杀死目标进程 |
| 浮点数例外 | 使用 CPU 计算器产生计算异常（最典型：**除零**） | SIGFPE（8 号），杀死目标进程 |

- 段错误示例：`char *p = "1234"; p[0] = 'A';`——"1234" 在只读区，写它就是越权，必触发段错误；能改的只有"当前变量地址中存的值"（重新赋值），不能改字面量内容；
- 总线错误示例：文件刚创建没有大小、mmap 却映射 1MB，实际有效长度是 0，往映射内存写就触发总线错误；
- 浮点数例外示例：除零——编译器会先给警告（提示除零操作有风险），忽略警告强行运行，CPU 计算时触发异常，进程被 8 号信号杀死。

> 排查方向：看到段错误先查内存操作（越界读写、野指针、只读区写入）；看到总线错误先查映射/访问范围是否超出有效长度；看到浮点例外先查计算（除零、非法运算）。

#### 10.3.5 软条件产生信号

与硬件异常的"一碰就炸"不同，**软条件是正常使用时一直没事、某一天满足了特定条件才触发**：

| 软条件 | 触发条件 | 系统发送的信号 |
|---|---|---|
| 管道 | 读端关闭后，写端还向管道写数据 | SIGPIPE（13 号），杀死写端进程 |
| 定时器 | alarm 定时时间到 | SIGALRM（14 号），杀死定时进程 |

> 类比：硬件异常像"吸毒"——碰了就是红线，立刻出事；软条件像"吸烟"——本身可以一直进行，但吸到某个量（条件满足）才会出事。

**alarm 定时器**：

```c
#include <unistd.h>

unsigned int alarm(unsigned int seconds);
// 参数为定时的秒数；返回值为之前未定时够的剩余秒数
// 返回 0 表示定时成功（没有遗留），返回 >0 表示之前还有剩余定时，失败
```

`alarm.c`——定时 1 秒后程序被 SIGALRM 杀死：

```c
#include<stdio.h>
#include<unistd.h>
#include<stdlib.h>
#include<sys/types.h>
#include<sys/stat.h>
#include<sys/fcntl.h>
#include<pthread.h>
#include<signal.h>
#include<sys/mman.h>

int main()
{
	alarm(1);
	int count = 0;
	while(1)
	{
		printf("count++ = %d\t",++count);
	}
	
	return 0;	
}
```

编译运行：计数器疯狂打印，**1 秒后进程被系统的 SIGALRM 信号杀死**（终端会提示"闹钟"——即 alarm 信号杀死的提示）。观察：1 秒内打印约 29 万次——但这**不能代表 CPU 的运算能力**：CPU 算得远比输出快，瓶颈在输出（缓冲区刷新）而不在计算。

> 问题：alarm 是好心提醒"时间到了"，却默认把进程杀了——太粗暴。`sleep` 函数其实也是"定时挂起 + 唤醒"，但它睡 5 秒后不会死——说明它一定处理过 SIGALRM。办法就是下面要讲的**修改信号行为**（让 SIGALRM 失效/被捕捉）。

### 10.4 信号的三种行为与五种默认处置动作

每个信号都有**三种行为**：默认行为、忽略行为、捕捉行为。若不人为修改，信号永远走**默认行为**；默认行为下面有**五种处置动作**（五选一）：

| 默认动作 | 含义 |
|---|---|
| term（终止） | 直接杀死进程，没有废话（不产生 core 文件） |
| core（核心转储） | 杀死进程的同时生成 **core 文件**（核心转储）——段错误、总线错误、浮点数例外都带"核心已转储" |
| ign（忽略） | 不处置进程——信号变成一次"通知" |
| stop（挂起） | 挂起进程（19 号 SIGSTOP、20 号 SIGTSTP 属于此类） |
| cont（继续） | 唤醒/继续执行（continue 的简写） |

- 看到"**核心已转储**"字样 → 判定为 core 动作；信号来了进程没事 → 必然忽略；进程被挂起 → stop；对应地恢复 → cont；
- **忽略行为 vs 忽略动作**：两者结果一样（都不处置进程），区别是**优先级不同**——行为优先：信号来了先看行为，行为是"忽略"就根本走不到默认动作那一步；
- **忽略行为下面没有任何动作**——进程看到信号就完事，不处置；
- **捕捉行为**对应的动作是**自定义动作**——绑定一个**捕捉函数**：系统默认的五个动作相当于系统写好的五个函数，而捕捉函数是**用户自己声明与实现**的（接口固定），信号触发时系统自动调用它——想干什么由你决定（类似回调）。

> 与信号槽呼应：槽函数是你写的、不是你调的——信号触发时系统自动调用；捕捉函数完全一样。

### 10.5 修改信号行为：sigaction

要改变某个信号的行为（默认 → 忽略/捕捉），需要修改这个进程的信号行为结构体，用 `sigaction` 完成：

```c
#include <signal.h>

struct sigaction nact, oact;    // nact：新信号行为；oact：存储原有的（用于复位还原）
nact.sa_handler = SIG_DFL;      // 三选一：SIG_DFL 默认行为 / SIG_IGN 忽略行为 / 捕捉函数地址
nact.sa_flags = 0;              // 默认选项
sigemptyset(&nact.sa_mask);     // 临时屏蔽字，初始化即可

sigaction(SIGINT, &nact, &oact); // SIGINT：Ctrl+C 触发的 2 号信号；把它的行为换成 nact，原有行为存入 oact
while (1);                      // 必须写死循环测试，否则进程直接结束看不出效果
```

**结构体三个成员**：

| 成员 | 作用 |
|---|---|
| `sa_handler` | 设置行为：`SIG_DFL`（默认）、`SIG_IGN`（忽略）、捕捉函数地址（捕捉）三选一 |
| `sa_flags` | 默认选项，传 0 |
| `sa_mask` | 临时屏蔽字，用 `sigemptyset` 初始化即可 |

**捕捉函数的固定接口**：

```c
void sig_do(int signo)    // 返回值空、参数固定 int（系统传入当前捕捉到的信号编号）
{
    printf("捕捉了 %d 信号\n", signo);
}
```

- 捕捉函数由用户**声明和实现**，但**不是用户调用的**——信号递达（条件满足）时**系统自动调用**；
- 参数 `signo` 由系统传：捕捉的是 2 号信号，进来就是 2；捕捉 3 号就是 3——打印它就能看到是哪个信号触发的。

**sigaction 函数本身**：

```c
int sigaction(int signo, const struct sigaction *act, struct sigaction *oldact);
```

- 作用：**修改（或查询）指定信号的行为**——`act` 传入新行为，`oldact` 带出原有行为，传 `NULL` 表示不关心那一侧；
- 返回值：成功返回 **0**，失败返回 **-1** 并设置 `errno`。

**SIGINT 是什么**：名字拆开是 `SIG`（signal）+ `INT`（interrupt）—— 2 号"中断信号"。终端里按 **Ctrl+C** 时由线路规程生成并发给前台进程；它的默认行为是 **term（终止进程）**，这正是平时 Ctrl+C 能直接杀掉程序的原因。

**sigaction 的三个参数**：

1. 要修改的信号：**建议传信号名（如 SIGINT）而不是编号 2**——不同系统信号编号可能不同，用名字跨系统不会出错；
2. 新的行为结构体地址：`&nact`；
3. 传出原有行为：`&oact`（要复位时用）；不想保存传 `NULL` 即可。

> 为什么建议存 oact？换灯泡类比：换个新灯泡，旧的别急着扔——用完之后把旧的装回去，恢复原样。信号行为也一样：修改是为了临时使用，用完可以用 oact 复位还原。

`signal.c`——捕捉 SIGINT（2 号信号）的完整示例：

```c
#include<stdio.h>
#include<signal.h>

void sig_do(int signo)
{
	printf("%d signal",signo);	
}

int main()
{
	struct sigaction nact,oact;
	nact.sa_handler = sig_do;
	nact.sa_flags = 0;
	sigemptyset(&nact.sa_mask);

	sigaction(SIGINT,&nact,&oact);
	while(1);
	
	return 0;	
}
```

编译运行后按 **Ctrl+C**：不再被杀掉，而是打印 `2 signal`——信号被捕捉，进程继续跑。

**为什么按 Ctrl+C 能触发 `sig_do`？** 整条链路分四步：

```
Ctrl+C 按键
   ↓ 终端线路规程拦截识别（功能键，不进输入缓冲区）
向前台进程发送 2 号信号 SIGINT
   ↓ 进程 PCB 中 SIGINT 的行为已被 sigaction 改写
行为 = 捕捉，捕捉函数地址 = sig_do
   ↓ 信号递达，系统自动调用
sig_do(2) → 打印 "2 signal" → 返回，回到 while(1) 继续空转
```

- **信号源**：Ctrl+C 本身只是一个按键，由**终端线路规程**翻译成 SIGINT，发给当前的**前台进程**——所以程序必须在前台运行，后台进程按 Ctrl+C 不会有任何反应；
- **行为改写**：`sigaction(SIGINT, &nact, &oact)` 已把该进程 SIGINT 的行为从默认的 term（直接终止）改成**捕捉**，`sa_handler = sig_do` 等于告诉系统"这个信号来了就调用 `sig_do`"；
- **是系统调用，不是用户调用**：`while(1);` 里没有任何一句代码调用 `sig_do`，是内核在信号递达时打断执行流、跳进捕捉函数，返回后再接着执行被打断的位置——所以进程不会死，死循环会一直转下去；
- **按几次打印几次**：每按一次 Ctrl+C 产生一个 SIGINT 信号，就触发一次 `sig_do`，每触发一次打印一行 `2 signal`。

测试建议：

- 三种行为都要试一遍：默认（SIG_DFL，Ctrl+C 照常被杀）、忽略（SIG_IGN，Ctrl+C 无反应）、捕捉（打印编号后继续运行）；
- 捕捉测 2 号信号最方便——Ctrl+C 随时可触发；
- **忽略与捕捉都能让信号失效**（捕捉函数写空，则信号"来了跟没来一样"）。

### 10.6 信号的传递过程：两个信号集

信号抵达进程后**不是立即处理**，而是先记录在进程的 PCB 中，经过两道"门"的检查后才进入处理流程。PCB 中有**两个信号集**（signal set），都是位图：每一位对应一个信号（1~64），位码只有 0 和 1。位码相当于一扇门：**0 表示开门、允许信号通过；1 表示关门、不允许通过**。

```
                         ┌──────────── PCB ────────────┐
信号（如 2 号）─────────→│  未决信号集（系统维护）       │
                         │  对应位 0→通过，1→丢弃       │
                         │  通过后：位翻为 1（未决态）    │
                         └────────────┬────────────────┘
                                      ↓
                         ┌──────────── 屏蔽字 ──────────┐
                         │  阻塞信号集（用户可设置）      │
                         │  对应位 0→通过，1→阻塞        │
                         └────────────┬────────────────┘
                                      ↓ 通过后未决位由 1 翻回 0
                               信号处理流程
                           （默认 / 忽略 / 捕捉行为选择）
```

**第一道：未决信号集**

- 信号尝试通过未决信号集：对应位为 **1** → 信号**直接丢弃**，系统不做处理；对应位为 **0** → 信号通过，进入"**未决态**"；
- 系统把未决信号集中该信号对应位**翻为 1**——标记"当前有一个未决信号"；当信号通过屏蔽字进入处理流程后，该位再**翻回 0**；
- **未决信号集由系统自动维护，用户无法修改**，只能查看；
- 由于"未决位为 1 时，同一信号的再次抵达会被直接丢弃"，所以 **UNIX 经典信号不支持排队**。

**第二道：屏蔽字（阻塞信号集）**

- 对应位为 **0** → 信号通过、进入后续处理流程（抵达态）；
- 对应位为 **1** → 信号**陷入屏蔽（阻塞）**，卡在两个信号集之间，无法递达、无法处理——这就是"信号屏蔽/信号阻塞"；
- **屏蔽字可以由用户自行设置**，决定要阻塞哪些信号。

**通过两道门之后**，信号进入处理流程做**行为选择**：默认行为（五种默认动作处置进程）、忽略行为或捕捉行为——即 10.4、10.5 的内容。

> 补充：前 31 个经典信号主要面向软件研发（处置进程：终止、挂起、异常处理）；34~64 的自定义（实时）信号主要面向驱动开发——例如光盘驱动器，把"上一首/下一首"功能分别绑定到不同信号上，用户每按一次键就触发一次信号。

**为什么经典信号不排队、而实时信号排队？**

- 经典信号的设计初衷是**处置进程**：一个信号就足以杀死进程；杀不死的话再发多次也没用；若信号已被忽略/捕捉（失效），发再多次也同样无效——不需要排队；
- 实时信号绑定的是**功能**：连续按 5 次"下一首"，用户期望跳 5 首，需要把 5 次触发都记录下来逐次处理——所以**实时信号有排队队列**，连续触发多次会依次排队、逐个传递处理。

### 10.7 信号屏蔽：信号集与 sigprocmask

**原理**：每个进程默认自带屏蔽字（所有位为 0）；开发者自定义一个新的信号集，把要屏蔽的信号位置 1，再**替换**进程原有的屏蔽字——与修改信号行为结构体的思路一致：进程原来有一个，自己准备一个，设置好后替换掉。

**信号集类型与操作函数**：“sigset_t”是信号集类型——无论是未决信号集还是屏蔽字，都是这个类型（位图，每一位对应一个信号）。

| 函数 | 原型（要点） | 说明 |
|---|---|---|
| `sigemptyset` | `int sigemptyset(sigset_t *nset);` | 初始化，将 nset 中所有位初始化为 0 |
| `sigfillset` | `int sigfillset(sigset_t *nset);` | 初始化，将 nset 中所有位初始化为 1 |
| `sigaddset` | `int sigaddset(sigset_t *nset, int signo);` | 设置函数，将 nset 中 signo 信号位设置为 1 |
| `sigdelset` | `int sigdelset(sigset_t *nset, int signo);` | 设置函数，将 nset 中 signo 信号位设置为 0 |
| `sigismember` | `int sigismember(sigset_t *nset, int signo);` | 获取/查看 nset 中 signo 信号位的位码并返回（0 或 1） |

**替换函数 sigprocmask**：

```c
sigprocmask(SIG_SETMASK, &nset, &oset);
```

- 第一个参数：替换方式，`SIG_SETMASK` 表示直接用 nset **覆盖替换**进程原有信号集（最简单）；
- 第二个参数：新的信号集地址；
- 第三个参数：传出进程原有信号集（保存在 oset 中，可省略传 NULL）。

**注意**：以上所有操作修改的都是**屏蔽字（阻塞信号集）**，不是未决信号集。

`sigset.c`——屏蔽 2 号信号（Ctrl+C）：

```c
#include<stdio.h>
#include<signal.h>
#include<stdlib.h>
#include<unistd.h>

int main(void)
{
	sigset_t nset,oset;                     // nset：自定义屏蔽字；oset：保存进程原有的屏蔽字
	sigemptyset(&nset);                     // 初始化信号集：31 位全部清零，默认谁都不屏蔽

	sigaddset(&nset,SIGINT);                // 把 2 号信号（Ctrl+C 的 SIGINT）对应位置 1：准备屏蔽它

	sigprocmask(SIG_SETMASK,&nset,&oset);   // 用 nset 覆盖进程原屏蔽字：SIGINT 卡在两道门之间，无法递达
	while(1)                                // 死循环让进程一直活着，方便反复按 Ctrl+C 验证屏蔽效果
		sleep(1);                          // 睡眠等待信号，每秒醒来一次

	return 0;
}
```

编译运行 `gcc sigset.c -o app`、`./app` 后，按 Ctrl+C 进程不再退出——2 号信号被屏蔽、卡在两个信号集之间；连续按多次也一样（同一信号再次抵达时被未决信号集直接丢弃）。若要同时屏蔽 Ctrl+\（3 号信号），再增加一行 `sigaddset(&nset, SIGQUIT);` 即可。

### 10.8 查看未决信号：sigpending

想看"信号已经来了、并且被屏蔽卡住"的状态，要看**未决信号集**而不是屏蔽字：

- **屏蔽字是静态的**：它是事先设好的"要屏蔽谁"的清单，设置之后不再变化；
- **未决信号集是动态的**：信号未抵达时为 0，抵达并被卡住后由系统置为 1——所以"实时是否被阻塞"要看它。

`sigpending(sigset_t *pset);`：获取当前进程的未决信号集，传出到 pset 中。

`sigpending.c`——每秒打印一次 31 位未决信号集：

```c
#include<stdio.h>
#include<stdlib.h>
#include<unistd.h>
#include<signal.h>
#include<string.h>

void print_pset(sigset_t pset)
{
	int signo = 1;
	for(signo;signo<32;signo++)                 // 逐个检查 1~31 号经典信号
	{
		if(sigismember(&pset,signo))            // 位码为 1 → 该信号已产生、被屏蔽卡住（未决）
			putchar('1');
		else                                    // 位码为 0 → 该信号当前不存在
			putchar('0');
	}
	putchar('\n');                              // 31 位打印完，换行
}

int main()
{
	sigset_t nset,oset;
	sigemptyset(&nset);
	sigaddset(&nset,SIGINT);                    // 屏蔽 2 号信号，让它只能停在未决态
	sigprocmask(SIG_SETMASK,&nset,&oset);       // 用 nset 覆盖进程原屏蔽字

	sigset_t pset;
	while(1)
	{
		sigpending(&pset);                  // 取出当前进程的未决信号集
		print_pset(pset);                   // 打印 31 位位码：0 无未决、1 有未决
		sleep(1);                           // 每秒刷新一次，观察按 Ctrl+C 前后的变化
	}

	return 0;	
}
```

运行现象：

- 启动后每秒输出一行 **31 个 0**（当前没有未决信号）；
- 按一次 **Ctrl+C**（2 号信号被屏蔽）：输出变为第 2 位是 **1**（第 1 个字符对应 1 号信号，第 2 个字符就是 2 号信号）；
- 若代码中同时 `sigaddset(&nset, SIGQUIT);` 屏蔽 3 号信号，再按 **Ctrl+\**，输出变为 `0110…`。

### 10.9 三种让信号失效的方式与高权信号

到目前已经学了三种让信号失效的方式，区别在于**信号有没有递达**：

| 方式 | 做法 | 信号是否递达 | 效果 |
|---|---|---|---|
| 信号忽略 | 修改信号行为为 `SIG_IGN` | 已递达 | 信号被送达进程，但处理动作为空（NULL），进程不处置 |
| 信号捕捉 | 自定义信号行为（捕捉函数） | 已递达 | 信号被送达，由自定义动作"消化" |
| 信号屏蔽 | 修改进程屏蔽字 | **未递达**（阻塞在屏蔽字之间） | 临时失效——信号没有消失，解除屏蔽后仍按默认动作处置进程（杀死/挂起） |

**高权信号**：如果所有信号都能被屏蔽、忽略、捕捉，系统还安全吗？系统提供 2 个无法被屏蔽、忽略、捕捉的信号：

| 信号 | 编号 | 作用 |
|---|---|---|
| `SIGKILL` | 9 号 | 杀死进程（`kill -9`） |
| `SIGSTOP` | 19 号 | 挂起进程 |

**屏蔽的权限边界**：屏蔽信号还要考虑**发出者权限与进程权限**：

- 用户进程主动用 `kill -11 <pid>` 发送 11 号信号：可以被屏蔽，进程不会死；
- 但**硬件异常**（段错误）产生的 11 号信号由系统内核直接产生，权限高于用户进程——屏蔽/忽略/捕捉都无效，进程依然被杀死（输出"段错误（核心已转储）"）。

演示对比一——屏蔽 11 号信号，手动 kill -11 无效：

```c
// 此代码屏蔽 11 号信号 SIGSEGV（段错误信号）
int main(void)
{
	sigset_t nset, oset;
	sigemptyset(&nset);
	sigaddset(&nset, SIGSEGV);
	sigprocmask(SIG_SETMASK, &nset, &oset);   // 实现屏蔽段错误信号
	while(1)
		sleep(1);
}
// gcc test.c -o app
// ./app（pid 3000）
// kill -11 3000;   // 可以成功屏蔽信号，11 号信号无法杀死进程
```

演示对比二——同样的屏蔽，无法屏蔽系统产生的硬件异常信号：

```c
int main(void){
	char *str = "9890890809123123";
	sigset_t nset, oset;
	sigemptyset(&nset);
	sigaddset(&nset, SIGSEGV);
	sigprocmask(SIG_SETMASK, &nset, &oset);   // 实现屏蔽段错误信号
	str[0] = 'A';   // 非法操作内存：系统检测到硬件异常，向进程发送 11 号 SIGSEGV 信号，进程被杀死，抛出段错误（核心已转储）
	printf("str %s\n", str);
}
```

### 10.10 用信号回收僵尸进程：SIGCHLD

第 4 章的回收方式（wait/waitpid 轮询）都是**主动回收**——父进程要自己盯着子进程；用信号可以改成**被动回收**：

- 僵尸进程只有父进程能回收；
- 子进程退出时，**系统给其父进程发送一个 `SIGCHLD` 信号**；
- 父进程用 sigaction 对 SIGCHLD 设置捕捉：信号递达时系统自动调用捕捉函数，在捕捉函数里完成回收——父进程平时可以安心做自己的事，不用轮询。

```c
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <sys/wait.h>
#include <unistd.h>
#include <signal.h>

void sig_wait(int n)                     // SIGCHLD 的捕捉函数：把已退出的子进程全部回收
{
	pid_t zpid;
	// SIGCHLD 属于经典信号，不支持排队：大量信号同时递达会丢弃，只回收一次会漏回收、残留僵尸
	while ((zpid = waitpid(-1, NULL, WNOHANG)) > 0)   // 循环回收，不会漏
	{
		printf("parent wait child sucessly , zpid %d\n", zpid);
	}
}

int main(void)
{
	pid_t pid;
	int i;
	// 父进程创建子进程之前完成信号捕捉设定
	struct sigaction act, oact;
	act.sa_handler = sig_wait;              // 捕捉函数地址：SIGCHLD 递达时由系统自动调用
	act.sa_flags = 0;
	sigemptyset(&act.sa_mask);
	sigaction(SIGCHLD, &act, &oact);        // 把 SIGCHLD 的行为改为捕捉（子进程退出时内核自动发它）

	for (i = 0; i < 10; i++){
		pid = fork();                   // 父进程返回子进程 PID；子进程返回 0
		if (pid == 0)
			break;                  // 子进程跳出循环，不再继续 fork，直接走退出分支
	}
	if (pid > 0){
		printf("wait sigchld...\n");
		while (1)
			sleep(1);               // 父进程不轮询，挂起等待 SIGCHLD 被动触发回收
	} else if (pid == 0){
		printf("child i %d pid %d exit\n", i, getpid());
		exit(i);                        // 子进程退出 → 内核向其父进程发送 SIGCHLD
	} else {
		perror("fork call failed");
	}
}
```

要点：

- **必须循环回收**：SIGCHLD 是经典信号、不排队——10 个子进程几乎同时退出，内核只保留一个 SIGCHLD；若捕捉函数只调用一次 waitpid，就会漏回收、残留僵尸。`while ((zpid = waitpid(-1, NULL, WNOHANG)) > 0)` 把所有已退出子进程一次收干净；
- 捕捉函数里用 `WNOHANG` 非阻塞：有僵尸就收，收完立即返回；
- **捕捉必须在 fork 之前设置**——否则子进程先退出、SIGCHLD 先到达时，父进程还没建立捕捉，就会漏掉；
- 与第 4 章呼应：主动回收（轮询）与被动回收（信号触发）可以按场景选择，信号方式开销更小、更优雅。

### 10.11 信号实现进程间通信：父子交替报数

信号的最后一个用途：**进程间通信（IPC）**。用一个实例——父子进程交替报数：父进程给子进程发 1，子进程收后回 2，父再回 3、4、5……数值通过信号在父子间来回传递。

要写出这个程序，需要搞定三件事：

**① 信号选择：用开发专用信号**

信号不能乱用——每用一个信号就要对它做处置（捕捉或忽略），它原本的作用就失效了：占用了 2 号信号 Ctrl+C 就不好使；占用了 11 号信号，段错误的处理就受影响。应当使用两个**开发专用信号**：`SIGUSR1`（10 号）与 `SIGUSR2`（12 号）——系统不会主动触发它们，专门提供给软件研发使用。

**② 发送信号时携带数据**

kill 命令、kill 函数都只能发信号、不能携带数据，这里用 **sigqueue** 函数：

```c
#include <signal.h>
sigqueue(pid_t pid, int signo, union sigval val);
```

union sigval 是联合体，两个成员**二选一**（联合体共享同一块内存）：

| 成员 | 类型 | 说明 |
|---|---|---|
| `sival_int` | int | 携带整型数据 |
| `sival_ptr` | void * | 携带指针（地址）数据 |

交替报数携带的是 1、2、3……选 `sival_int` 即可。

**③ 接收信号携带的数据：必须用新版捕捉函数**

旧版捕捉函数接口 `void sig_do(int n)` 只有一个参数（系统传入信号编号），**没有地方接收通信数据**；想接收数据必须用新版三参数接口：

```c
void sig_do(int n, siginfo_t *info, void *arg);
// info 中的 si_int、si_ptr 两个成员用于接收联合体数据
```

系统收到携带数据的信号后，会自动把数据存到 `info->si_int`（对应 sival_int）或 `info->si_ptr`（对应 sival_ptr）——捕捉函数里直接访问即可。

**为什么要捕捉（两个原因）**：

1. 避免两个信号杀死父子进程——SIGUSR1/2 默认动作是终止进程，不捕捉就会互相杀死；
2. 捕捉函数才能接收信号携带的数据。

**首次发送与后续回传**：后续的回传全部在各自的捕捉函数中完成（像打乒乓球，一方回球另一方自动接）；**首次“发球”由父进程完成**。父子发送方向：父发子用 `SIGUSR1`、子发父用 `SIGUSR2`。父发子的目标 pid 可直接用 `getpid()+1`——Linux 下父子进程 PID 连号（简单可行，但跨系统不保证连号）。

**新版 sigaction 的设置**：

```c
struct sigaction act, oact;
act.sa_sigaction = sig_do;      // 新版捕捉函数（替代 sa_handler）
act.sa_flags = SA_SIGINFO;      // 必选关键字（不再是 0）
sigemptyset(&act.sa_mask);
sigaction(SIGUSR2, &act, &oact);
```

`ipc_signal.c`——父子交替报数完整示例：

```c
#include<stdio.h>
#include<stdlib.h>
#include<unistd.h>
#include<string.h>
#include<signal.h>

void sig_parent(int n,siginfo_t * info,void * arg)
{
    //打印通信数据
    printf("parent pid %d , si_int = %d\n",getpid(),info->si_int);
    //处理通信函数
    union sigval val;
    val.sival_int = ++(info->si_int);
    //回传信号和数据
    sigqueue(getpid()+1,SIGUSR1,val);
    usleep(300000);
}

void sig_child(int n,siginfo_t * info,void * arg)
{
    //打印通信数据
    printf("child pid %d , si_int = %d\n",getpid(),info->si_int);
    //处理通信函数
    union sigval val;
    val.sival_int = ++(info->si_int);
    //回传信号和数据
    sigqueue(getppid(),SIGUSR2,val);
    usleep(300000);
}

int main(void)
{
    //父进程fork之前完成对SIGUSR2信号的捕捉设定
    struct sigaction act,oact;
    act.sa_sigaction = sig_parent;
    act.sa_flags = SA_SIGINFO;
    sigemptyset(&act.sa_mask);
    sigaction(SIGUSR2,&act,&oact);
    //父进程设置对SIGUSR1屏蔽，继承给子进程
    sigset_t nset,oset;
    sigemptyset(&nset);
    sigaddset(&nset,SIGUSR1);
    sigprocmask(SIG_BLOCK,&nset,&oset);
    //进程创建
    pid_t pid;
    pid = fork();
    if(pid > 0)
    {
        //父进程进行第一次信号发送
        union sigval val;
        val.sival_int = 1;
        sigqueue(getpid()+1,SIGUSR1,val);
        //首次发送完毕等待回传
        while(1)
            sleep(1);
    }
    else if(pid == 0)
    {
        //子进程创建（继承），屏蔽了SIGUSR1
        struct sigaction act,oact;
        act.sa_sigaction = sig_child;
        act.sa_flags = SA_SIGINFO;
        sigemptyset(&act.sa_mask);
        sigaction(SIGUSR1,&act,&oact);
        //捕捉完成后解除屏蔽
        sigprocmask(SIG_SETMASK,&act.sa_mask,NULL);
        //子进程捕捉完毕等待信号
        while(1)
            sleep(1);
    }
    else
    {
        perror("fork call failed");
        exit(0);
    }

    return 0;
}
```

运行效果：父子进程交替打印 `si_int`（1、2、3……递增）；`usleep(300000)` 用于放慢节奏（微秒级，300000 微秒 = 0.3 秒），否则打印速度过快会刷屏。

**时序问题与解决方案（本节的难点）**：

- **现象**：去掉延迟后，父进程 fork 完立即发信号，子进程可能还没来得及执行捕捉设定代码——信号以默认动作（终止）把子进程杀死，联调失败（子进程变僵尸/卡死）；
- **临时解法**：首次发送前 sleep/usleep 给子进程一个时间片——但 sleep 会拖慢执行进度，不是好方案；
- **正解：利用信号屏蔽字可继承**——父进程 fork **之前**用 `sigprocmask(SIG_BLOCK)` 屏蔽 SIGUSR1，子进程一出生就继承了这个屏蔽（信号抵达后只能卡在未决态），可以从容完成捕捉设定，然后**解除屏蔽**（用初始化后的空信号集替换：`sigprocmask(SIG_SETMASK, &act.sa_mask, NULL)`）——此后信号递达就能正常捕捉；
- **注意**：不能用 fork 前保存的 oset 来恢复——子进程继承的“原有屏蔽字”本身就是屏蔽状态（1），要用一个全 0 的信号集替换。

**适用范围**：信号 IPC 不限于父子进程——只要能拿到对方的 PID，就可以向他发送携带数据的信号。

### 10.12 五种触发方式速查

| 方式 | 触发手段 | 常见信号 |
|---|---|---|
| 终端组合按键 | Ctrl+C / Ctrl+\ / Ctrl+Z（只对前台进程） | SIGINT(2) / SIGQUIT(3) / SIGTSTP(20) |
| 命令 | kill -signo pid / kill -9 -pgid | 任意 |

## 第 11 章 线程（Pthread）基础

进程用“一个进程一块独立内存”换来了资源隔离，但每个进程都要消耗一份地址空间，进程数量被内存硬性限制。本章引入更小的执行单元——**线程**：多个线程共享一个进程的资源，只做调度单位。本章覆盖线程的诞生、与进程的关系、用户级/内核级/混合线程、查看命令、共享资源与 NPTL 库；线程库函数与线程安全在后续展开。

### 11.1 线程的诞生

**线程**是操作系统支持的**执行单元（调度单位）**：与进程一样可以获取 CPU、执行指令、完成特定任务。

线程与进程的关键区别在于资源：

- **进程的双重身份**：它既是调度单位，又是**最小的资源分配单位**——每个进程创建时都要分配独立的 0~4G 虚拟地址空间（并映射物理内存），内存开销大；
- **进程数量的瓶颈**：内存有限，而每个进程都要吃一大块内存——进程数量被内存卡死；
- **解决问题**：多个线程**共享一个进程的内存资源**——调度单位变多，内存开销不变。

> 类比：一个工人配一个工厂——工人有能力干活，但工厂（内存资源）是昂贵的附加属性；100 个工人就要盖 100 个工厂，国家（系统）再能生工人，也盖不起那么多工厂。改成 10 个工人共用一个工厂，干活的人变多、工厂还是那一座。

**结论**：**进程是最小资源分配单位，线程是最小调度单位**——创建线程不额外分配内存，只获取时间片干活。

> 线程并不“碾压”进程：两者长期共存，说明各有适用场景（线程共享资源带来的便利与风险，是后续线程安全要解决的问题）。

### 11.2 进程与线程的关系

- **包含/寄生关系**：线程存活于进程内部，与进程及其他线程共享资源，完成特定任务；
- **线程的生存环境**：线程被创建后会占用部分进程内存——典型是 **8M 线程栈**（从进程 0~3G 用户空间中划出的虚拟地址，不是系统额外分配）；
- **主控线程与普通线程**：进程默认自带一个执行单元，称为**主控线程（主线程）**；主控线程可以创建新的普通线程——主从关系，主控线程就是进程本身；
- **PCB 与 TCB**：一个进程中所有线程**共享 PCB**（进程信息）；每个线程拥有独立的 **TCB（线程控制块）**，一个包含线程信息的结构体，包含 tid 等线程信息。

```
进程
├── PCB（进程信息，所有线程共享）
├── 内存资源（0~3G 用户空间：堆、全局数据、代码…）
├── 主控线程（进程默认执行单元）  ← TCB + 8M 线程栈（独立）
├── 普通线程 1（主控线程创建）   ← TCB + 8M 线程栈（独立）
└── 普通线程 2                   ← TCB + 8M 线程栈（独立）
```

### 11.3 线程调度：用户级、内核级与混合线程

回顾：并发 = 多个执行单元共用一个 CPU 按时间片交替（阻塞时时间片就近交给相邻同类执行单元）；并行 = 多核同时执行。线程按实现分为三种：

**用户级线程**：

- 线程库安装在用户空间，由进程内的线程库负责创建、调度、切换；
- 内核**不认识线程**，只按进程为单位分配时间片；线程使用的是进程“领到”的时间片，在进程内部转手使用；
- **只支持并发，不支持并行**——内核不知道有多个调度单位，无法把多个线程分到多个核上；
- 优点：
  - 可以在任意系统安装用户级线程库使用线程——即使系统本身不支持线程技术；
  - 系统无需关心用户线程的调度（内核只看到一个进程），调度开销小；
  - 线程资源数据都在用户层，使用无需频繁层级转换（不需要反复进出内核），某些情况下开销比内核级更小、速度更快；
- 缺点：不支持物理级并行。

**内核级线程**：

- 系统原生支持，提供原生函数供开发者创建线程；
- 每个线程创建一个**内核对象**，系统按内核对象分配 CPU 与时间片；
- 支持并发；硬件多核时支持并行；
- 内核级线程体系下进程与线程的界线变得模糊——系统只看内核对象（调度单位）的数量来分配资源。

**混合线程**：

- 用户级与内核级结合：每个线程创建内核对象（可并发 + 并行）；
- 同时将线程资源安装在用户层，线程执行与访问在用户层完成，无需频繁切换到内核，提高访问效率；
- Windows 的线程属于此类。

| 类型 | 系统是否识别 | 时间片分配 | 并发 | 并行 | 典型场景 |
|---|---|---|---|---|---|
| 用户级线程 | 否（只看到进程） | 按进程分配，线程库内部转手 | 支持 | 不支持 | 不支持线程的旧系统 |
| 内核级线程 | 是（每线程内核对象） | 系统按内核对象分配 | 支持 | 支持（多核） | Linux NPTL |
| 混合线程 | 是 | 用户层 + 内核对象结合 | 支持 | 支持 | Windows |

### 11.4 查看线程：ps -eLf 与 ps -Lf

```bash
ps -eLf          # 查看系统中所有线程
ps -Lf <pid>     # 查看指定进程中的线程
```

`ps -eLf` 关键列：

| 列 | 含义 |
|---|---|
| UID | 用户 id |
| PID | 进程 id |
| PPID | 父进程 id |
| **LWP** | 轻量级进程编号（线程编号） |
| **NLWP** | 该进程的线程数量 |

- **PID == LWP** 的线程是**主控线程**，其余为普通线程；
- **NLWP = 1** → 单线程进程；NLWP = 3 → 一个主控线程 + 两个普通线程；
- **LWP 不是 TID**：LWP 是 int 型编号，用于系统调度管理（类似学号，用于点名）；线程的“真名”是 **TID**，类型为 `unsigned long int`——直接按整型打印可能得到很大的数甚至负数，打印 TID 一般按地址格式处理。

### 11.5 线程间共享与非共享资源

| 类别 | 资源 |
|---|---|
| **共享** | PCB（进程信息）、堆、全局变量/静态数据、文件描述符表、工作目录、用户 id 等进程信息、**信号行为** |
| **非共享** | 线程栈（8M）、TCB（线程信息）、线程优先级、**信号屏蔽字**、errno（见 11.6） |

- **堆可以共享**：一个线程申请的空间，其他线程只要拿到地址就能直接用；
- **文件描述符表只有一张**：进程打开 3 个文件 + 自带 0/1/2 三个标准描述符，表中一共 6 个，所有线程共用同一张表；
- **信号行为共享的隐患**：某个线程对信号设置了捕捉，这个设定会共享给所有线程——信号来了可能被其他线程捕捉处理，而不是“本应处理它的线程”。解决：**屏蔽字是线程独立的**——让其他线程各自屏蔽该信号，信号就只会由目标线程处理；
- **线程优先级独立**：每个线程可以单独调整优先级（优先级越高，获得 CPU 资源越倾斜）。

### 11.6 errno 与线程错误处理

`errno` 是全局错误号变量（`errno.h`）：系统调用失败时置位，用于判断失败原因。例如非阻塞 read 无数据返回 -1、errno 为 EAGAIN——这属于可重试的“包容性错误”，不应直接退出进程。

**多线程共享 errno 的隐患**：T1 的 read 失败，errno 被置为 30；T1 还没处理，T2 的 open 又失败，把 errno 改成 42——T1 最终拿到的是 42 的错误信息，完全错乱。

> 系统实际上对 errno 做了线程局部化处理（多线程访问时各线程看到自己的 errno），但线程库有自己的错误处理惯例，不用 errno。

**线程库惯例**：**函数成功返回 0，失败返回错误号**——用 `strerror(err)` 转成错误描述。

```c
#include <errno.h>
int main(void)
{
    int err;
    err = pthread_xxxx();    // 线程库函数成功返回 0，失败返回错误号
    if (err > 0)
    {
        printf("pthread_xxx() error:%s\n", strerror(err));
    }
}
```

几乎所有的 NPTL 线程库函数，错误处理都这么写。

### 11.7 NPTL 线程库与编译

- **NPTL（Native POSIX Thread Library）**：遵循 POSIX 标准的原生线程库，简称 **Pthread**；
- 典型的内核级线程库；
- Ubuntu 系统自带，无需用户安装、直接可用；但它随系统版本加入（并非最原始的系统调用），**编译时必须链接库**；
- 头文件：`#include <pthread.h>`；
- 编译：

```bash
gcc x.c -lpthread -o app    # -lpthread 放在 -o 之前，否则报未定义引用
```

> 线程创建、tid 获取、回收、分离、取消、退出、线程属性与线程安全（锁、同步、条件变量）等内容，后续按线程库函数逐步展开。

### C. 常见问题排查

- **僵尸进程堆积**：确认父进程是否对每个子进程都做了回收（循环 wait/waitpid）；只回收一次或漏回收都会残留；
- **进程数不对**：检查循环创建是否漏写 `if (pid == 0) break`（漏写会变成 2^n-1 的失控结构）；
- **子进程执行出错**：子进程踏出了自己的代码段，跑到父进程专属代码（如 wait）——在分支内 `exit(0)` 收尾；
- **输出看不到**：printf 加 `\n`（Linux 不显式刷新缓冲区可能看不到输出）；
- **编译报错/行为不符**：改完代码**先重新编译再运行**；注意循环变量作用域、判断用 `==` 而不是 `=`；
- **execl 加载失败**：路径必须指向**编译后的可执行文件**并拼接完整（绝对路径或 `./` 前缀）；用打印验证是否加载成功；
- **段错误**：检查内存操作——越界读写、野指针、向只读区写字面量（系统发 SIGSEGV 11 号信号）；
- **总线错误**：检查映射/访问范围是否超出文件有效长度（系统发 SIGBUS 7 号信号）；
- **浮点数例外**：检查除零等 CPU 计算异常（系统发 SIGFPE 8 号信号）；
- **孤儿进程残留**：`ps ajx` 查组号后 `kill -9 -组号` 按组清理，或用 9.5 的管道方案自动处理；
- **信号屏蔽后进程无反应**：确认屏蔽字设置是否正确（sigaddset 传的是信号名）；用 sigpending 查未决信号集，确认信号是否已抵达并被阻塞；
- **SIGCHLD 回收漏收**：捕捉函数内必须循环 `waitpid(-1, NULL, WNOHANG)` 直到返回 0/-1——SIGCHLD 不排队，只回收一次会残留僵尸；
- **信号 IPC 首包杀死子进程**：父进程 fork 后立即发信号，子进程可能尚未完成捕捉设定——fork 前先屏蔽该信号（子进程继承屏蔽），子进程捕捉设定完成后再解除屏蔽；
- **mmap 映射失败**：检查两点——映射权限是否 ≤ open 权限；映射大小是否 ≤ 文件大小（超出会触发 SIGBUS 总线错误）；
- **open 管道文件阻塞**：命名管道要凑齐读、写两个权限才能打开——先跑写端会卡在 open 是正常现象，等读端跑起来就通了；
- **vim 交换文件**：编辑时提示 .swp 是上次异常退出留下的——按 `R` 恢复内容，或删除该 .swp 后重新打开；写代码**勤保存**（写一段保存一下），防止意外关闭丢失代码；
- **vim 效率配置**（可选）：配置 `.vimrc` 可以让 vim 具备代码补全、错误警告、F5/F6 一键编译、按后缀自动插入文件模板（如 .c 自动补 `#include`）等能力，接近 IDE 的体验；注意配置不要与插件强耦合。
